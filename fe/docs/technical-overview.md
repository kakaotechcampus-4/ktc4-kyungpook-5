# 운영해 FE 기술 문서 (초안)

> 기준: 2026-11-10, `develop` `63b4130`. 화면 사용법은 [README](../README.md), API 목록은 [BE API Reference](../../be/docs/api-reference.md)를 봅니다.
> 이 문서는 FE가 **무엇을 어떻게 구현했는지**와 **토리(AI)가 자동으로 하는 일이 화면에 어떻게 드러나는지**를 설명합니다.

## 1. 한눈에 보기

운영해 FE는 동아리 운영진이 쓰는 React SPA이고, PWA로 설치해 쓸 수 있습니다.
FE는 BE만 호출합니다. AI(`be/app/ai`)는 BE 프로세스 안의 모듈이라 FE가 직접 부르지 않습니다.

```text
브라우저 (React 19 SPA · PWA)
 ├─ REST  /api/v1 (axios) ─────────── 조회·저장·승인
 ├─ SSE   (fetch 스트림) ──────────── 계획 대화·생성: 토리 작업 진행 줄 + 답변 조각
 ├─ WebSocket ─────────────────────── 회의 음성 PCM16 16kHz 전송, 전사·판단 신호 수신
 └─ Service Worker ◀── Web Push ───── 할 일 예약 알림
        │
        ▼
BE (FastAPI) ── app.ai (LangGraph · LLM) / PostgreSQL + pgvector / Whisper STT / Push 발송
```

| 기능 | 통신 방식 | 왜 이 방식인가 |
| --- | --- | --- |
| 행사 계획 대화·생성 | SSE (POST 응답 스트림) | 토리가 조건을 반영하고 기록을 찾는 과정을 기다리는 동안 보여 주려고 |
| 회의 음성 | WebSocket (JSON 메타 + binary 프레임) | 100ms 단위 음성을 끊김 없이 보내고 서버 확인(ack)을 받으려고 |
| 회의 전사·답·후보 | REST 폴링 (2.5초) + WS 신호로 즉시 재조회 | 화면은 서버에 저장된 상태만 그린다. WS 메시지를 그대로 그리지 않는다 |
| 자료·영수증·초안 처리 상태 | REST 폴링 (처리 중일 때만) | 서버 비동기 작업이 끝나면 폴링을 멈춘다 |
| 예약 알림 | Web Push + Service Worker | 앱을 닫아도 기기 알림으로 받는다 |

## 2. 토리가 자동으로 하는 일

운영해의 원칙은 **토리는 제안하고, 운영진이 확정한다**입니다.
그래서 FE의 일은 두 가지입니다. 토리가 자동으로 한 일을 **보이게** 하고, 운영진이 확정하는 순간을 **분명하게** 만드는 것입니다.

| 기능 | 토리가 알아서 하는 일 | 화면에 드러나는 방식 | 운영진이 확정하는 지점 |
| --- | --- | --- | --- |
| 행사 계획 대화 (P1) | 대화에서 행사 조건 6칸(행사 이름·종류·예상 인원·참가비·일정·장소)을 뽑아 반영. 필요하면 동아리 과거 기록을 찾아 근거로 붙임 | 답변 위에 「토리가 처리한 작업」 줄(진행 중 → 완료). 바뀐 조건 칸을 1.5초 강조. 조건마다 확정·잠정·미정·나중에 표시, 잠정이면 근거 발화 인용. 참고한 기록은 파일·위치·원본 다운로드와 함께 표시 | 생성 버튼. 서버가 판단한 생성 가능 여부(`generationReadiness`)를 따르고, 막힌 이유는 문장으로 안내 |
| 계획 초안 생성 | 조건을 바탕으로 13개 단계 카탈로그에서 넣을 단계를 고르고 일정·행동을 작성. 뺀 단계에는 이유를 남김. 서버가 결과를 카탈로그·날짜·출처 기준으로 다시 검증 | 「조건 확인 → 초안 작성 → 저장 확인 → 계획 불러오기」 네 줄. 실제로 지난 구간만 체크, 퍼센트·남은 시간은 표시하지 않음 | 생성 결과는 초안. P2에서 검토 후 「운영 시작」 |
| 계획 검토 (P2) | 운영진이 계획을 고치면 바뀐 계획에 문제가 있는지 다시 검토. 단계 구성을 바꾼 뒤에는 검토를 자동으로 요청 | 단계 카드의 실행 주체 칩(AI 실행·승인 필요·직접 수행, 단계마다 카탈로그에 정해진 값), 「AI가 처음 제외한 이유」, 「검토 받기」 카드와 검토 결과(문제 있음·없음) | 단계 일정·행동 내용 수정, 단계 넣기·빼기(빼기는 확인창), 운영 시작 |
| 행사 운영: 공지·발송 초안 | 다음 단계가 시작되면 공지(NOTICE)·외부 발송(EXTERNAL_SEND) 본문 초안을 작성 | 「쓰는 중」 표시(3초 폴링), 운영진이 채울 곳은 `[ ]` 빈칸, 「다시 받기」 | 검토 창에서 수정·저장 → 승인. **승인해도 앱이 보내지 않음**: 운영진이 밖에서 게시·이체한 뒤 완료 표시 |
| 운영 중 상황 대응 | 운영진이 입력한 상황에 되물을 질문을 만들고, 답을 받으면 요약과 대응 제안을 작성 | 처리 중 2.5초 폴링. 「제안은 아직 적용되거나 발송되지 않았어요」 문구 | 제안을 실제로 적용하는 것은 운영진 |
| 회의 중 | 서버가 음성 구간을 나누고(VAD) 받아쓰기(STT). 발화마다 기록을 찾아봐야 하는 말인지 판단해 필요할 때만 과거 기록에서 답을 찾고, 같은 발화에서 일정·할 일 후보도 뽑음 | 「들은 말」과 「토리가 찾은 것」 두 칸. 답은 찾음·기록에 없음·찾지 못함으로 구분하고 출처의 「원문 보기」로 원문 위치를 엶. 찾을 필요가 없는 말(NO_LOOKUP)에는 개입하지 않음 | 녹음 시작(시작 버튼이 녹음 동의), 일시정지, 종료(되돌릴 수 없음 확인) |
| 회의 후 | 녹음에서 화자를 나누고, 운영진이 이름을 확인하면 회의록과 일정·할 일 후보를 정리 | 처리 상태 4단계, 후보 미리보기. 후보마다 근거 발화로 이동 가능 | 화자 이름 저장 뒤 후보 생성. 후보는 「후보만 저장」「알림 없이 확정」「확인 후 저장·예약」 세 버튼으로 구분 |
| 할 일 알림 | 확정한 알림 시각에 서버가 Push 발송 | 기기 시스템 알림. 누르면 해당 할 일 상세가 열림 | 알림 시각·수신자는 운영진이 직접 고름(이름으로 추론하지 않음) |
| 송금 → 장부 | 송금 행동을 완료 표시하면 서버가 지출을 자동 기록 | 장부에 「자동 기록」 표시. 연결 행사는 바꿀 수 없음 | 송금 완료 표시 |
| 영수증 가져오기 | 영수증 이미지를 읽어 지출 초안을 만듦 | 「읽는 중 → 검토 필요 → 확정됨」(읽는 중에는 5초 폴링). 「확정 전에는 지출에 반영되지 않아요」 | 「확인했어요」 체크 후 저장, 연결할 행사 선택 |
| 자료함 | 올린 파일을 파싱하고 검색용으로 색인(임베딩) | 「처리 대기 → 내용 읽는 중 → 파싱 완료 · 검색 준비 전 → 검색 준비 완료」를 구분(처리 중에는 5초 폴링). 실패 시 색인 다시 시도 | 업로드할 자료 선택 |
| 메인 브리핑 | 서버가 3일 안에 마감되는 단계, 승인을 기다리는 행동, 내게 배정된 할 일과 진행·계획 중인 행사를 모음. 문장도 이 값으로만 만들고 모델이 쓰지 않음 | 첫 화면의 「확인할 일」 줄과 행사 카드. 누르면 행사 상세나 해당 할 일로 이동 | — |
| 메인 토리에게 묻기 | 질문 의도를 모델이 분류(자료 찾기·할 일·승인 대기·행사 목록·행사 현황·회의 할 일 등)한 뒤, 서버가 DB에서 읽은 값으로 답함. 모호하면 되물음 | 한 줄 답과 카드(승인 대기, 행사 현황, 회의 할 일 등). 자료 답에는 출처와 원본 다운로드. 이어서 물을 질문 버튼 | 승인·발송·이체처럼 토리가 하지 않는 일은 해당 화면으로 안내. 계획 요청은 계획 화면 입력창에 넣어 두고 보내기는 운영진이 함 |

### 자동 처리를 화면에 보여 주는 원칙

1. **실제로 일어난 처리만 진행·완료로 표시합니다.** 진행 줄은 실제로 일어난 처리(서버가 보낸 `progress` 이벤트, 저장 확인, 계획 조회)로만 바뀌고, 가짜 진행률은 쓰지 않습니다.
2. **사실·가정·제안을 섞지 않습니다.** 사용자가 말한 조건, 기록에서 확인한 사실, 토리의 가정, 확인하지 못한 내용을 다른 표시로 보여 줍니다.
3. **근거가 있는 답에는 출처를 붙입니다.** 출처는 `recordId`로만 열고, 다른 소속의 자료는 열지 않습니다. 기록끼리 내용이 달라도 FE가 정답을 고르지 않습니다.
4. **확정은 따로 누릅니다.** 저장·확정·예약을 다른 버튼으로 나누고, 밖으로 나가는 행동은 확인 체크나 확인창을 거칩니다.

## 3. 구조

### 레이어

```text
pages/<Screen>Page.tsx        화면 조립
  └─ features/<domain>/components/   화면 조각
       └─ features/<domain>/hooks.ts  TanStack Query 훅 (캐시 키, 폴링 주기, 저장 뒤 재조회)
            └─ features/<domain>/api.ts   엔드포인트 함수
                 └─ shared/api/client.ts  axios 인스턴스 (인증, 봉투 해제, 오류 통일)
```

- 원칙은 `features/`끼리 import하지 않는 것입니다. 여러 기능이 쓰는 세션·소속 상태는 `shared/auth`, `shared/session`에 둡니다. 다만 지금은 메인·계획·회의 등이 다른 feature의 컴포넌트·타입을 가져다 쓰는 곳이 남아 있습니다.
- 서버 상태는 TanStack Query, 전역 상태는 Zustand(세션 토큰·선택 소속, 녹음 중 잠금, 토스트), 화면 상태는 `useState`로 나눕니다.
- 서버 enum → 화면 문구는 `shared/lib/labels.ts`, 오류 `code` → 문구는 계획·회의·행사의 `errors.ts`나 각 기능의 hooks에서 바꿉니다.

### 타입 계약

BE의 OpenAPI 문서에서 `openapi-typescript`로 `src/shared/api/schema.d.ts`를 생성합니다(`npm run gen:api-types`).
요청·응답 타입이 BE 스키마(`be/app/schemas/`)에서 나오므로, BE가 필드를 바꾼 뒤 타입을 다시 생성하면 `tsc -b`가 어긋난 화면 코드를 알려 줍니다.

### HTTP 클라이언트 (`shared/api/client.ts`)

- 응답 봉투 `{ data, meta }`를 벗겨 돌려주고, 오류 봉투는 `ApiError(code, message)`로 통일합니다.
- 401이 오면 refresh를 **한 번만** 호출합니다. 동시에 온 401은 같은 갱신을 기다리고, 재시도도 한 번뿐입니다.
- SSE는 axios가 브라우저에서 응답을 조금씩 읽지 못해 `fetch` + `ReadableStream`으로 받습니다. 파서(`shared/api/sse.ts`)는 네트워크와 분리된 순수 함수입니다.

## 4. 기능별 구현

### 4.1 행사 계획: 스트리밍과 요청 복구

**스트림 처리** (`features/planning/stream.ts`)

| 이벤트 | 처리 |
| --- | --- |
| `progress` | 같은 `operationId`의 「진행 중」 줄을 결과 줄로 바꿈 |
| `reply_delta` | 답변 조각을 이어 붙임 |
| `reply_reset` | 받은 조각을 버림 |
| `done` | 응답 모양을 검사한 뒤 결과로 채택 |
| `error` | `ApiError`로 던지고 계획을 다시 불러옴 |

**같은 요청이 두 번 처리되지 않게 하는 장치**

- 채팅은 메시지마다 `crypto.randomUUID()`로 만든 `messageId`를, 생성 버튼은 새 UUID를 `Idempotency-Key`로 보냅니다.
- 요청 본문에 화면이 본 `baseRevision`을 넣습니다. 보내기 전에 서버의 snapshot과 비교해 다르면 보내지 않습니다.
- 진행 중인 요청은 탭 기록(sessionStorage, 행사별)으로 잠급니다. 기록을 남기지 못하면 첫 요청도 보내지 않습니다.
- 한글 입력 조합 중의 Enter는 전송하지 않습니다.

**연결이 끊겼을 때** — POST를 다시 보내지 않고 `GET /plan/requests/{key}`로 결과만 확인합니다.

| 결과 | 화면 |
| --- | --- |
| `completed` | 받았어야 할 응답으로 이어서 처리 |
| `processing` | 3초 뒤 다시 조회 |
| `not_saved` | 잠금을 풀고 보냈던 문장을 입력창에 되돌림 |

**생성 완료 확인** — P2로 넘어가기 전에 저장된 snapshot을 검사합니다(revision이 1 올랐는지, 단계 ID가 새것인지). 생성 중 「대화로 돌아가기」를 눌러도 생성은 계속되고, 끝나면 P1에 「계획 검토하기」 링크가 뜹니다.

### 4.2 회의: 음성 파이프라인

```text
마이크 (getUserMedia: mono, echoCancellation, noiseSuppression)
  → AudioWorklet (public/meeting-pcm-worklet.js): 채널 평균으로 mono
  → pcm.ts: 16kHz로 리샘플, 100ms(1600샘플)씩 Int16 LE
  → transport.ts: WS로 JSON {audioSeq, startMs, endMs} → binary 프레임
  → BE: VAD → Whisper STT → 발화 판단 → 기록 검색 → 답 저장
```

- **켜는 순서**: WS 연결 → `start` → 서버의 `audio.ready`로 형식 확인 → 그 뒤에 마이크 권한을 요청합니다. 서버가 준비되지 않았는데 녹음부터 하지 않습니다.
- **FE와 서버의 경계**: FE는 형식 변환과 전송만 합니다. 음성 구간 나누기(VAD)·받아쓰기·판단은 서버가 합니다.
- **끊김 대비**: 서버가 받았다고 확인한(ack) 프레임 번호를 기억합니다. 연결이 끊기면 500ms 뒤 `resume{lastAckSeq}`로 다시 붙고, 서버가 알려 준 마지막 번호 이후의 프레임만 다시 보냅니다.
- **무한정 쌓지 않기**: 연결된 상태에서 전송 대기 버퍼가 256,000바이트를 넘거나 확인받지 못한 프레임이 100개(10초 분량)에 이르면 마이크를 멈춥니다. 끊긴 동안 쌓인 프레임이 100개를 넘어도 실패로 처리합니다. 프레임을 조용히 버리지 않습니다.
- **끝내는 순서**: worklet flush → 남은 tail 전송 → `end{lastAudioSeq}` → `audio.end_ack`(번호 일치) → `audio.completed`(오류 0). 이 단계를 모두 통과해야 「완료」로 봅니다.
- **일시정지**: 트랙을 끄고 무음을 계속 보내며, 그 시간은 녹음 시간에서 뺍니다.
- **녹음 중 이탈 방지**: 라우터 이동(`useBlocker`)과 새로고침(`beforeunload`)을 막습니다.
- **노이즈 억제**: RNNoise(wasm, Worker)를 구현해 두었지만 현재 화면은 브라우저 기본 `noiseSuppression`만 씁니다. 브라우저가 이를 끄면 배너로 알립니다.

### 4.3 회의: 타임라인과 근거

- 회의 정보는 녹음·마무리 중 3초, 전사·판단·후보는 2.5초마다 폴링합니다. WS로 `transcript.final`·`judgment` 신호가 오면 즉시 재조회합니다.
- 답은 `sourceId`+`sourceVersion`이 일치하는 것만 보이고, 오래된 판단(STALE)은 숨깁니다.
- 진행 중에는 답을 도착 순서로, 종료 후에는 발화 순서로 정렬합니다. 새 답에는 「새 답」 배지와 스크린리더 알림을 붙입니다.
- 「근거 발화 보기」를 누르면 해당 발화로 스크롤·포커스합니다. 그사이 근거가 바뀌었으면 「다시 확인」을 안내합니다.
- 후보 저장: 「후보만 저장」(PATCH) / 「알림 없이 확정」(PATCH 후 accept) / 「확인 후 저장·예약」(confirm). 알림 시각은 미래여야 하고 일정·마감보다 늦을 수 없습니다.

### 4.4 행사 운영: 승인과 실행

- 승인 대기 행동에는 「검토하기」만 있습니다. 고친 내용을 저장하지 않으면 승인할 수 없습니다.
- 승인 후 상태는 「실행 대기」입니다. 앱이 직접 보내지 않고, 운영진이 복사·게시·이체한 뒤 「게시했습니다」「이체했습니다」로 완료를 표시합니다.
- 모든 처리 요청에 화면이 본 `expectedVersion`을 보냅니다. 그사이 내용이 바뀌어 409가 나면 다시 불러와 확인하게 합니다.

### 4.5 알림 (PWA · Web Push)

- 앱 시작 때 Service Worker를 등록하지만 알림 권한은 요청하지 않습니다. 권한은 사용자가 버튼을 눌렀을 때만 요청합니다.
- 구독: VAPID 키 → `PushManager.subscribe` → 서버 등록. 서버가 active로 답해야 등록 완료로 봅니다. 해제는 서버에서 먼저 지운 뒤 브라우저 구독을 풉니다.
- `sw.js`는 받은 payload의 URL이 같은 origin의 http(s)이고 계정 정보가 없을 때만 엽니다. 그 밖에는 `/meetings`로 보냅니다.
- 알림을 누르면 `/meetings?taskId=&clubId=`로 열리고, 페이지가 사용자의 소속을 확인한 뒤에만 그 할 일을 엽니다.
- 「서버가 Push를 접수함」과 「기기에 알림이 표시됨」을 구분해 안내합니다.

### 4.6 인증과 계정 전환

- 이메일 로그인과 카카오 OAuth를 지원합니다. 카카오는 32바이트 무작위 `state`를 sessionStorage에 두고 콜백에서 검증합니다.
- 서비스 대상은 회장(OWNER)·임원(MANAGER)입니다. `/me` 응답에서 이 소속만 선택할 수 있게 합니다.
- **오래된 응답 차단**: 로그인·로그아웃마다 `sessionId`를 올리고, 요청 때와 응답 때의 `sessionId`가 다르면 응답을 버립니다. 다른 탭의 로그인 변화는 `storage` 이벤트로 감지합니다. 계정을 바꾼 직전에 출발한 요청이 새 계정 화면에 섞이지 않게 하려는 장치입니다.
- 로그인 뒤 이동할 주소는 같은 origin의 안전한 경로만 허용합니다(`features/auth/destination.ts`).

## 5. 실패를 다루는 방식

| 상황 | 화면 |
| --- | --- |
| 기록을 찾았지만 없음 vs 검색 자체 실패 | 「기록에 없음」과 「찾지 못함」을 다르게 표시 |
| 회의 후보 추출 실패 vs 후보 0건 | 실패 배너와 「후보 없음」을 구분 |
| 자료 파싱 완료(COMPLETED) vs 검색 준비 완료(INDEXED) | COMPLETED를 검색 가능으로 보지 않음 |
| 계획 생성 결과 불명 | 서버가 거절한 경우와 「확인하지 못함」을 나누고, 후자는 결과 조회로 확인 |
| P2 수정 중 일부만 저장됨 | 저장된 항목 이름과 실패 건수를 함께 알리고 최신 계획을 다시 불러오게 함 |
| 개발용 예시 | `?demo`·`?fixture=1`은 명시한 경우에만. API 실패를 예시 데이터로 대체하지 않음 |

## 6. 테스트와 품질

- 단위 테스트 173개가 있습니다(`node --test tests/*.test.mjs src/shared/api/sse.test.mjs`). `tests/`의 37개 파일이 172개, SSE 파서가 1개입니다. 음성 변환·서비스 워커 테스트도 `tests/` 안에 들어 있습니다. 별도 테스트 프레임워크 없이 `node:test`로 돌립니다.
- 주로 지키는 규칙
  - 계획: 진행 줄은 실제 결과만, 끊겼을 때 POST 재전송 금지, 결과 조회 3분기, 조건 강조는 바뀐 칸만
  - 회의: 음성 프레임 순서(메타 → binary → end), ack 없으면 완료 불가, 48kHz → 정확히 초당 16,000샘플, 일시정지 시간 제외, 오래된 판단 숨김, 출처는 같은 소속 자료만
  - 인증: refresh 한 번, 다른 계정·다른 탭의 응답 차단, 안전하지 않은 목적지 차단
  - 알림: 외부·`javascript:`·계정 정보가 든 URL 거부, 현재 소속과 일치할 때만 할 일 열기
- CI(`deploy.yml`)는 PR과 `develop` push마다 `npm ci → lint → build`를 실행합니다. 단위 테스트는 아직 CI에 넣지 않았습니다.
- `tests/e2e/`에 Playwright 스크립트 6개(계획 생성, 조건, P2 검토, 스트림 끊김, 행동 초안 등)가 있습니다. 개발 서버만 필요한 것, 가짜 API로 도는 것, 합성 DB가 필요한 것이 섞여 있고 조건은 파일 머리말에 있습니다.

## 7. 한계와 다음 일

- RNNoise는 구현만 하고 현재 화면에서는 켜지 않았습니다.
- WS 재접속은 서버가 상태를 60초 동안 들고 있는 동안만 이어집니다. 모바일 백그라운드 녹음과 오프라인 캐시는 지원하지 않습니다.
- 단위 테스트는 CI에서 돌지 않습니다.
- `?demo`는 `/dashboard`, `/planning`, `/events`, `/mypage`에서만 동작합니다.
- 메인 토리 대화는 서버에 남기지 않아 새로고침하면 사라집니다.
