# 행사 계획 P1 → 생성 중 → P2 UX 구체화안

기준: 2026-11-05, `origin/develop` `af8e492` 및 사용자와의 논의. 상태: **P2 시안 채택 / 제품 구현 미착수**. P2 기본 화면과 두 수정 동선, 묶음 내 드래그 정렬·경계 강화는 사용자가 채택했다(§17). 생성 전환·복원·교체 동의 등 나머지 정책은 해당 이슈에서 확인한다. 제품 코드는 변경하지 않았다. 상위 작업: [#317](https://github.com/kakaotechcampus-4/ktc4-kyungpook-5/issues/317). 확인창·접근성 등 기존 후속: [#316](https://github.com/kakaotechcampus-4/ktc4-kyungpook-5/issues/316).

## 1. 합의된 방향과 범위

- 주 사용자는 PC로 비슷한 행사를 반복 준비하는 동아리 운영진이다. 4번 첨부는 4K 환경이며 맥북 프로 14인치에서는 화면이 충분히 차 보인다. 4K 캡처만으로 노트북에서도 밀도가 낮다고 판단하지 않는다.
- P1은 대화로 조건을 정하는 화면, P2는 계획을 검토·수정하는 화면이다. P2의 이전 대화는 읽기 전용이다. 새 대화는 P1에서만 한다.
- P2 설계·구현을 먼저 진행한다. 생성 중 대화 복귀는 P2 이후 편의 기능으로 미루며 P2 완료 조건에 포함하지 않는다. 초안 재진입은 P2, 조건 변경 시 기존 초안 보존에 동의했다.
- P1의 조건 요약과 생성 버튼을 한 덩어리로 묶는다. 참고한 과거 기록의 내용·출처·다운로드·조회 이력은 유지한다.
- 채팅과 버튼은 두 생성 진입점이며 같은 생성 중 상태와 P2로 이어진다. 화면이 바뀌어도 진행 중인 요청이 끊기지 않는다.
- 운영 시작은 행사를 진행 상태로 바꾸는 행동이다. 공지 발송·이체 등이 시작 버튼만으로 실행된다고 설명하지 않는다.
- 방문자 모드는 Operate다. 현재 토리·블루·중립색·공용 컴포넌트를 바탕으로 정보 위계와 흐름을 정돈한다. 전체 사이트 재디자인, 새 채팅 graph, 새 자동 실행 기능은 이 설계 범위에 포함하지 않는다.

## 2. 제안하는 화면과 주소

모두 같은 ‘행사 계획’ 화면의 작업 단계다. 제목과 작은 단계 안내의 위치를 유지하고 아래 내용을 바꾼다. 생성 중은 세 번째 사용자 단계로 세지 않는다.

```text
행사 계획 · 행사 이름 또는 새 계획
① 행사 조건 → ② 계획 검토
────────────────────────────────────────
P1        대화                 이번 행사 조건
                              생성 가능 안내 + 생성 버튼
                              참고한 과거 기록

생성 중          토리 · 초안을 만들고 있어요
                 이번 요청에 사용할 조건
                 [대화로 돌아가기: P2 이후 후속]

P2        준비 순서와 단계      확인할 점
                              계획 요약
                              운영 시작
```

- 제안 주소는 `/planning?eventId=…&stage=conditions`와 `stage=review`다. 기존 `eventId`를 유지한다. 예전 `stage` 없는 링크도 지원한다.
- 기본 진입: 새 계획 또는 초안 없음 → P1. 저장된 초안 있음 → P2. ‘행사 조건 수정’으로 명시한 진입은 초안이 있어도 P1을 연다.
- 위 기본 진입은 계획 중인 행사를 계획 화면에서 여는 경우다. 행사 목록의 기존 카드→행사 상세 동선은 유지한다. 계획 중 상세에 ‘계획 이어보기’를 두어 초안 있음→P2/없음→P1로 연결하는 안을 다음 와이어프레임에서 확인한다. 진행 중·완료 행사는 운영/기록 상세를 유지한다. 같은 eventId를 사용하고 별도 행사나 별도 목록을 만들지 않는다.
- 초안 없이 P2 주소를 열면 P1로 안내한다. 진입·뒤로 가기·새로고침은 생성 API를 호출하는 계기가 아니다.
- 생성 중 표시만으로 주소를 추가하지 않는다. 자동 P2 전환은 현재 작업 기록을 교체하고, ‘조건 수정’ 등 사용자가 직접 선택한 이동은 뒤로 가기로 되돌아올 수 있게 한다.
- 미완료 요청이 있으면 기본 진입 판단보다 해당 요청의 결과 확인이 먼저다. 오래된 초안이 있다는 이유로 새 요청도 성공했다고 표시하지 않는다.

## 3. P1: 조건을 확인하고 초안을 요청한다

### 화면 구성

- 왼쪽: 기존 대화·빠른 답변·입력창. 입력한 문장과 기존 대화 위치는 생성 상태를 열었다 돌아와도 보존한다. 서버 저장 여부와 브라우저 임시 입력을 구분한다.
- 오른쪽 첫 카드: ‘이번 행사 조건’. 행사 이름·종류·예상 인원·참가비·일정·장소를 표시하고, 같은 카드 하단에 생성 안내와 주 버튼을 둔다.
- 오른쪽 다음 카드: 최신 PR #320·#322의 ‘참고한 과거 기록’. 조회 전 자리, 최근 결과 1개, 더 보기, 이전 조회, 출처·다운로드를 유지한다. 긴 기록이 생성 버튼을 아래로 밀지 않는다. 과거 기록을 올해 조건에 자동 채우지 않는다.
- ‘계획 이어보기’는 기존 기능을 유지하되 작업 영역보다 강한 제목이나 커다란 카드로 만들지 않는다. 목록 명칭 개선은 기존 #316의 별도 범위다.

### 상태와 문구 제안

| 상태 | 안내와 행동 |
| --- | --- |
| 아직 생성 불가 | 필요한 항목과 미정으로 답할 수 있는 항목을 현재 서버 판정에 맞춰 안내. 버튼은 비활성 |
| 생성 가능 | ‘만든 뒤 단계와 일정을 수정할 수 있어요.’ + **이 조건으로 초안 만들기** |
| 일반 채팅 처리 중 | 채팅 진행 표시. 생성 버튼은 중복 요청 방지를 위해 잠그되 ‘초안 생성 중’으로 바꾸지 않음 |
| 기존 초안 있음 | **이 조건으로 다시 만들기**와 **기존 초안 보기**. 교체 전 확인은 #316과 공통 처리 |
| 새 초안이 준비됨, 사용자는 P1에 머무름 (복귀 편의 기능 추가 이후) | ‘초안이 준비됐어요.’ + **계획 검토하기**. 자동으로 화면을 빼앗지 않음 |

생성 가능 여부는 서버의 `generationReadiness`를 사용한다. ‘여섯 항목 중 N개’ 같은 점수나 ‘종류만 있으면 가능’ 같은 별도 규칙을 FE가 만들지 않는다. 잠정·미정·명시적 보류·무료를 구분한다.

채팅에서 사용자가 생성을 요청하면 기존 해석 경로를 유지한다. 빠른 생성 버튼을 새로 붙이려면 실제로 유효한 생성 제안을 알 수 있어야 하며, 답변 문자열에서 제안을 추측해 버튼을 만들지 않는다. 버튼 클릭을 가짜 사용자 발화로 저장하지 않는다.

## 4. 두 진입점의 공통 전환

이번 제안은 기존 #317의 **A안**이다. AI의 생성 Tool과 graph 의미를 바꾸지 않고 기존 스트림을 계속 받는다. B안의 별도 요청 계약이나 지연 개선은 이번 UI 변경에 섞지 않는다. A안이 더 빠르다는 주장은 하지 않는다.

| 시점 | 버튼 경로 | 채팅 경로 |
| --- | --- | --- |
| 요청 | 클릭 즉시 공통 대기 상태. 서버가 받아 생성하기 전에는 ‘초안 생성 요청을 확인하고 있어요’ | 일반 대화 대기·실제 진행 줄을 유지 |
| 실제 생성 시작 | `generation_started` 이후 ‘초안을 만들고 있어요’ | 같은 이벤트가 오면 공통 생성 중 화면으로 전환 |
| AI 생성 종료 | 결과 저장을 기다림 | 후속 토리 답변과 결과 저장을 계속 기다림 |
| 저장 성공 확인 | `done`의 `generationResult.status=generated`와 저장된 새 단계 조회를 확인한 뒤 P2 | 동일. 후속 설명은 저장된 이전 대화에서 확인 가능 |
| 추가 질문 필요 | P1에 질문·이유 표시 | P1의 토리 답변으로 계속 진행 |
| 명시적 실패 | P1로 돌아가 실패 이유·재시도 표시. 기존 초안과 저장 조건 보존 | 동일 |
| 결과 확인 불가 | 실패로 단정하지 않고 ‘처리 결과 확인 중/확인 필요’. 새 생성보다 기존 요청 확인을 먼저 제공 | 동일 |

`generation_finished`는 저장 완료가 아니므로 이 이벤트만으로 P2 성공 화면을 열지 않는다. 새 단계 불러오기만 실패했다면 생성 API를 다시 호출하지 않고 **초안 다시 불러오기**를 제공한다. 이전 단계가 조회됐다는 이유만으로 이번 요청이 성공했다고 판정하지 않는다.

## 5. 생성 중: 요청 기준을 유지하며 기다린다

- 페이지 제목과 단계 안내는 유지한다. 단계 안내에는 ‘행사 조건 ✓ → 계획 검토 준비 중’처럼 설명하고 별도 3단계를 만들지 않는다.
- 본문 중앙에 토리, 현재 상태, 생성에 사용하는 조건을 보여준다. 조건 반영 이벤트로 기준이 갱신되면 서버가 확인한 값으로 맞춘다. 과거 기록의 값이나 임의의 날짜를 끼워 넣지 않는다.
- 현재 실제 상태만 표시한다. 백분율이나 확인하지 못한 내부 생성 단계를 그리지 않는다. 예상 시간은 최신 실측이 제공될 때만 사용하고, 경과 시간은 보조 정보로 둔다.
- **후속 편의 기능:** **대화로 돌아가기**는 보기만 P1으로 바꾼다. ‘초안 생성은 계속돼요’라고 안내하며 요청을 취소한 것처럼 설명하지 않는다. 돌아간 P1은 대화 기록을 읽을 수 있지만 완료 전 새 채팅·생성·조건 변경을 잠근다. 최초 생성 전환에서는 이 버튼을 노출하지 않는다.
- 생성 화면에 머물러 있으면 성공 후 P2로 자동 이동한다. 다른 계획을 열었으면 현재 화면을 강제로 바꾸지 않는다. 이후 대화 복귀 기능을 추가하면 P1 복귀에도 같은 원칙을 적용한다.
- 성공·추가 질문·실패·결과 미확인은 각각 한 번 알린다. 키보드 포커스는 자동 전환 후 새 화면 제목으로 옮기되 일반 채팅 응답이나 조건 강조마다 이동시키지 않는다. 모션 감소 설정을 따른다.

## 6. P2: 계획을 읽고 필요한 부분을 고친다

### 정보 순서

상단: ‘행사 계획’ 제목, 행사 조건의 짧은 요약, ‘계획 초안’ 상태, **행사 조건 수정**, **이전 대화 보기**.

왼쪽: 사전 준비 → 모집·확정 → 행사 진행·마무리 순서의 단계 흐름. 고정 카탈로그의 code로 묶음을 찾고 서버의 단계 순서를 보존한다. 알 수 없는 단계가 와도 숨기지 않고 확인할 수 있게 한다.

각 단계는 이름, 날짜/기한 또는 ‘일정 미정’, 담당 방식(기존 AI 실행·승인 필요·직접 수행), 실제 행동 제목, 수정 진입을 표시한다. 색 점 외에 글자로 담당을 읽을 수 있어야 한다. 행동이 없는 단계에 할 일·자동 처리·설명을 임의 생성하지 않는다. 현재 API에 없는 AI 목적 문장은 시안 문구로 채워 넣지 않는다.

오른쪽: ① 확인할 점(있을 때) → ② 계획 요약 → ③ 운영 시작. 경고가 길면 핵심과 더 보기를 제공해 주 행동이 과하게 밀리지 않게 한다. ‘확인할 점’은 AI 검토 의견이며 실행 시 ‘승인 필요’와 다른 정보다.

### 기존 기능과 연결

- 단계 구성은 기존 `/planning/steps`에서 편집한다. 처음부터 P2 안에 새 편집기를 만들지 않는다. 돌아올 위치를 현재 eventId의 P2로 명시하고, 저장 성공 뒤 최신 단계를 읽는다.
- 단계 세부 수정도 기존 상세 모달을 재사용한다. 구성 저장과 세부 저장의 기존 단위·충돌 처리·삭제 확인을 유지한다.
- 현재 API가 주는 요약은 전체/AI/승인/직접 수행 네 가지 단계 수다. 준비 기간·공지 횟수·수금 총계 등 시안의 추가 숫자는 검증된 계산 계약이 없으면 표시하지 않는다.
- 생성 경고와 수정 후 검토는 기존 `PlanReviewCard`의 최신 버전 판정·실패·재검토 상태를 유지한다. 과거 검토가 현재 계획의 검토인 것처럼 보이지 않게 한다. 검토 실패만으로 저장된 계획 전체를 실패 화면으로 바꾸지 않는다.
- **이전 대화 보기**는 오른쪽 패널을 연다. 실제 저장된 대화와 동일 순서로 보여주고 입력창·전송·과거 빠른 답변 실행은 제공하지 않는다. 새로고침으로 사라지는 임시 작업 줄을 저장된 사실처럼 복원하지 않는다. 닫으면 열었던 버튼으로 포커스를 돌린다.

## 7. 조건 수정과 기존 초안

1. P2의 **행사 조건 수정** → 같은 eventId의 P1. 기존 대화·조건·초안은 유지한다.
2. 조건 변경은 기존 초안을 자동 삭제하거나 자동 재생성하지 않는다. 기존 초안 보기로 P2에 돌아갈 수 있다.
3. 서버가 현재 조건과 생성 기준의 불일치를 확인하면 ‘조건을 바꾼 뒤 아직 초안을 다시 만들지 않았어요.’를 표시한다. **새 조건으로 다시 만들기**와 **행사 조건 수정**을 제공한다. 한 번 대화했다는 이유만으로 불일치라고 판정하지 않는다.
4. 재생성은 기존 초안이 있을 때 항상 교체 확인을 제안한다. ‘기존 단계와 직접 수정한 내용이 새 초안으로 바뀌어요.’ + **기존 초안 유지** / **다시 만들기**. 확인 문구만으로 서버의 보호를 우회하지 않는다.
5. **채팅으로 요청한 재생성도 같은 교체 동의가 필요하다.** 현재 FE 모달만으로 이 조건을 보장할 수 없다. #316 및 열린 PR #220의 계약과 조정해야 한다. 합의 전에는 채팅 입력을 문자열 분석해 가로채거나 자동 재전송하지 않는다. 허용된 요청/버전/확인 계약이 없으면 교체 기능을 완료 처리하지 않는다.
6. 재생성 실패는 이전 초안 유지. 요청 중에는 구 초안을 최신 결과처럼 표시하지 않는다. 오래된 초안 표시와 AI 검토의 오래됨은 별도 상태다.

초안과 조건의 불일치는 확인할 정보다. 이것만으로 기존 서버에 없는 운영 시작 금지 정책을 만들지는 않는다. 운영 시작 확인에는 불일치가 있음을 함께 알리고, 구체적인 시작 가능 여부는 실제 서버 규칙으로 판단한다. 사용자가 계획을 직접 조정한 것을 자동 검증한 것처럼 표시하지 않는다.

## 8. 새로고침·이탈·복원

- 미완료 요청은 같은 사용자·동아리·행사·탭 범위에서 식별할 수 있어야 한다. 기존 요청 키와 정확한 본문을 유지해 같은 요청 결과를 확인한다. 버튼/채팅 원래 경로를 유지하고 새 요청으로 바꾸지 않는다.
- 처리 중 응답이면 대기, 완료 응답이면 저장 결과 조회, 명시적 실패면 실패 안내, 확인 불가면 ‘결과 확인 필요’를 표시한다. 먼저 새 초안을 만들도록 유도하지 않는다.
- 화면을 바꾸는 것과 서버 작업을 중단하는 것을 구분한다. 이전 행사 요청이 나중에 끝나도 새로 선택한 행사 화면을 덮어쓰지 않는다.
- 저장된 현재 초안은 다시 열 수 있다. 미완료 요청이 있으면 옛 초안의 존재만으로 새 생성 성공을 판단하지 않는다.
- 요청 기록을 탭에 보관하는 안은 **같은 탭 복원**을 목표로 한다. 로그인 변경·동아리 변경·만료·권한 실패를 처리하고, 완료 뒤 재실행용 임시 정보를 정리한다. 다른 기기나 새 탭에서의 진행 중 복원은 서버 작업 조회 계약이 없으면 제공된다고 약속하지 않는다.

## 9. 운영 시작

- 주 버튼은 **운영 시작**. 보조 설명은 ‘행사를 진행 중으로 바꿔요. 공지 발송과 이체 등은 별도 승인이 필요해요.’
- 시작 전 확인에서 행사 이름과 실제 상태 변경을 알린다. 취소는 P2 유지, 확인 후 요청 동안 중복 실행을 막는다. 이 확인 UI는 기존 #316 담당 범위를 재사용한다.
- 현재 BE는 행사 시작일과 1개 이상의 계획 단계를 요구한다. 미정 일정으로 초안을 보는 것은 허용하되, 시작 전에는 ‘행사 날짜를 정해 주세요’와 조건 수정 동선을 제공한다. 시작일은 준비 단계의 첫 날짜와 다르다.
- 성공하면 해당 행사의 상세 화면으로 이동해 운영 상태를 확인한다. 실패하면 P2의 계획을 유지하고 오류와 다시 확인할 행동을 제공한다. 응답 불명·동시 상태 변경은 행사 상태를 조회한 뒤 재시도를 판단한다.

## 14. 고정 13단계 구현 확인과 편집 동선 구체화

확인 기준은 `origin/develop` `af8e492`의 AI 생성·검증 코드와 BE 단계 편집/생성 저장 코드다. 문서와 실행 코드가 다를 때는 확인한 실행 범위를 기준으로 아래처럼 구분한다.

- 13개는 선택 가능한 카탈로그다. AI는 포함 단계와 제외 단계/이유를 반환하고, 검증은 모든 카탈로그 단계가 두 목록 중 하나에 정확히 한 번 존재하는지 확인한다. 새 단계 코드·중복·취소 단계는 생성 카탈로그에 넣지 않는다.
- 사전 준비 3개: 담당 인원 배치, 장소·교통 알아보기, 사전 수요 조사.
- 모집·확정 5개: 모집 공지, 응답 확인, 인원·일정 확정, 예약, 참가비 수금.
- 행사 진행·마무리 5개: 사전 안내, 행사 당일, 지출 정산, 참가비 환급, 피드백 기록.
- 단계 이름·묶음·담당 방식은 카탈로그 속성이다. 수정 가능한 Action 제목과 단계 이름을 혼동하지 않는다. 사용자 지정 14번째 단계나 담당 방식 편집은 현재 범위가 아니다.
- BE 구성 편집은 포함·제외와 묶음 안 순서를 지원하며 최소 1개를 남기도록 요구한다. 그룹 순서는 고정이다. 남긴 단계의 기존 입력은 유지하지만, 제외하고 저장한 단계의 Step/Action은 삭제한다.
- 다시 포함은 과거 입력 복구가 아니다. 새 Step과 허용된 기본 Action이 만들어지며 이전 일정·입력은 자동 복원되지 않는다. 버튼은 ‘다시 포함’으로 표현하고 필요한 입력 확인을 안내한다.
- 세부 수정은 현재 Step의 일정과 기존 Action의 수정 가능 필드를 다룬다. 일정과 여러 Action 저장은 별도 요청일 수 있어 일부 저장 후 실패를 전체 저장 취소처럼 표현하지 않는다.

### P2 화면에 적용할 제안

1. 본문에는 현재 포함된 단계 흐름을 우선 보여준다. ‘13개 중 10개 포함’ 같은 표기는 완료율로 보이지 않도록 ‘포함 단계 10개 · 포함하지 않은 단계 3개’로 쓴다.
2. 본문 아래에 ‘포함하지 않은 단계 N개 보기’를 접어둔다. 실제 현재 미포함 목록은 13개 카탈로그와 저장된 포함 목록의 차이로 구한다. AI가 생성 시 반환한 제외 목록을 현재 미포함 목록으로 그대로 쓰지 않는다.
3. 이유가 있는 경우에도 ‘AI가 처음 제외한 이유’로 설명한다. 이후 사용자 편집 내역이 충분히 저장되지 않았으면 누가 마지막으로 뺐는지 단정하지 않는다. 사용자가 다시 포함한 단계를 과거 AI 제외 목록에 있다는 이유로 미포함에 중복 표시하지 않는다.
4. 단계 카드의 ‘일정·내용 수정’은 기존 상세 모달로 연결한다. 저장 후 같은 P2 카드 위치로 돌아오고, 실패/부분 저장은 실제 저장 상태에 맞춰 안내한다.
5. 목록 상단의 ‘단계 구성 변경’은 기존 구성 화면으로 연결한다. 포함/제외/같은 묶음 안 순서만 편집하고 저장 뒤 같은 행사의 P2로 돌아온다. 단계 제외 시 그 단계의 입력도 삭제된다는 확인을 유지한다.
6. 구성 수정 뒤 기존 AI 검토 흐름을 이어 표시한다. 검토는 계획을 자동 수정하는 동작이 아니며, 검토 실패가 구성 저장 실패를 뜻하지 않는다.

### 보장하지 않을 문구

현재 FE ExcludedSteps에는 ‘계획을 다시 만들어도 빼신 단계는 되살아나지 않아요’라는 문구가 있으나, 확인한 BE 생성 저장은 새 생성 결과로 전체 교체한다. 사용자 제외가 재생성에도 영구 보존된다는 보장은 확인되지 않았다. 새 P2 설계에서 이 약속을 사용하지 않는다. 재생성 보호·사용자 제외 반영은 #316·PR #220 및 #328과 별도 확인한다. 제품 코드는 이 검토에서 수정하지 않았다.

### 먼저 결정할 시안 범위

새로 그릴 중심 화면은 **P2 기본 화면 1장**이다. 여기에 포함/미포함 단계 배치와 두 수정 버튼 위치를 명시한다. 기존 상세 모달과 구성 편집 화면은 새로 전면 설계하지 않고 ‘진입→수정→저장/취소→P2 복귀’ 흐름과 삭제/부분 저장/검토 상태를 주석으로 연결한다. 이후 긴 검토 의견·일정 미정 상태를 같은 화면의 변형으로 확인한다.

## 16. 시안 피드백 반영: 묶음 내 드래그 정렬

사용자 피드백에 따라 단계 구성 변경의 위/아래 화살표를 드래그 손잡이로 바꿨다. 제품 코드는 변경하지 않고 같은 검토용 시안을 수정했다.

- 마우스와 터치로 왼쪽 손잡이를 잡아 같은 묶음 안에서 정렬한다. 이동 중에는 들어 올린 단계와 들어갈 위치를 표시한다.
- 다른 묶음에 놓으면 순서 변경을 취소한다. 사전 준비/모집·확정/행사 진행·마무리의 소속은 바뀌지 않는다.
- 각 묶음을 독립된 영역으로 구분하고, 배경이 있는 제목 행·단계 수·테두리·묶음 사이 간격으로 경계를 강화했다. 바깥의 포함 목록 전체 카드 테두리는 제거해 중첩된 카드 구성을 피했다.
- 키보드는 손잡이 버튼에서 Space 또는 Enter로 선택, 위/아래 방향키로 같은 묶음 안 이동, 다시 Space/Enter로 놓기, Escape로 정렬 취소를 지원한다.
- 정렬만으로 저장하지 않는다. 기존 ‘구성 저장’과 ‘변경 취소’ 동선을 유지한다. 제외/다시 포함도 기존처럼 동작한다.
