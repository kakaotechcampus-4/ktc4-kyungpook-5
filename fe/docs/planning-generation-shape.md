## 2. 화면과 이동

기존 ‘행사 계획’ 제목, 계획 선택, 작은 `① 행사 조건 → ② 계획 검토` 안내는 같은 자리를 쓴다.
생성 대기는 새 사용자 단계나 별도 페이지가 아니다. 대기 중 현재 단계는 ‘행사 조건’이며
새 초안 확인이 끝나야 ‘계획 검토’로 이동한다.

그 아래 대화·오른쪽 요약을 하나의 공통 대기 영역으로 교체한다.
토리 표시 → 상태 제목 → 다음에 일어날 일 한 문장 → ‘요청 기준 조건’ 순서다.
상태 제목과 조건은 함께 읽히되, 큰 화면 전체를 채우는 장식이나 진행률을 만들지 않는다.

조건은 요청 시작 시 서버에서 읽은 값과 `condition_applied.conditionDraft`처럼 서버가 검증한 값으로만 표시한다.
채팅은 실제 생성 시작 시점의 검증된 조건을 고정하고, 값이 없으면 미정/잠정/나중에를 유지한다.
현재 progress에는 생성 기준 초안 자체가 없으므로 ‘저장 완료된 생성 조건’으로 표현하지 않는다.
생성 뒤 확정 조건은 `done.draft`로 교체한다. 생성 중 임의의 숫자·날짜를 보완하지 않는다.
행사 이름/종류·일정·장소·인원·참가비·총예산 중 실제 값과 상태가 있는 항목을 보여준다.

- 버튼: 클릭 직후 ‘생성 요청을 확인하고 있어요’ → 실제 `generation_started`에서 생성 중.
- 채팅: 기존 대화·조건 반영·기록 검색 표시 유지 → 실제 `generation_started`에서 동일 생성 화면.
- 일반 상담, 기록 검색, 생성 권유, 거절, 추가 질문은 생성 시작 이벤트 없이 화면을 교체하지 않는다.
- 대기 중 새 전송·생성·계획 선택·새 계획을 잠근다. 중복 클릭은 동기적인 요청 잠금으로 차단한다.
- 서버 취소·대화 복귀 버튼은 제공하지 않는다. 다른 라우트/행사로 이탈한 뒤 늦게 완료된 요청은 현재 화면을 이동시키지 않는다.
- 브라우저 뒤로 가기·URL 진입·새로고침은 새 생성 계기가 아니다. 다른 행사로 바꿔도 해당 요청 기록을 새 행사에 적용하지 않는다.

## 3. 상태·문구·다음 행동

| --- | --- | --- |
| 버튼 요청 발송 직후, 실제 시작 전 | **생성 요청을 확인하고 있어요** / 정한 조건으로 초안을 만들 수 있는지 확인하고 있어요. | 대기. 생성 중이라고 단정하지 않음 |
| `generation_started` | **초안을 만들고 있어요** / 정한 조건에 맞춰 준비 순서와 일정을 만들고 있어요. | 대기. 예상 시간·가짜 백분율 없음 |

| `generation_finished` 이후, 최종 `done` 이전 | **생성 결과를 확인하고 있어요** / 결과와 저장 여부를 확인한 뒤 계획 검토로 이어갈게요. | 기존 스트림 계속 수신. 완료/실패 확정 안 함 |
| `done.generationResult.status=generated`, 단계 조회 중 | **저장된 초안을 불러오고 있어요** / 새 초안의 준비 순서를 확인하고 있어요. | 새 저장 단계의 조회·검증 |
| `done`의 `needs_clarification` | P1 복귀. **초안을 만들기 전에 확인할 내용이 있어요** / 서버의 실제 질문·이유 표시 | **조건 이어서 정하기**: 입력창 포커스. 기존 초안 있으면 기존 검토 링크 유지 |
| `done`의 `failed` | P1 복귀. **초안을 완성하지 못했어요** / 실제 실패 이유 표시. 기존 초안이 있으면 ‘기존 초안은 유지했어요.’ | **다시 생성 요청**은 사용자 명시 행동으로만, 조건과 보호 계약 확인 후 실행 |
| 생성 후 명시적 저장 거절: 버전 충돌/행사 상태 변경 등 | P1. **생성한 초안을 저장하지 못했어요** / 다른 변경이 있어요. 저장된 계획을 다시 확인해 주세요. | **저장된 계획 다시 확인**: GET. 생성 재전송 안 함 |
| `done generated` 후 GET만 실패 | **초안은 저장됐지만 불러오지 못했어요** / 연결을 확인한 뒤 초안을 다시 불러와 주세요. | **초안 다시 불러오기**: GET만. 기존 done 결과 유지 |
| GET 응답은 왔으나 옛 단계/버전 불일치/빈 단계 | **새 초안을 확인하지 못했어요** / 이번 요청으로 저장된 준비 순서를 다시 확인해 주세요. | **초안 다시 확인하기**: GET만. 옛 결과를 새 성공으로 쓰지 않음 |
| `done/error` 없이 단절, 파싱 실패, 응답 불명 또는 저장 여부 불명인 5xx | **연결이 끊겨 결과를 확인하지 못했어요** / 요청이 처리됐을 수 있어요. 같은 요청의 결과를 확인하기 전에는 다시 만들지 않아요. | 새 생성 잠금. 아래 결과 확인 계약 적용 |
| 조회 중/다른 탭에서 더 최신 버전으로 변경됨 | **생성 뒤 계획에 다른 변경이 있어요** / 현재 저장된 계획을 확인해 주세요. | **현재 계획 확인하기**: 명시적 최신 P2 진입. 이번 생성의 자동 성공/완료 알림과 구분 |
| 이번 요청의 저장된 새 초안 확인 | P2로 자동 이동. **계획 초안 N단계를 만들었어요** 한 번 | 같은 eventId의 `stage=review`, replace, P2 행사 제목에 포커스 |

‘기존 초안 유지’ 문구는 해당 실패에서 저장 전 트랜잭션이 거절됐거나 `done failed`임을 확인했을 때만 쓴다.
불명 상태에서 ‘저장되지 않았어요’ 또는 ‘기존 초안은 그대로예요’라고 단정하지 않는다.
예상하지 못한 5xx는 명시적 저장 실패와 구분한다. `generation_finished.failed` 뒤에도 채팅 Agent의 후속 처리가 가능하므로 최종 결과까지 기다린다.
같은 요청 안에서 생성이 다시 시작되면 실제 새 시작 이벤트에 따라 생성 중으로 돌아간다.

`done failed/needs_clarification`에도 같은 채팅에서 바뀐 조건이 저장될 수 있다.
이때는 성공적으로 저장된 `done.draft`를 유지한다. 요청 전 조건으로 되돌리거나 기존 단계를 지우지 않는다.
스트림의 임시 조건만 받은 채 저장이 실패했다면 GET으로 마지막 저장 조건을 다시 읽는다.
서버의 사용자용 `reason/reply`를 사용하고 내부 rule/path·공급자 오류 원문은 제품 문구로 노출하지 않는다.

## 4. 새 초안임을 확인하는 기준

현재 `PlanViewOut`은 `baseRevision`과 generated 여부를 주지만 생성 ID·저장 planRevision·단계 ID를 주지 않는다.
그러므로 아래 기준을 함께 확인한다. 단순한 `steps.length > 0` 또는 planRevision 증가만으로 성공 판정하지 않는다.

1. 발송 전에 같은 행사의 **일관된** `steps/snapshot`으로 기준 baseRevision·planRevision·단계 ID 집합을 확보한다. 확보 실패 시 POST를 보내지 않는다.
2. 그 요청의 `done`에서 `generationResult.status=generated`를 확인한다. 반환 revision이 발송 기준 다음 revision인지 확인한다.
3. 새 GET `steps/snapshot`의 baseRevision이 done과 같고 planRevision이 발송 전보다 증가했는지 확인한다.
4. 단계가 1개 이상이고, 현재 저장 구현이 전체 교체하며 새 ID를 부여한다는 계약에 따라 이전 단계 ID와 겹치지 않아야 한다.
5. P2의 screen·messages·steps를 갱신하고, screen의 baseRevision·planRevision이 단계 snapshot과 일치하는지 확인한다. 읽기 사이 버전이 바뀌면 재조회한다.
6. 위 검증을 통과한 동일 스냅샷을 P2 캐시에 넘긴 뒤 이동한다. 더 최신 버전이면 자동 성공 대신 현재 계획 확인 경로를 제공한다.

기준 조회와 실제 POST 사이에 다른 변경이 생기면 BE의 revision 충돌을 그대로 받는다. 최신 revision으로 요청 값을 덮어써 자동 재전송하지 않는다.
단계 ID 비교는 현재 materialize 구현의 계약이며, 향후 ID를 재사용한다면 요청별 저장 식별자를 제공하는 BE 계약으로 교체해야 한다.

## 5. 스트림 소유권·접근성·화면 크기

- 결과 조회 실패·결과 불명에서도 잠금을 무조건 해제하지 않는다. 생성 요청의 종료와 P2 준비 완료를 구분한다.
- 사용자/동아리/행사/요청 ID를 확인한 뒤에만 캐시·상태를 갱신한다. 이전 요청의 완료로 새 행사 화면을 이동시키지 않는다.
- 상태 영역의 `role=status`는 문장이 바뀔 때만 알린다. 답변 조각·로딩 모션을 반복 낭독하지 않는다. 오류는 한 번 알리고 복구 버튼을 설명한다.
- P1→대기 전환에서 사라지는 입력/버튼의 포커스는 대기 제목으로, 질문/실패에서 돌아오면 복구 안내 또는 입력창으로, 성공은 P2 행사 제목으로 옮긴다.
- 완료 낭독은 한 곳이 소유한다. 기존 채팅 완료·토스트·P2의 중복 낭독을 막고 탭 복원에서도 같은 요청 완료를 반복 알리지 않는다.
- 기존 토리·상태 표시를 재사용한다. 움직임 줄이기에서는 정지 상태 표시와 텍스트로 동등한 정보를 제공한다. 화면 전환용 지연·완료 타이머는 없다.
- 노트북에서는 상태와 요청 기준이 첫 화면에서 읽히게 하고, 좁은 화면에서는 상태→조건→복구 버튼 한 열로 배치한다. 긴 행사명/장소·여러 실패 문장을 자르지 않는다.
- UI 구현 직전에 craft-floor를 읽는다. 1280×800·1440×900·1024 경계·390·320 CSS px와 실제 사용 브라우저 viewport를 기록하고 키보드/모션 감소를 검증한다. 4K 하드웨어 해상도를 CSS 너비로 쓰지 않는다.

## 6. 새로고침·연결 단절: #326 최소 안전성과 BE 의존성

**추천: 안전성에 필요한 최소 기록·중복 방지는 #326, 편의 복귀는 #327.**
같은 탭에 미해결 요청이 있으면 원래 eventId와 사용자/동아리 범위를 알아야 한다.
발송 전에 탭 저장소에 요청 키·원래 경로·정확한 본문·기준 revision/단계 ID·생성 시작 여부를 기록한다.
새 행사가 첫 채팅 중 만들어졌다면 URL에 아직 없더라도 그 eventId를 기록한다.
토큰은 기록하지 않는다. 요청 키를 새로 만들거나 조건/revision을 갱신해 자동 재전송하지 않는다.
done 수신 뒤에는 결과와 확인 목표를 기록해, 새로고침 후에도 저장된 결과 GET만 이어갈 수 있게 한다.
저장소를 사용할 수 없으면 지속 복구를 보장한다고 표시하지 않으며, 최초 POST 전 이를 알리고 안전한 복구 경로를 먼저 확보한다.

단, **현재의 같은 키 POST 재시도는 조회 전용이 아니다.**
`planning_service._open_turn`은 실패 시 키를 해제하며, `core/idempotency.py`는 5분이 지난 PROCESSING을 새 실행이 인계할 수 있게 한다.
턴 저장과 멱등 응답 저장도 별도 커밋이다. 따라서 현재 `stream.ts`의 자동 POST 재요청만으로 ‘모델을 다시 부르지 않는 결과 확인’을 보장할 수 없다.
현재 공개 API에는 요청별 읽기 전용 결과 조회도 없다.

BE 별도 보완안은 요청 키에 연결된 **조회 전용 결과 계약**이다. 경로는 BE 설계에서 확정한다.
사용자·동아리·행사·원래 요청 경로에 대한 권한을 검사하고 처리 중/저장 완료/확정 실패/확인 불가를 구분한다.
완료에는 원래 done 결과와 저장 revision 또는 생성 식별자를 제공한다.
실패·확인 불가를 조회했다고 키를 풀거나 모델을 다시 실행하지 않아야 한다.
저장 커밋 뒤 응답 기록만 유실된 경우와 장시간 처리 중 상태의 판정도 이 BE 작업에서 다룬다.

- 해당 계약 전에는 연결 단절을 ‘결과 확인 필요’로 남기고 새로운 생성·전송을 잠근다. 현재 계획 GET만으로 이번 요청 성공을 확정하지 않는다.
- 계약 연결 후의 **처리 결과 다시 확인**은 읽기 전용 조회다. 처리 중이면 실제 상태에 따라 대기하고, 완료이면 §4, 확정 실패이면 §3, 확인 불가이면 안내를 유지한다.
- 로그아웃/다른 소속은 원래 범위에 접근하지 않는다. 만료되거나 읽을 수 없는 기록은 새 생성 허가로 해석하지 않는다. 미해결 기록을 단순 시간 초과로 지우고 잠금을 풀지 않는다.
- 완료/확정 실패를 처리한 뒤 본문 등 임시 자료를 정리한다. 다른 탭/기기의 전체 진행 복원과 생성 중 대화 읽기는 #327 이후 범위다.

**BE 보완 전 FE의 불명 상태 표시는 구현할 수 있지만, 안전한 결과 확인까지 완료했다고 선언하거나 공개하지 않는다.**
브라우저 탭 기록을 삭제하거나 다른 기기로 이동한 상황까지 FE 잠금으로 보장하지 않는다.

## 10. 사용자 확인

확인할 제안은 **위 상태·문구·전환과 최소 안전성 범위**다.
기존 P2와 제품 디자인은 그대로 유지한다.
