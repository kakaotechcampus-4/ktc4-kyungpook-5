# BE 스키마 검토 요청 (FE)

FE 명세를 쓰다 보니 현재 스키마로 못 그리는 화면이 나왔습니다.
**전부 FE 판단이고 합의된 게 아닙니다.** 반려하셔도 되고, 그러면 FE에서 화면을 바꾸겠습니다.

## 변경 요청

| # | 대상 | 변경 | 왜 | 없으면 |
| --- | --- | --- | --- | --- |
| 1 | `steps` | `phase` 추가 (IntEnum: PREPARATION / RECRUITING / EXECUTION) | P2에서 7단계를 3묶음으로 나눠 표시. `step_order`만으로는 어느 묶음인지 알 수 없고, 드래그로 순서 바꾸면 추론도 깨짐 | **P2 계획 화면 못 그림** |
| 2 | `events` | `plan_meta` (JSONB) 추가 | `plan:generate`가 만드는 경고("입금 마감과 리허설 사이 8일 공백")와 제외 단계 목록. 저장 안 하면 새로고침 시 소멸 | **P2 우측 패널 소멸** |
| 3 | `events` | **`title`을 `nullable=False`로 변경** | 임시 저장 목록에서 계획을 구분하려면 제목이 있어야 함. `POST /events`(대화 생성) 시점에 확정하고, 사용자가 안 적으면 서버가 기본값 부여 | 임시 저장 목록 구분 불가 |
| 4 | `actions` | `deny_reason` (Text, nullable) 추가 | L2 "처리된 승인"에서 거절 사유 표시. 임원 여러 명이 쓰므로 왜 거절됐는지 남아야 함 | 거절 사유 표시 불가 |
| 5 | `actions` | `payload` (JSONB) 추가 | `CONFIRMATION`은 예/아니오가 아니라 선택지가 건마다 다름("봄 MT에 넣기 / 공동 회계로"). 선택지와 처리 결과를 담을 곳 없음 | L2 확인 요청 처리 불가 |
| 6 | `events` | `end_date` (Date, nullable) 추가 | 행사 대부분 1박 2일. 헤더에 "3/21–3/22" 표시 | 종료일 표시 불가 |
| 7 | `events` | `event_type` (IntEnum), `location` (String) 추가 | 행사 유형은 AI가 단계를 배열하는 근거. 저장 안 하면 계획 열 때마다 대화 재해석. 장소는 L2 헤더 표시 | 계획 재현 불가 |

## 확인 요청

**1. 거절 시 `approved_by` / `approved_at`을 쓰나요?**
필드명이 `approved_*`라 거절에 쓰기 어색합니다. 그대로 쓰기로 하면 FE는 "처리자 / 처리 시각"으로 읽겠습니다. 아니면 `resolved_by` / `resolved_at`으로 바꾸는 것도 방법입니다.

**2. `Event.title`과 `Conversation.title`의 관계**
둘 다 있는데 용도가 갈립니다. FE는 화면 어디서도 `Conversation.title`을 쓰지 않습니다. 계획 화면 제목은 전부 `Event.title` 기준으로 잡았습니다.

**3. `Record.parse_error` JSONB 내부 형식**
컬럼은 이미 있으니 스키마 변경은 아니고, **형식만 맞추면 됩니다.** R1에서 "왜 못 읽었나"를 문장으로 보여주고 해결 버튼을 띄우려면 아래 정도가 필요합니다.

```json
{
  "reason": "COLUMN_MISMATCH",
  "detail": "열 이름이 표준과 달라 어떤 값이 금액인지 찾지 못했습니다.",
  "expectedColumns": ["날짜", "적요", "입금", "출금"],
  "actualColumns": ["일자", "내용", "금액", "구분"],
  "suggestions": [{ "action": "MAP_COLUMNS", "label": "열 직접 맞추기" }]
}
```

**4. 실제 장부는 입금·출금이 한 열에 섞여 있습니다.**
`금액` 한 열에 숫자가 있고 `구분` 열로 입출금이 나뉘는 형태가 흔합니다. 열 이름 매핑만으로는 안 풀리고 부호 판별 규칙이 별도로 필요해 보입니다.

## 판단 필요

**MANUAL 단계가 항상 완료로 계산됩니다.** (공유해주신 "구현 시 주의할 것" 1번)
Action이 0개라 `completed(0) == 총수(0)`. L2 진행 상황에서 안 한 단계가 완료로 뜹니다.

- A. `steps.completed_at` 추가 + 완료 엔드포인트
- B. MANUAL 단계에도 체크용 Action 1개 자동 생성 (`ActionType.CHECK` 추가)

FE는 둘 다 가능합니다. B가 "누가 언제 완료했는지"를 `approved_by`에 남겨 추적이 일관됩니다.

## 금액 논의에 같이 올려주세요

**`participants` (행사별 참가 신청) 테이블이 안건에 없는 것 같습니다.**
미납자 = "참가 신청했는데 납부 기록 없는 사람"입니다. `transactions`만 생기고 참가자가 없으면 미납자를 못 뽑습니다. `members`는 동아리 전체 명단이라 이번 행사 참가자와 구분이 안 됩니다.

## FE 대응

🔸 필드는 `null`로 내려온다 가정하고 빈 상태로 그립니다. 응답 구조는 미리 잡아둬서 나중에 값이 채워져도 FE 코드는 안 바뀝니다.

지금 구현 가능: 동아리 기록 전체 / 승인 조회·처리 / 계획 1단계
1·2번 필요: 계획 2단계
금액 확정 후: 행사 목록·상세의 금액 영역

상세 응답 형태는 `운영해_FE_API_명세_초안.md`의 🔸 표시 부분에 있습니다.
