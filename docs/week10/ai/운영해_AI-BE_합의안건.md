## 1. AI가 BE에 올린 항목 (requirements.md의 D-01~D-09)

원문을 쉬운 말로 풀어 쓴 것입니다. 번호는 원문 그대로 씁니다.

| ID | 한 줄 요약 | 정해야 하는 것 |
| --- | --- | --- |
| D-01 | **계획을 만들려면 최소 뭘 알아야 하나** | 행사 유형·날짜·인원·예산 중 몇 개가 있어야 계획 생성 버튼이 눌리는지. "장소 미정"인 채로 확정해도 되는지 |
| D-02 | **어떤 행사를, 어떤 단계로 지원하나** | MT·환영회 등 지원 행사 목록과 기본 단계 구성. 사용자가 단계를 추가·삭제할 수 있는 범위 |
| D-03 | **계획을 언제 저장하고, 다시 열면 어느 대화를 이어받나** | 자동 저장 시점. 한 행사에 대화가 여러 개일 때 복원 대상 |
| D-04 | **올린 파일을 누가 어디까지 처리하나** | 지원 파일 형식, 텍스트 추출·검색 색인 담당, 읽기 실패 시 복구 범위 |
| D-05 | **AI가 제안할 수 있는 행동과 승인 정책** | 지원 행동 종류, 어떤 행동이 승인 대상인지, 중복 제안 판정 기준, 실제 발송·이체까지 하는지 흉내만 내는지 |
| D-06 | **돈 관련 기능의 범위** | 예산안·참가비·수납·환불 중 어디까지 하고, 그 계산과 데이터를 BE가 어떤 형태로 주는지 |
| D-07 | **어떤 변화에 AI가 반응하나** | 참가 취소·입금·일정 변경 중 대응 대상, 그리고 BE가 언제 AI를 호출하는지 |
| D-08 | **실행 상태를 어떻게 보여주나** | 승인 대기 / 실행 대기 / 성공 / 실패 / 확인 불가의 구분, 재시도 방식 |
| D-09 | **운영 중 계획 변경 범위** | 이미 진행된 단계가 있는 상태에서 무엇을 바꿀 수 있고 어떻게 확정하는지 |

## 3. 취합한 회의 안건

위 둘을 합쳐 **결정 단위**로 다시 묶었습니다. 회의에서는 이 순서로 진행합니다.

### A. 연결 방식 — AI와 BE가 어떻게 서로를 부르나

| # | 안건 | 지금 상태 | 결정할 것 | 관련 |
| --- | --- | --- | --- | --- |
| A-1 | **한 프로세스 함수 호출로 간다** | AI README는 "별도 AI 서버 없음"인데, BE README에는 `AI_SERVICE_BASE_URL`과 `infra/agent_client.py`가 남아 있음 | HTTP 호출 흔적을 지우는 작업의 담당과 시점 | `[AI]` migration, `[BE]` README |
| A-2 | **AI가 BE에 열어줄 기능 목록** | `facade.py`·`contracts.py`가 주석만 있는 빈 파일 | 함수 이름, 입력·출력 필드, 오류 형식. 최소 3개: 계획 대화 진행 / 계획 생성 / 기록 질의 | D-01·D-02, `[FE]` messages·plan:generate·records/chat |
| A-3 | **AI가 BE에 요구할 조회·계산 목록** | `ports.py`가 빈 파일 | `event_rules.py`의 어떤 함수를 AI tool로 노출할지. 행사 상태 조회 메서드 | `[BE]` README 규칙 1, D-06 |
| A-4 | **응답 시간과 실패 처리** | 계획 생성이 수십 초. SSE는 이번 범위 밖 | 타임아웃 값, 시간 초과 시 사용자에게 보이는 것, 재시도 시 기존 계획 보존 | D-08, AI-COMMON-02 |
| A-5 | **무엇을 어디에 저장하나** | 행사 원본=BE, AI 실행 체크포인트=AI로 구두 합의만 | 대화(`Conversation`/`Message`) 주인, AI 체크포인트 저장소, `AgentLog` 기록 시점과 필드 | `[AI]` architecture, `[FE]` AgentLog 표기 |
| A-6 | **데이터 표기 규약을 AI도 따른다** | BE·FE는 확정 (enum은 문자열 코드, JSON은 camelCase, 금액은 정수 원, 날짜는 `DATE`/마감은 `TIMESTAMPTZ`) | AI `contracts.py`도 같은 규약을 쓴다는 확인만 | `[BE]` 검토안 §5, `[FE]` 공통 규약 |

### E. 확인만 하고 넘어갈 것

결정이 이미 났고 AI가 알고만 있으면 되는 것들입니다.

- `approved_by`/`approved_at` → **`resolved_by`/`resolved_at`** 으로 개명됨
- `steps.completed` 컬럼 삭제 → `completed_at`·`completed_by`로 판정, 완료 API 신설
- enum은 DB에도 문자열 코드로 저장 (변환 계층 없음)
- 금액은 정수 원 단위만 사용
- RAG 저장소는 **pgvector 확정** (Milvus 아님)
- 경로의 콜론 표기(`:generate`·`:confirm`·`:reorder`)는 팀 합의 대기 — AI 기능에는 영향 없음

## 4. 회의 진행 제안

1. **0장 3건 먼저** — 임베딩 모델, 공개 함수·port 계약, 참가자·입출금 테이블. 상대 팀 작업을 막고 있는 것들입니다.
2. **A장(연결 방식)** — 여기서 결론이 나야 AI가 `facade.py`·`ports.py`에 첫 줄을 씁니다. AI 문서 기준 "합의 전에는 빈 Protocol·가짜 응답을 만들지 않는다"라서 현재 진도가 0입니다.
3. **B·C·D장** — 이번 스프린트에 구현할 것부터. 전부 정할 필요는 없고, **이번 주 안에 코드로 옮길 항목만** 결론을 냅니다.
4. 결론이 안 나는 항목은 **"다음 회의"가 아니라 "누가 언제까지 초안"** 형태로 남깁니다.

각 안건의 결론은 `be/app/ai/docs/requirements.md`의 D-표와 `be/README.md`의 "확인이 필요한 항목"에 반영하고, 관련 Issue의 착수 조건으로 연결합니다.
