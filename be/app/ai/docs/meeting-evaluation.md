# 회의 어시스턴트 측정 기록

판단 모델·음성 인식·지연을 바꿀 때 같은 조건으로 다시 재고, 이전 값과 비교하기 위한 기록이다.
최근 기록을 위에 쌓는다. 결정과 그 이유는 [아키텍처의 회의 어시스턴트](architecture.md#회의-어시스턴트)에 둔다.

## 재는 방법

프롬프트 후보를 찾는 탐색 측정은 레포 밖 별도 폴더에서 한다. 측정에만 쓰는 의존성과 오디오 파일을 레포에 들이지 않기 위해서다.
탐색 측정의 재현 자료(스크립트, 문항, 설정값, 원시 결과 JSON)는 측정마다 관련 이슈에 첨부한다. 2026-10-13은 #111, 2026-10-14는 #114, 2026-10-15는 #117.

모델과 프롬프트를 비교하는 측정은 레포의 평가 문항과 스크립트로 한다. 같은 문항을 같은 입력 글로 다시 재야 하기 때문이다.
판단 전용 모델(Laya)에 필요한 laya·torch는 BE 의존성에 넣지 않고 잴 때만 `uv run --with`로 붙인다.
이 측정도 원시 결과 JSON을 관련 이슈에 첨부한다. 2026-10-19 학습 전 Laya는 #117, 2026-10-20 평가 세트 기준선은 #115, 다시 판단할 모델은 #117.

- CI에서 돌리지 않는다. luna는 키가 필요하다.
- 공통 조건: 추론 끔(`effort=none`), 재시도 끔(`max_retries=0`), 노트북에서 인터넷을 거쳐 게이트웨이 호출
- 지표: 균형 정확도(조회 필요와 불필요를 각각 맞힌 비율의 평균), 재현율·특이도·정밀도, 오개입률(조회 아닌 발화 100개당 조회로 판단한 수), 지연 p50·p95, 판단 1,000회 비용. 평가 세트는 오답을 묶음별·태그별로도 센다

아래는 탐색 측정에 쓴 측정 폴더의 스크립트다. 레포에는 없고 재현 자료로 이슈에 첨부했다.

| 스크립트 (측정 폴더) | 재는 것 |
| --- | --- |
| `check_gateway.py` | 게이트웨이 연결, 추론 깊이·구조화 출력이 먹는지 |
| `bench_judge.py` | 판단의 정확도와 지연. 모델 비교, 출력 형식 비교 |
| `exp_ab.py` | 판단 지연을 줄이는 변형들. 발화마다 번갈아 호출한다 |
| `exp_floor.py` | 몇 토큰만 주고받는 최소 호출의 지연 |
| `make_audio.py` | 회의 대본을 macOS TTS로 읽혀 측정용 오디오를 만든다 |
| `probe_whisper.py` | Whisper 지연과 옵션 동작 |
| `bench_pipeline.py` | 오디오 → Whisper → 판단 전체 |
| `exp_query.py` | 검색어 품질. 프롬프트와 앞 발화 수를 바꿔 가며 발화마다 번갈아 호출한다 |

레포에서 재는 판단은 [회의 판단 평가 문항](../tests/fixtures/eval/README.md#회의-판단-평가-문항) 110개(`tests/fixtures/eval/meeting_judge.jsonl`)를 쓴다. 측정 폴더의 세 묶음을 옮긴 것이다.

```bash
cd be && uv run python app/ai/scripts/check_meeting_judge.py [--set query] [--json 결과.json]
cd be && uv run --with laya==0.4.7 python app/ai/scripts/check_laya_judge.py [--model 체크포인트] [--threads 2] [--threshold 0.5] [--json 결과.json]
```

프롬프트·모델 비교와 판단 전용 모델 교체 결정은 [회의 판단 평가 세트](../tests/fixtures/eval/README.md#회의-판단-평가-세트) 350건(`meeting_judge_set.jsonl`, #115·#117)으로 한다.
아래 세 판단 스크립트 모두 `--eval-set`을 주면 이 세트의 개발용을 재고, `--holdout`을 더하면 홀드아웃도 재서 따로 낸다. 홀드아웃은 기록에 남길 측정에서만 켠다.

- `check_meeting_judge.py`: luna 판단을 레포 코드 경로(`features/meeting`)로 잰다. 호출마다 토큰(입력·캐시·출력)을 세서 아래 단가로 판단 1,000회 비용을 낸다
- `check_laya_judge.py`: 같은 입력 글(`build_judge_input`)과 판단 질문(`questions.py`)으로 Laya를 CPU에서 돌린다. P(true)가 임계값(`--threshold`, 기본 0.5) 이상이면 조회로 보고, AUROC(기준값과 관계없이 조회할 발화에 더 높은 확률을 줬는지)와 지연·최대 메모리를 낸다.
  임계값 후보(`--sweep`, 기본 0.05~0.95를 0.05 간격)마다 재현율·놓침·오개입률·둘 다 허용에서 조회한 수를 표로 낸다. 같은 확률로 다시 셀 뿐이라 모델을 다시 돌리지 않는다.
  이 표는 홀드아웃을 빼고 만든다. 임계값은 개발용에서 고르고 홀드아웃은 고른 값을 확인하는 데만 쓴다. 둘 다 허용인 문항은 AUROC에도 넣지 않는다
- `check_jev_judge.py`: 학습하지 않고 API로 부르는 판단 전용 모델 Jev(#245)를 Laya와 같은 입력 글과 판단 질문으로 잰다. 임계값 표는 기본 0.01~0.99를 0.01 간격으로 낸다. Jev는 같은 입력에도 확률이 조금씩 달라서, 문항 전체를 `--repeat`번(기본 3) 보내고 판단은 첫 회 값으로 한다. 회차마다 정한 임계값에서 조회·아님이 뒤집힌 문항도 낸다. 모델은 버전을 고정해(`typesafe/jev-1.14`) 부르고, 키는 `JEV_BASE_URL`·`JEV_API_KEY`로 받는다
- `rejudge_meeting_decisions.py`: 운영 회의의 판단 기록을 Jev로 다시 판단해 그때 luna의 판단과 견준다. 판단 기록에 남은 요청(`judge_input`, #241)으로 luna가 본 것과 같은 입력 글을 다시 만든다. 정답이 없으므로 일치 수와 갈린 발화 목록만 내고, 갈린 발화는 사람이 정답을 붙일 후보다. 결과에 실제 회의 발화가 들어 있어 레포와 이슈에 올리지 않는다
- `check_meeting_query.py`: Laya가 조회로 본 발화에 남는 검색어만 받는 호출(`meeting-query-v1`)과 지금의 판단 + 검색어 호출을 평가 세트 개발용의 조회 필요 발화로 번갈아 불러 지연·토큰·검색어를 견준다
- `check_meeting_path.py`: 지금 경로(luna 판단 + 검색어)와 Jev 경로(Jev 판단 → 조회로 보면 검색어만 받는 luna 호출)를 평가 세트 개발용 전체로 번갈아 불러, 발화부터 검색어를 받기까지의 시간을 정답 묶음별로 견준다(#245). Jev 경로는 확률이 임계값(`--threshold`, 기본 0.35) 이상일 때만 검색어 호출을 붙인다
- 단가 (100만 토큰당, ML API 모델 페이지 기준): `gpt-5.6-luna` 입력 ₩283, 캐시된 입력 ₩28, 출력 ₩1,701 (2026-10-19) / `gpt-6-luna` ₩141, ₩14, ₩708 / `claude-haiku-5-5` ₩152, ₩15, ₩761 (2026-10-20) / `typesafe/jev-1.14` 입력 $0.042 (2026-11-03, 입력 토큰만 센다)
- 다른 모델은 그 모델의 `AI_API_BASE_URL`·`AI_API_KEY`·`AI_MODEL`을 담은 파일을 `--env-file`로 준다. 게이트웨이는 모델마다 배포 주소가 다르다.
  회의 뒤 다시 판단할 모델처럼 실시간이 아닌 판단은 `--judge-timeout 60`으로 제한 시간을 늘려, 늦은 응답이 오류로 빠지지 않게 한다
- **이 110개는 Laya 학습 데이터에 넣지 않는다.** 학습 전후를 같은 문항으로 비교하기 위해서다

판단 뒤의 기록 검색과 근거 판단은 기록 검색 평가 세트로 잰다. `scripts/make_meeting_queries.py`가 평가 질문을 회의 판단에 넣어 검색어를 만들고, `scripts/eval_retrieval.py --queries`가 그 검색어로 잰다.

평가 문항을 바꾸면 이전 기록과 직접 비교할 수 없으므로 기록에 적는다.

### 걸린 시간

전사가 화면에 온 뒤 판단 결과가 오기까지다(클라이언트에서 잼).

| | 바꾼 뒤 (Jev) p50 / p95 | 바꾸기 전 회차 p50 / p95 | 바꾸기 전 회차의 luna 판단만 p50 / p95 |
| --- | --- | --- | --- |
| 조회 아닌 말 | **0.51 / 0.65초** (135건) | 2.44 / 6.29초 (134건) | 1.87 / 3.16초 |
| 조회한 말 (기록 검색까지) | 5.70 / 6.94초 (9건) | 5.61 / 6.74초 (10건) | |

- Jev 판단 한 번은 p50 0.49초, p95 0.63초였다
- **바꾸기 전 회차의 조회 아닌 말 p95 6.29초는 대부분 할 일 후보 추출을 기다린 시간이다.** 그 회차는 #249 전이라 판단 결과가 추출이 끝나야 나갔다. luna 판단만의 시간(운영 DB의 `judge_ms`, [#240 기록](#2026-11-03--발화마다-따로-실행한-뒤-운영-회의-지연-240))은 p50 1.87초, p95 3.16초다. 그래서 왼쪽 두 칸의 차이에는 #249와 Jev가 함께 들어 있고, Jev만의 차이는 첫 칸과 셋째 칸(p50 약 1.4초, p95 약 2.5초)으로 본다. 같은 측정에서 번갈아 잰 값(조회 아닌 말 1.97 / 3.10초 → 0.52 / 2.61초)과 같은 방향이다
- 조회한 말은 거의 같다. 검색어 호출이 하나 더 붙어도 기록 검색·답 작성 시간이 더 크다
- 화면의 "최근 발화를 처리하고 있어요" 표시는 판단 결과가 아니라 작업(job)이 끝날 때까지 남고, 작업은 할 일 후보 추출까지 끝나야 끝난다(FE 코드로 확인). 그래서 조회 아닌 말의 판단이 빨라져도 이 표시가 사라지는 시점은 추출이 정한다

## 2026-11-03 · 판단 결과를 추출보다 먼저 보낸 뒤 지연 (#249)

[#240 기록](#2026-11-03--발화마다-따로-실행한-뒤-운영-회의-지연-240)에서 판단 결과(`judgment`)가 할 일 후보 추출이 끝나기를 기다려 늦게 가는 것을 봤다. 판단이 끝나면 판단 기록을 저장해 바로 보내고, 추출은 같은 처리 안에서 뒤에 마무리하도록 바꿨다(#249). 바꾸기 전과 후를 로컬에서 같은 음성으로 견줬다.

- 코드: 바꾸기 전은 develop `9d62154`, 바꾼 뒤는 같은 develop에 #249의 `context_service.py`·`meeting_service.py`를 얹은 것(`b620f27`). 두 회차는 이 두 파일만 다르다
- 실행·음성: [#240의 로컬 비교](#바꾸기-전과-후-로컬에서-같은-음성-두-번)와 같다. 노트북 BE(uvicorn)와 Docker DB, luna는 운영과 같은 게이트웨이, #245의 9.2분 WAV를 실제 시간 속도로 들려줌
- 순서: 바꾸기 전(`mtg_j8SX6vEZCBLD6SPIwYeTr`) → 바꾼 뒤(`mtg_exFdS3upq97V6Kvb9zy0u`), 연달아 한 번씩. 둘 다 전사 144건
- 판단 뒤 남은 시간 = (처리 시작 `stage` → `judgment` 도착) − 판단(`judge_ms`) − 기록 검색·답 작성(`tool_calls` 합). 앞의 것은 받는 쪽 시각, 뒤의 둘은 판단 기록 값이다. `judgment`가 추출을 기다렸으면 커진다
- 추출 나머지 = 작업 전체(`agent_jobs.finished_at − started_at`) − 판단 − 기록 검색·답 작성. 추출이 판단·검색보다 늦게 끝난 만큼이다. 바꾼 뒤에도 작업은 추출까지 끝나야 끝나므로 이 값은 줄지 않아야 한다

- luna 판단 시간은 두 회차가 비슷하다. 줄어든 것은 판단 뒤에 기다린 시간이다
- 추출 나머지는 두 회차가 비슷하다. 추출은 여전히 판단보다 늦게 끝나지만(p95 약 4.7~5.4초 더), 이제 판단 결과를 막지 않는다. 추출을 빠르게 하는 일은 따로 다룬다(#250)
- 바꾸기 전 회차에는 판단이 10초 제한 시간을 넘긴 발화가 3개 있었다(발화 129·132·133, `AITimeoutError`). 그래서 그 회의는 `FAILED`로 끝났다. 판단 실패는 바꾼 뒤에도 회의 실패로 세므로 이번 변경과 관계없고, 위 표에서는 뺐다. 그 무렵 게이트웨이가 느렸던 것으로 보인다. 바꾼 뒤 회차는 오류 0, `COMPLETED`, 판단 기록 144건 모두 `SUCCEEDED`다

### 한계

- 회차마다 한 번씩, 바꾸기 전을 먼저 쟀다. 게이트웨이 지연이 회차마다 달라 "발화 끝 → 판단" 값에는 그 차이가 섞인다. 판단 뒤 남은 시간은 판단 시간을 빼고 본 값이라 게이트웨이 차이의 영향이 작다
- 로컬 DB에는 동아리 기록이 없어 조회한 말은 "기록에 없음"으로 끝난다. 기록 검색·답 작성이 운영(p50 2.7초)보다 짧아(0.6~0.7초), 바꾸기 전에도 조회한 말이 추출을 기다린 경우가 운영보다 많았을 수 있다
- 두 회차 모두 추출이 실패한 발화는 없었다. 추출만 실패하면 회의를 실패로 세지 않는 동작은 테스트로만 확인했다
- 화면(FE)에서 답 카드가 뜨는 시각은 재지 않았다. 받는 쪽 시각은 재생 스크립트가 메시지를 받은 시각이다

## 2026-11-03 · 지금 판단 경로와 Jev 경로의 지연을 번갈아 잼 (#245)

판단을 Jev로 바꾸면 발화 하나를 처리하는 호출이 바뀐다. 다른 날 잰 값을 더하면(Jev p95 0.69초 + 검색어만 받는 호출 p95 2.72초) 게이트웨이 지연이 날마다 달라 지금 판단(p95 2.96초)과 견줄 수 없어서, 같은 측정에서 발화마다 번갈아 쟀다.

```text
지금   발화 → luna (판단 + 검색어)
Jev    발화 → Jev (판단) ─┬ 확률 0.35 미만 → 끝
                           └ 0.35 이상     → luna (검색어만, meeting-query-v1)
```

- 문항: 평가 세트 개발용 151건(조회 필요 31, 조회 아님 110, 둘 다 허용 10)을 3번 돌아 두 경로 453쌍. 오류 0
- 발화마다 두 경로를 이어서 부르고, 먼저 부르는 쪽을 발화·회차마다 바꿨다. 세기 전에 두 경로를 2번씩 미리 불렀다. 시험에서 첫 호출이 연결을 맺느라 10초를 넘겼기 때문이다
- 경로 시간은 첫 호출 시작부터 마지막 호출이 끝날 때까지다. 그 뒤의 기록 검색은 두 경로가 같아 재지 않았다
- luna `gpt-5.6-luna`(`meeting-judge-v6`, `meeting-query-v1`, 추론 끔), Jev `typesafe/jev-1.14`(`meeting-questions-v1`, 임계값 0.35). 노트북에서 인터넷을 거쳐 잼. `check_meeting_path.py --repeat 3`, 커밋 `b2461da`

### 결과: 조회할 말은 p50이 0.5초 늦고 p95는 같다. 조회 아닌 말은 1.4초 빠르다

## 2026-11-03 · 운영 경로로 들려준 합성 회의를 Jev로 다시 판단 (#245)

- 판단이 발화 순서와 다르게 도착한 발화가 9개 있었다. 화면은 `segmentId`로 맞춘다(#119).
- "발화 끝"은 VAD가 자른 시점이다. VAD는 0.6초 조용해야 끝으로 보므로 사람이 말을 멈춘 때부터는 약 0.6초가 더 걸린다.

### AI 처리 안의 구간 (판단 기록, 밀리초)

| | n | 판단 p50 / p95 | 검색·답 작성 p50 / p95 | 처리 전체 p50 / p95 | 나머지 p50 / p95 |
| --- | --- | --- | --- | --- | --- |
| 조회 안 함 (`NONE`) | 134 | 1868 / 3163 | 0 / 0 | 2393 / 5893 | 221 / **4057** |
| 조회함 (`RAG`) | 10 | 2190 / 3487 | 2712 / 3817 | 5595 / 6490 | 10 / 955 |

나머지 = 처리 전체 − 판단 − 검색·답 작성. 처리 하나는 판단과 할 일 후보 추출을 동시에 부르고 둘 다 끝나야 결과를 보내므로, 나머지가 크면 추출이 늦게 끝난 것이다(추출 시간은 따로 저장하지 않는다).

| 발화 | 판단 | 처리 전체 |
| --- | --- | --- |
| "응." | 1897 | 7337 |
| "전철 타고 짐은 마트 픽업 차에 싣자" | 1657 | 7222 |
| "방 잡으려면 인원 파악 빨라야 하니까" | 1773 | 7113 |

- 조회하지 않는 말에서 느린 쪽은 판단이 아니라 **할 일 후보 추출**이다. 처리 시간 상위 10개 중 7개가 판단 1.6~2.4초, 처리 전체 6.0~7.3초였다.
- 조회한 말은 대부분 판단 → 기록 검색이 끝나기를 기다렸다(나머지 p50 0.01초). p95 0.96초는 추출 때문에 답이 그만큼 늦게 간 경우다.

운영에는 바꾸기 전 코드가 없으므로, 로컬에서 같은 WAV를 두 번 들려줘 견줬다. 두 회차는 `audio_stream_service.py` 한 파일만 다르다.

## 2026-11-03 · 배포 서버에서 잰 Laya 하나의 메모리와 지연 (#117)

1단계 교체 기준의 조회 경로 지연은 배포 서버에서 재기로 했는데 한 번도 재지 않았다. 판단 정확도와 관계없는 값이라, 홀드아웃을 통과하지 못한 1,500건 시드 2로 운영 EC2에서 쟀다.

- 방법: 운영 컨테이너와 따로 일회성 컨테이너(`python:3.12-slim`, `--memory 2300m --cpus 1`)에 CPU 전용 torch 2.15.0과 laya 0.4.7을 설치하고, 개발용 151발화를 Laya 입력 글로 미리 만든 파일로 판단했다(스레드 1, 3회). 메모리가 넘치면 이 컨테이너만 종료되게 했다
- 결과를 보기 전에 정한 해석: 최대 메모리 1.8GB 이하면 상시로 올리는 것을 검토, 1.8~2.3GB면 스왑부터, 넘치면 같은 서버는 어렵다. 판단 p95는 약 0.4초 안이어야 조회 경로가 지금보다 0.2초 넘게 늘지 않는다(검색어만 만드는 호출 p95 2.72초, luna v6 판단 p95 2.96초)

- 같은 입력에 같은 확률이 나오므로, Laya의 판단은 서버에서 돌리지 않아도 저장된 판단 입력(`judge_input`, #241)으로 나중에 다시 계산할 수 있다

## 2026-11-03 · 1,500건으로 한 Laya 학습 (#117)

[6차 250건](#2026-11-03--학습-대본-6차-250건-117)을 더한 1,500건을 1,250건 label smoothing 0.1과 같은 설정으로 학습해 견줬다([7단계](architecture.md#7-학습측정보관) 실행 22~27). 바뀐 것은 데이터 하나다.

- 판정 (학습 전에 정함): "기준에 닿는 시드"는 임계값 0.01~0.99(0.01 간격) 중 하나라도 luna가 잡은 조회를 하나도 놓치지 않고 오개입률이 16 이하가 되는 시드다. 나아짐은 기준에 닿는 시드 4개 이상, 그중 3개 이상은 구간 폭 2칸 이상, AUROC 평균 0.955 이상이다
- 학습: 데스크톱, laya 0.4.7, `laya-multilingual`부터, `--label-smoothing 0.1`, 4에포크, 시드 0~5. 학습 1,286줄, 보정 142줄, 갱신 84번
- 측정: 노트북 CPU 2스레드, `check_laya_judge.py --model <s0> … <s5> --eval-set --luna <luna 결과> --sweep 0.01~0.99 --repeat 1`, 커밋 `643c250`. 개발용 141건(조회 31, luna가 잡은 조회 29, 아님 110). luna 결과는 1,250건과 같은 10-21 측정(`meeting-judge-v5`)이다
- 체크포인트는 `t1500-ls01-s0`~`s5`다. 파일을 하나씩 지정해 받아 크기와 해시를 확인했다

### 판정: 나아짐

| | 1,250건 label smoothing (시드 0~5) | **1,500건 label smoothing (시드 0~5)** |
| --- | --- | --- |
| 기준에 닿는 시드 (구간) | 2개 (시드 0: 0.08~0.09, 시드 4: 0.09) | **4개** (시드 0: 0.10~0.12, 시드 1: 0.11, 시드 2: 0.12~0.15, 시드 5: 0.12~0.15) |
| 그중 구간 폭 2칸 이상 | 1개 | **3개** |
| AUROC | 0.989 / 0.970 / 0.971 / 0.960 / 0.983 / 0.970 | 0.981 / 0.992 / 0.987 / 0.978 / 0.972 / 0.979 |
| AUROC 평균 (범위) | 0.974 (0.960~0.989) | **0.982 (0.972~0.992)** |
| 오개입률 16 이하에서 luna가 잡은 조회를 가장 적게 놓친 수 | 0 / 1 / 2 / 1 / 0 / 2 | 0 / 0 / 0 / 1 / 1 / 0 |
| 임계값 0.5의 luna가 잡았는데 놓침 | 5 / 4 / 4 / 10 / 6 / 4 | 2 / 4 / 5 / 4 / 4 / 3 |
| 확률 보정 온도 | 1.06~1.16 | 1.25~1.34 |

- 미리 정한 세 조건을 모두 채워 판정은 나아짐이다. 데이터를 1,250건에서 1,500건으로 늘린 것만으로 기준에 닿는 시드가 2개에서 4개가 됐고, AUROC의 가장 낮은 시드도 0.960에서 0.972로 올랐다
- 10-28 표의 "가장 적게 놓친 수"(1 / 1 / 2 / 1 / 1 / 2)는 0.05 간격으로 센 값이다. 위 표는 두 실행 모두 0.01 간격으로 다시 셌다

### 어떤 말이 나아졌나

| 발화 | 1,250건 시드 0~5 | 1,500건 시드 0~5 |
| --- | --- | --- |
| 아 재작년 말고 작년 거요 작년 버스비 (앞 질문의 대상을 고친 말) | 0.09 / 0.08 / 0.10 / 0.07 / 0.10 / 0.07 | 0.83 / 0.22 / 0.15 / 0.10 / 0.09 / 0.28 |
| 근데 작년 정산하고 남은 돈 동아리 통장으로 들어갔나요? | 0.30 / 0.10 / 0.11 / 0.15 / 0.14 / 0.38 | 0.15 / 0.58 / 0.24 / 0.31 / 0.20 / 0.80 |
| 회측에 MT 못 가면 환불 몇 프로까지 해주는 거 있지 않나? | 0.25 / 0.11 / 0.09 / 0.27 / 0.14 / 0.07 | 0.61 / 0.34 / 0.19 / 0.19 / 0.12 / 0.42 |
| 선거 공고는 언제까지 올려야 돼요 회칙에 정해져 있죠 | 0.37 / 0.13 / 0.08 / 0.14 / 0.09 / 0.38 | 0.13 / 0.12 / 0.16 / 0.13 / 0.11 / 0.15 |

- 앞 질문의 대상을 고친 말은 여섯 시드가 모두 0.1 안팎으로 놓치던 말인데, 세 시드가 0.15 넘게 봤다. 6차에서 이 꼴을 12줄 더했다. 다만 이 유형은 개발용에서 놓친다는 것을 알고 채운 유형이라, 이 차이에는 개발용에 맞춘 몫이 섞여 있을 수 있다
- 회칙에 정한 기한을 묻는 말은 6차에서 늘리지 않았고, 여섯 시드 모두 0.11~0.16으로 여전히 낮다
- 1,250건에서 시드 3만 0.12~0.15로 크게 놓치던 말("작년엔 어디였더라 청평이었나" 등 4개)은 1,500건에서 모든 시드가 0.4 넘게 봤다(넷 중 셋은 0.5 넘게)

### 임계값이 좁은 범위에 몰려 있다

| 임계값 | 0.09 | 0.10 | 0.11 | **0.12** | 0.13 | 0.15 |
| --- | --- | --- | --- | --- | --- | --- |
| 기준에 닿는 시드 (luna 놓침 0, 오개입률 16 이하) | 0 | 1 | 2 | **3** | 2 | 2 |
| 시드 0~5 오개입률 범위 | 31.8~83.6 | 12.7~37.3 | 8.2~16.4 | 7.3~12.7 | 6.4~10.9 | 5.5~9.1 |

- label smoothing으로 조회 아닌 말의 확률이 0.08~0.10에 모여 있다(110건의 여섯 시드 평균 중앙값 0.09). 그래서 임계값을 0.10에서 0.09로 0.01만 내려도 오개입률이 두세 배가 되고, 0.12에서 0.13으로 올리면 놓침이 생기는 시드가 나온다
- 하나의 임계값에서 기준에 닿는 시드는 0.12에서 가장 많은 3개(시드 0·2·5)다. 같은 임계값에서 시드 1·3은 1건, 시드 4는 3건을 놓친다
- 홀드아웃에서는 이 좁은 범위가 그대로 옮겨 가지 않을 수 있다. 홀드아웃에서 무엇을 잴지는 재기 전에 1단계에 적는다

| 여섯 모델 함께 올림 (노트북 CPU 2스레드, 개발용 151발화) | 값 |
| --- | --- |
| 발화 하나 판단 (여섯 모델 차례로) | p50 504ms, p95 749ms |
| 최대 메모리 | 3.52GB |

여섯 모델을 함께 쓰려는 것이 아니라 한 번에 재려고 함께 올렸다.

## 2026-11-03 · 학습 대본 6차 250건 (#117)

### 다음: 1,500건 학습

같은 설정(`--label-smoothing 0.1`, 4에포크)으로 시드 0~5를 학습해 1,250건 label smoothing 0.1과 견준다([7단계](architecture.md#7-학습측정보관) 실행 22~27). 판정은 학습 전에 정했다.

- 기준에 닿는 시드: 임계값 0.01~0.99 중 하나라도 luna가 잡은 조회 놓침 0, 오개입률 16 이하. 기준에 닿는 임계값 구간의 폭(칸 수)도 함께 센다. 1,250건 label smoothing은 2개(시드 0은 2칸, 시드 4는 1칸), AUROC 평균 0.974

## 2026-10-27 · 1,250건으로 한 Laya 학습과 세 시드 평균 (#117)

1~4차(라벨을 고친 파일)에 5차를 더한 1,250건으로 학습했다([7단계](architecture.md#7-학습측정보관) 실행 10~12). 설정은 고친 1,000건 4에포크와 같고 데이터만 다르다.

- 학습: 데스크톱, laya 0.4.7, `laya-multilingual`부터, 4에포크, 시드 0·1·2. 학습 1,191줄 중 1,072줄로 학습하고 119줄은 확률 보정에 썼다. 갱신 68번. 세 시드 모두 보정 온도가 상한(5.0)에 걸렸다
- 측정: 노트북 CPU 2스레드, `check_laya_judge.py --eval-set --repeat 1`, 커밋 `8a71145`. 개발용 141건. 홀드아웃은 보지 않았다
- 체크포인트는 `t1250-s0`~`s2`다. 파일을 하나씩 지정해 받아 크기와 해시를 확인했다

### 회차 비교 (세 숫자)

| 숫자 | 1,000건 (고친 파일) | **1,250건** |
| --- | --- | --- |
| AUROC | 0.962 / 0.975 / 0.962 | **0.989 / 0.971 / 0.979** |
| 오개입률 16 이하에서 가장 적은 놓침 | 4 / 4 / 3 | **2 / 5 / 3** |
| 놓침 2건 이하일 때 오개입률 | 닿지 못함 ×3 | **6.4** / 닿지 못함 / 닿지 못함 |
| 임계값 0.5의 놓침 / 오개입률 | 6·4·6 / 3.6·3.6·5.5 | 6·9·7 / 2.7·1.8·3.6 |

- AUROC는 평균이 0.966에서 0.980으로 올랐다(시드 1만 0.975 → 0.971)
- 시드 0은 임계값 0.05에서 놓침 2건·오개입률 6.4로 개발용 기준에 닿았다. 시드 1·2는 0.05에서도 5건·3건을 놓친다
- **앞 질문의 대상을 고친 말("아 재작년 말고 작년 거요 작년 버스비")은 여전히 놓친다.** 세 시드가 0.09 / 0.01 / 0.32를 줬다(1,000건은 0.01 ×3). 5차에서 10줄을 채웠지만 이 발화를 잡을 만큼은 아니었다
- 1,000건에서 잡던 "회칙에 졸업생도 회비 내는 거 있었나요 아 그건 아닌가"를 시드 1·2가 놓쳤다(0.23, 0.11)

### 세 시드의 확률을 평균하면

시드마다 같은 발화에 정반대 확률을 주는 일이 계속돼, 학습을 더 하지 않고 세 시드의 조회 확률을 평균해 봤다.

| | AUROC | 오개입률 16 이하에서 가장 적은 놓침 | 놓침 2건 이하일 때 오개입률 |
| --- | --- | --- | --- |
| 1,000건 (고친 파일) 세 시드 평균 | 0.970 | 2 | 9.1 (임계값 0.1) |
| **1,250건 세 시드 평균** | **0.983** | **2** | **7.3** (임계값 0.1) |
| luna (10-21, 개발용) | — | 놓침 2, 오개입률 8.2 | |

- 1,250건 평균은 임계값 0.1에서 놓침 2건, 오탐 8건(110건 중)이다. 놓친 2건("여기 두 번째 데가 작년에 했던 데 아니에요?", "아 그건 장부 봐야 알아.")은 luna도 놓쳤다. **개발용에서는 luna가 잡은 조회를 하나도 놓치지 않고 오개입률 16 이하**라 교체 기준에 닿는다
- 다만 이 결과는 개발용에서 평균이라는 방법과 임계값 0.1을 고른 것이다. 홀드아웃으로 확인해야 한다
- 1단계의 "시드를 바꿔 세 번 학습해 셋 다 기준을 넘음"은 모델 하나를 기준으로 쓴 조건이다. 세 모델 평균을 쓰면 이 조건을 어떻게 읽을지 다시 정해야 한다

| 세 모델 함께 올림 (노트북 CPU 2스레드, 개발용 151발화) | 값 |
| --- | --- |
| 발화 하나 판단 (세 모델 차례로) | p50 243ms, p95 274ms (한 모델은 약 80 / 90ms) |
| 최대 메모리 | 2.16GB (한 모델은 1.6~2.1GB, 올리기 전 0.26GB) |

- 지연 기준에 대어 보면 Laya 세 모델 p95 0.27초 + 검색어만 만드는 호출 p95 2.72초 = 2.99초로, 같은 날(10-20) 잰 지금 판단 p95 3.55초보다 낮다. 배포 서버(t3.medium, 메모리 4GB)에서는 재지 않았다

### 다음: 다른 시드로 두 번째 평균

홀드아웃으로 바로 가지 않고, 같은 1,250건으로 시드 3·4·5를 학습해 두 번째 평균을 개발용에서 먼저 잰다([7단계](architecture.md#7-학습측정보관) 실행 13~15). 평균이라는 방법과 임계값 0.1을 모두 시드 0~2의 결과를 보고 골랐고, 0.1의 여유가 얇기 때문이다.

| 1,250건 세 시드 평균의 임계값 | 0.05 | **0.1** | 0.2 | 0.3 | 0.5 |
| --- | --- | --- | --- | --- | --- |
| 놓침 (31건 중) | 2 | **2** | 6 | 6 | 7 |
| 오개입률 | 9.1 | **7.3** | 5.5 | 4.5 | 0.9 |

- 0.1은 luna가 잡은 조회를 하나도 놓치지 않는 가장 높은 임계값이다. 0.2로 올리면 조회 4건을 더 놓친다. 이 4건의 평균 확률이 0.1~0.2 사이에 있다
- Laya의 확률은 0.01이나 0.9 쪽으로 몰려 있어서, 0.1을 "조회일 가능성 10%"로 읽을 수는 없다. 조회 아닌 말 110개 중 평균 0.1을 넘은 것은 8개뿐이다. 평균이 0.1을 넘는다는 것은 대개 세 시드 중 하나 이상이 조회 쪽으로 강하게 봤다는 뜻이다. 예: "아 재작년 말고 작년 거요 작년 버스비"는 0.09 / 0.01 / 0.32로, 시드별 0.5로는 셋 다 놓치지만 평균 0.14는 0.1을 넘는다

**통과 조건은 결과를 보기 전에 정했다.** 시드 3~5의 평균을 임계값 0.1 그대로 개발용에서 재서, luna가 잡은 조회를 하나도 놓치지 않고 오개입률이 16 이하이면 통과다. 임계값은 다시 고르지 않는다.

- 통과하면 두 평균(0~2, 3~5)을 홀드아웃에서 한 번 잰다. 1단계의 "시드를 바꿔 세 번 학습해 셋 다 기준을 넘음"은 "다른 시드로 만든 평균 두 개가 모두 기준을 넘음"으로 바꿔 적는다
- 통과하지 못하면 홀드아웃은 재지 않고, 데이터를 더하거나 학습 설정을 바꾸는 쪽을 다시 정한다

### 한계

- 개발용으로만 쟀다. 5차 대본, 평균이라는 방법, 임계값 0.1 모두 이 문항을 보고 정했으므로 이 점수는 실제보다 좋게 나올 수 있다
- 시드를 세 개만 학습했다. 다른 시드 세 개로 평균을 다시 만들면 결과가 얼마나 흔들리는지 재지 않았다
- 측정 결과 JSON은 #117에 첨부한다

## 2026-10-27 · 학습 대본 5차 250건 (#117)

1,000건 모델은 개발용에서도 교체 기준에 닿지 않았고, 놓치는 말 중 "앞 질문의 대상을 고친 말"은 학습 데이터에 2줄뿐이었다([아래 기록](#2026-10-27--라벨-점검-고친-1000건과-에포크-117)).
그래서 요구사항에 적혀 있는데 학습 데이터에 거의 없던 말을 채우는 250건을 더 만들었다. 홀드아웃은 아직 보지 않았다.

- **무엇을 채울지는 요구사항 문구로만 정했다.** 개발용 문항을 보고 고르면 개발용에 맞추는 것이 되므로, 지시서에는 개발용 문장을 넣지 않았다. 지시서 예시 68개는 평가 문장과 겹치지 않는다(`check_spec.py`)

  | 말 (근거) | 1~4차 학습 데이터 | 5차 목표 (회의 10개마다) |
  | --- | --- | --- |
  | 앞 질문의 대상을 고친 말 (AI-MEET-04 "작년 말고 재작년") | 2줄 | 다섯 번 안팎 |
  | 같은 질문을 다시 하는 말 (AI-MEET-04) | 따로 세지 않음 | 두세 번 |
  | 이름을 불러 지난 값·규칙을 묻는 말 (AI-MEET-01 "민수야, 작년 회칙상 환불 기준이 뭐였지?") | 조회 8줄 | 네다섯 번 |
  | 동아리 회칙·규정을 묻는 말 (같은 예시) | | 네다섯 번 |
  | 바깥 기관(구청·대관 장소·업체)의 규칙을 묻는 말. 라벨은 아님 (라벨 기준 3번의 바깥 지식) | | 두세 번 |

- 대본: 행사 준비 회의 20개(t81~t100), 250발화. **모두 Gemini 3.8 Flash(medium)가 썼다.** 표 I(t81~t90)는 처음에 Haiku 5.5가 썼지만 첫 원고(토리 15번, 조회 43개)와 다시 쓴 원고(조회 49개, 토리 16번, 언급만 2개)가 모두 같은 뼈대였고 다시 쓰자 더 나빠져, 검수자 결정으로 Gemini가 다시 썼다. 두 표 모두 첫 원고 뒤 줄만 한 번 고쳤다
- 음성: 절반(130발화)을 ElevenLabs로 읽혀 Whisper로 받아 적었다. 대본과 같은 전사가 75/130, CER 평균 4.9%다

## 2026-10-27 · 라벨 점검, 고친 1,000건과 에포크 (#117)

1,000건 세 시드 모두 확률 보정 온도가 상한에 걸리고 시드 1·2의 놓침이 늘어서([아래 기록](#2026-10-26--1000건으로-한-laya-학습과-라벨을-섞은-대조-117)), 원인 후보 두 가지를 차례로 봤다.
(가) 비슷한 말에 라벨이 서로 다르게 붙었다. (나) 학습을 너무 오래 했다.

### 라벨 점검 (가)

1,000건 세 모델로 학습 파일 955줄을 다시 판단해 라벨과 반대로 확신하는 줄을 찾았다(측정 폴더 `train1000/audit_labels.py`).

- 세 시드 평균이 라벨과 반대 쪽인 줄은 13줄이고 모두 조회 줄이다. 차수별로 1차 7, 2차 4, 3차 2, 4차 0이고, 검수 뒤 기준을 정해 고친 10줄은 하나도 없다. **3·4차에서 정한 기준이 1·2차 라벨과 부딪친 것은 아니다**
- `laya-train`은 줄 수와 고정 시드(20260922)만으로 보정 줄을 고르므로 같은 95줄을 다시 골랐다. 모델이 확률 0.01~0.02를 준 조회 서너 줄이 보정 벌점의 62~75%를 차지했다. **보정 온도가 상한에 걸린 것은 이 몇 줄 때문이다.** 대부분은 잘 맞히고 틀리는 몇 줄을 아주 강하게 틀린다
- 그 줄 중 라벨 기준과 어긋난 6줄을 검수자가 다시 정했다
  - 지난 값 질문에 모른다고 답한 말 3줄("저는 기억 안 나요. 그때 제가 없었어서요.", "그 규정은 연간 회칙 문서 뒤에 있을걸" 등): 아님 → 조회. 같은 모양의 다른 17줄은 이미 조회였다
  - 바깥 기관의 기한을 묻는 말 2줄("구장 예약은 며칠 전에 해야 돼요?", "학술제 신청 마감이 오늘까지인지 아세요? 홈페이지를 아직 못 봐서요."): 조회 → 아님. 동아리 기록이 아니다
  - 작년 것인지 이번 것인지 갈리는 말 1줄: 둘 다 허용
- 고친 파일은 954줄(조회 24.9%)이다. 라벨이 바뀐 줄이 5줄, 둘 다 허용으로 빠진 줄이 1줄이다. 줄 수가 하나 줄어 보정 95줄의 구성도 바뀌었으므로, 아래 "라벨 효과"에는 보정 줄이 바뀐 효과가 섞여 있다

## 2026-10-26 · 1,000건으로 한 Laya 학습과 라벨을 섞은 대조 (#117)

1~4차를 합친 1,000건으로 다시 학습했다([7단계](architecture.md#7-학습측정보관) 실행 7~9와 대조). 확인하려던 것은 두 가지다. 데이터가 늘수록 나아지는지, 그리고 점수가 라벨을 배워서 나온 것인지다.

- 학습: 데스크톱(WSL 우분투, RTX 4080 SUPER), laya 0.4.7 `laya-train` 기본 설정(4에포크, 64건씩 갱신), `laya-multilingual`부터 새로 학습. 시드 0·1·2
- 학습 데이터: 955줄(조회 24.9%) 중 860줄로 학습하고 95줄은 확률 보정에 썼다. 갱신은 56번이다(500건은 28번)
- 대조: 같은 955줄에서 입력 글은 그대로 두고 정답만 줄끼리 무작위로 섞은 파일(`train1000_shuffled.jsonl`, 섞는 시드 117)로 시드 0을 한 번 학습했다. 조회 238줄과 아님 717줄의 수는 원래와 같고, 원래 정답과 우연히 같은 줄은 581줄이다(무작위로 섞으면 약 597줄이 같다)
- 측정: 노트북 CPU 2스레드, `check_laya_judge.py --eval-set --repeat 1`, 커밋 `634309d`. 개발용 141건(조회 31, 아님 110)으로 채점했다. 홀드아웃은 보지 않았다
- 체크포인트는 `junhyungdev/meeting-judge-laya`의 `t1000-s0`~`t1000-s2`, `t1000-shuffled-s0`에 있다. 노트북에서 받을 때 이번에도 세 개가 0바이트로 받아지고 하나는 빠져, 폴더마다 `--force-download`로 다시 받고 크기(643.8MB)와 해시가 모두 다른 것을 확인했다. 학습 로그는 저장소에 올라오지 않아 에포크별 손실은 보지 못했다

### 회차 비교 (세 숫자)

| 숫자 | 250건 (시드 0 / 1 / 2) | 500건 (시드 0 / 1 / 2) | **1,000건 (시드 0 / 1 / 2)** |
| --- | --- | --- | --- |
| AUROC | 0.867 / 0.913 / 0.838 | 0.943 / 0.930 / 0.936 | **0.977 / 0.939 / 0.954** |
| 오개입률 16 이하에서 가장 적은 놓침 | 8 / 7 / 14 | 4 / 5 / 3 | **2 / 6 / 6** |
| 놓침 2건 이하일 때 오개입률 | 닿지 못함 / 닿지 못함 / 61.8 | 닿지 못함 / 30.9 / 46.4 | **12.7 / 닿지 못함 / 닿지 못함** |

- **AUROC는 세 시드 모두 올랐다.** 조회할 말을 위쪽에 줄 세우는 능력은 나아졌다
- **나머지 두 숫자는 시드 0만 나아지고 시드 1·2는 나빠졌다.** 시드 0은 임계값 0.05에서 놓침 2건·오개입률 12.7로, 개발용에서는 교체 기준(놓침 2건 이하, 오개입률 16 이하)에 닿은 첫 모델이다. 시드 1·2는 임계값 0.05에서도 6건을 놓친다
- **시드끼리 차이가 다시 커졌다.** AUROC 폭이 0.013(500건)에서 0.038로, "오개입률 16 이하에서 가장 적은 놓침"의 폭이 2건에서 4건으로 늘었다
- 그래서 계획에서 정한 "데이터가 늘수록 나아진다"의 조건(세 숫자가 세 시드 모두 나아지고 시드 차이가 줄어듦)은 **채우지 못했다**

- 임계값 0.5에서는 세 시드 모두 500건보다 덜 놓친다(10~12건 → 5~7건)

### 지나친 확신

1,000건 세 시드 모두 확률 보정 온도가 `laya-train`의 상한 5.0에 걸렸다. 500건은 0.86~1.67이었다.

| | 보정 온도 | 보정 뒤 평균 확신도 | 보정에 쓴 줄 |
| --- | --- | --- | --- |
| 500건 시드 0 / 1 / 2 | 0.94 / 0.86 / 1.67 | 0.95 / 0.91 / 0.90 | 47 |
| 1,000건 시드 0 / 1 / 2 | **5.0 / 5.0 / 5.0** (상한) | 0.96 / 0.97 / 0.97 | 95 |

- 보정 온도는 학습에 쓰지 않은 줄로 모델의 확률을 고르게 펴는 값이다. 1보다 크면 모델이 실제보다 확신한다는 뜻이고, 상한에 걸렸다는 것은 5로 눌러도 다 펴지지 않을 만큼 확신한다는 뜻이다
- 같은 발화에 시드마다 정반대 확률을 주는 것도 이와 맞는다. "아 그건 장부 봐야 알아."는 시드 0·1·2가 0.942 / 0.016 / 0.982, "근데 거기 숙소 비교에 나오지 않았어요? 얼마였죠?"는 0.963 / 0.034 / 0.226이다
- 원인이 학습 데이터를 외운 것(갱신이 56번으로 늘어서)인지는 확인하지 않았다. 학습 로그가 있으면 마지막 에포크의 손실로 볼 수 있다. 500건 시드 0은 마지막 에포크 손실이 0.009였다

## 2026-10-26 · 학습 대본 3차 250건 (#117)

1,000건 학습에 쓸 세 번째 250건을 1·2차와 같은 순서로 만들었다. 대본 → 단서 검사 → 절반은 음성 → 검수 → luna 교차 확인 → 학습 파일이다.
이번에는 Claude 쪽 대본을 Sonnet이 아니라 Haiku 5.5가 썼다([작업 순서](architecture.md#7-학습측정보관)). 이 기록은 두 모델이 원고를 몇 번 고쳐 썼는지, 남은 단서, 검수가 초안에 끌려갔는지, 1~3차를 합친 조회 비율을 남긴다. 학습은 4차까지 모아 1,000건으로 한다.

- 대본: 행사 준비 회의 20개(t41~t60), 254발화. Claude Haiku 5.5가 10개(129발화), Gemini 3.8 Flash(medium)가 10개(125발화)를 썼다. 동아리와 행사는 1·2차와 평가 세트에 나온 것과 겹치지 않게 새로 정했다
- 조회 목표는 22%(125발화 중 약 28)로 낮췄다. 1·2차를 합친 472줄이 25.8%라 합쳐 25%에 맞추기 위해서다
- 지시서에는 2차 Gemini 피드백에 있던 회의 모양 규칙을 처음부터 넣었다. 질문에는 대개 누가 받는다, 의견이 갈리고 결론이 나는 흐름을 회의마다 넣는다, 질문이 연달아 나오는 곳은 열 곳 아래로 둔다는 규칙이다. 첫 시험에서 Haiku가 "둘 다 허용이면 좋겠어"처럼 라벨을 설명하는 낱말을 대사에 넣어서, 판단 기준 낱말을 대사에 쓰지 않는다는 규칙도 더했다
- 음성: 절반(129발화)을 ElevenLabs로 읽혀 Whisper로 받아 적었다. 대본과 같은 전사가 79/129, CER 평균 5.4%다. "토리야"가 "토리아"로 적힌 것이 8건 중 2건, "참가비"가 "참갑이"로 적힌 것이 1건 있다. 음성으로 읽힐 회의의 "ㅋ"·"ㅠ"는 지우고 읽혔다

Haiku는 게이트웨이 API로만 부를 수 있어, 지시서 원문을 보내고 답으로 받은 `draft.py`를 저장했다. 지시서와 피드백, 고칠 때는 Haiku 자신의 원고만 보냈다.

| 문제 | 원인 | 처리 |
| --- | --- | --- |
| 출력 2,000토큰 넘게 요청하면 400 | 게이트웨이가 스트리밍이 아닌 답을 2,000토큰까지만 받는다 | 스트리밍으로 받았다. 회의 10개가 출력 약 1만~2만 토큰이다 |

첫 원고만 medium이고 나머지는 low다. 1·2차의 Sonnet도 medium이었다.

- **지금 일 질문이 모두 이름을 부르면 해롭다.** 판단 모델이 "이름을 부르면 조회 아님"을 외울 수 있고, 평가 세트에는 이름을 불러 지난 값을 묻는 조회가 있다(`호칭`). 그래서 지금 일 질문의 이름을 절반 아래로 줄였다

### 낱말 단서

| 셈 | Haiku (최종) | Gemini (최종) |
| --- | --- | --- |
| 조회 질문에 기록 이름이 들어감 | 1/29 (3%) | 4/28 (14%) |
| 조회 질문이 "작년·지난"으로 시작 | 6/29 (21%) | 0/28 (0%) |
| 조회 질문에 "그때"가 들어감 | 5/29 (17%) | 4/28 (14%) |
| 지금 일을 묻는 말에 "지금·현재"가 들어감 | 1/22 (5%) | 1/25 (4%) |
| 앞 줄과 이 줄이 모두 물음표로 끝남 | 5 | 8 |
| 지금 일 질문 중 사람 이름을 부름 | 0/22 | 10/25 |

- Haiku의 "작년·지난" 말머리 21%는 목표(20%)에 걸쳤지만, 2차 Gemini 원고(20%)처럼 넘는 폭이 작아 그대로 두었다
- Gemini 조회 질문 28개 중 6개에 "결제했-"·"지출했-"이 들어 있다. 2차처럼 입으로 쓰는 말이라 두었지만, 조회 질문에만 나오는 낱말이다
- 3차에는 사람 이름을 불러 지난 값을 묻는 조회가 없다. 이 유형은 1·2차에만 있다
- Gemini 회의 10개 중 7개가 지금 일 질문에 대한 대답으로 끝난다. 대답이라 라벨은 조회 아님으로 맞지만, 회의 끝 모양이 되풀이된다

### 검수

검수자 1명(1·2차와 같은 사람)이 AI 초안을 보고 확인하거나 고쳤다. 25건(10%)은 초안을 가렸다.

| | 문항 | 조회·아님·둘 다 허용이 초안과 같음 |
| --- | --- | --- |
| 초안을 보임 | 229 | 229 (100%) |
| 초안을 가림 | 25 | 25 (100%). 이유 코드까지 같은 것은 20 |

- 254건에 11분, 문항 사이 간격의 중앙값이 1.0초였다(2차 1.3초)
- luna(`gpt-5.6-luna`, `meeting-judge-v5`)로 254건을 판단해 검수와 갈린 19건을 다시 봤다. 17건은 검수가 아님, luna가 조회였다. 지금 일 9건, 의견·혼잣말 4건, 사람이 값을 댄 대답 4건이다.
  2건은 검수가 조회, luna가 아님이었다("그건 나도 모름, 장부에 있을 듯", "드레스 빌렸던 데 어디였지"). 기준대로 검수 라벨을 두었다
- **4건을 고쳤다.** 갈린 발화 중 값을 대지만 "열다섯 판이었나", "열 명 아니었나?"처럼 스스로 되묻는 대답 2건을 조회로 고쳤다. [라벨 기준](../tests/fixtures/eval/README.md#경계-사례)의 "서른 명 넘었던 것 같은데 정확히는 기억이 안 나네요"(조회)와 같은 쪽으로 봤다. "제 기억으로는 여섯 마리 정도 나갔던 것 같아요"처럼 되묻지 않는 대답은 아님으로 두었다.
  갈리지 않은 발화 중 이번 경기의 신청 인원("공지 올린 거 기준으로 몇 명 신청했더라?")과 이번 대회의 제작비("이번엔 얼마더라")를 묻는 2건은 초안·검수·luna가 모두 조회였지만, 지금 일로 고쳤다. 기준의 "지금 신청 현황"과 같은 말이다
- 2차처럼 보인 초안을 하나도 고치지 않았고, 초안·검수·luna가 같이 틀린 것이 2건 나왔다. 셋이 같이 틀린 것은 luna 교차 확인으로 찾을 수 없어, 남은 것이 더 있을 수 있다

| | 판단 | 학습 줄 | 둘 다 허용 | 평가 문항과 겹침 | 조회 비율 |

## 2026-10-26 · 500건으로 한 Laya 학습 (#117)

학습 대본 1차와 2차를 합친 500건으로 다시 학습했다. 확인하려던 것은 "데이터가 늘수록 나아지는지"다([7단계](architecture.md#7-학습측정보관) 실행 4~6).
250건 체크포인트에서 이어서 학습하지 않고 `laya-multilingual`부터 새로 학습했다. 데이터 양 말고는 250건 때와 모두 같다.

- 학습: 데스크톱(WSL 우분투, RTX 4080 SUPER), laya 0.4.7 `laya-train` 기본 설정(4에포크, 64건씩 갱신), 시드 0·1·2
- 학습 데이터: 472줄(조회 25.8%) 중 425줄로 학습하고 47줄은 확률 보정에 썼다. 갱신은 28번이다(250건은 16번)
- 측정: 노트북 CPU 2스레드, `check_laya_judge.py --eval-set --repeat 1`, 커밋 `367f7a0`. 개발용 141건(조회 31, 아님 110)으로 채점했다. 홀드아웃은 보지 않았다
- 체크포인트는 `junhyungdev/meeting-judge-laya`의 `t500-s0`~`t500-s2`, 학습 로그는 같은 저장소의 `logs/`에 있다

### 회차 비교 (세 숫자)

| AUROC | 0.867 / 0.913 / 0.838 | **0.943 / 0.930 / 0.936** |

- **세 숫자가 세 시드 모두 나아졌다.** 시드 0의 세 번째 숫자는 여전히 "닿지 못함"(임계값 0.05에서 3건 놓침)이지만, 그 지점의 오개입률이 43.6에서 16.4로 줄었다

### 아직 놓치는 말

세 시드가 모두 낮은 확률(0.2 아래)을 준 조회는 250건 때와 같은 유형이다.

- 질문 형식이 아닌 말: "작년엔 어디였더라 청평이었나", "아 그건 장부 봐야 알아." `평서형` 태그 6건 중 세 시드 모두 3건을 놓쳤다
- 앞 질문을 고친 말: "아 재작년 말고 작년 거요 작년 버스비"
- 화면에 띄운 것을 가리키는 말: "여기 두 번째 데가 작년에 했던 데 아니에요?"
- 지난 정산 결과를 묻는 말: "근데 작년 정산하고 남은 돈 동아리 통장으로 들어갔나요?"

반대로 `AI호출`(6건)과 `직접요청`(9건)은 세 시드 모두 0건을 틀렸다. 250건 시드 0은 각각 1건씩 틀렸다.
놓친 유형만 골라 대본을 늘리지는 않는다. 개발용 문항에 맞추는 것이 되기 때문이다([2차 대본](#2026-10-26--학습-대본-2차-250건-117)).

### 지연·메모리와 로그

- 판단 p50 81~82ms, p95 90~96ms로 250건(83ms, 118ms)과 비슷하다

- `laya-train` 로그의 개발용 정확도는 0.90~0.91, ECE는 0.046~0.068이다. 정확도는 [250건 기록](#laya-train-로그의-정확도를-쓰지-않는-이유)에 적은 이유로 판단에 쓰지 않는다.
  보정에 쓴 줄이 47개뿐이라는 경고는 이번에도 나왔다
- 마지막 에포크의 학습 손실이 0.009~0.163으로 시드마다 크게 다르다. 학습 데이터를 거의 외운 시드가 있다는 뜻이지만, 개발용 점수는 시드끼리 비슷했다

## 2026-10-26 · 학습 대본 2차 250건 (#117)

500건 학습에 쓸 두 번째 250건을 1차와 같은 순서로 만들었다. 대본 → 단서 검사 → 절반은 음성 → 검수 → luna 교차 확인 → 학습 파일이다.
이 기록은 1차에서 되풀이된 틀을 막았는지, 검수가 초안에 끌려갔는지, 1차와 합친 500건의 조회 비율을 남긴다. 학습 결과는 아직 없다.

- 대본: 행사 준비 회의 20개(t21~t40), 250발화. Claude Sonnet 5.5(effort medium)가 10개, Gemini 3.8 Flash(medium)가 10개를 썼다. 동아리와 행사는 1차와 겹치지 않게 새로 정했다
- 지시서는 1차 것을 바탕으로 1차에서 되풀이된 틀을 막는 규칙을 더했다. 앞 발화에 기대는 말이 "그때"로만 시작하지 않게, "어, ○○가…"처럼 말끝을 흐린 혼잣말은 회의 10개에 두세 번까지, 물음표는 라벨과 관계없이 같은 방식으로 붙이기, 조회 질문의 기록 이름은 다섯 개 중 한 개 아래로다
- 조회 목표는 24%로 1차(25%)보다 조금 낮췄다. 1차가 26.3%여서 합쳐 25%에 맞추기 위해서다. 질문 형식이 아닌 말이나 지시어처럼 첫 학습에서 놓친 유형은 1차 비율 그대로 두었다. 개발용 문항에 맞추지 않기 위해서다
- 분위기는 친한 회의 8개, 선후배가 섞인 회의 6개, 안 친한 회의 6개다. AI 호출어 "토리야"를 부른 말이 12건이다
- 음성: 절반(130발화)을 ElevenLabs로 읽혀 Whisper로 받아 적었다. 대본과 같은 전사가 78/130, CER 평균 5.6%이고 대부분 숫자 표기 차이다. "토리야"가 "도리아"로 적힌 것이 1건 있다

### 모델별 낱말 단서와 회의 모양

`cues.py`에 "그때"와 말끝을 흐린 혼잣말 셈을 더했다. 1차 Gemini 원고(다시 쓴 것)에 돌리면 "그때"가 조회 질문의 32%, 말끝을 흐린 혼잣말이 혼잣말의 79%였다.

- 대신 Gemini 1차 원고는 회의 모양이 실제 회의와 달랐다. 혼잣말 19건 중 17건이 회의 맨 끝 두 줄에 몰렸고, 질문이 줄줄이 이어지며 받아서 답하거나 반박하는 말이 적었다. 판단 모델은 앞 발화 4개를 함께 보므로, 이런 틀을 배우면 실제 회의의 흐름을 배우지 못한다.
  숫자와 고칠 방향을 피드백으로 주고 처음부터 다시 쓰게 했다
- 다시 쓴 원고의 "작년·지난" 말머리와 "지금"은 20%로 목표에 걸쳤지만 넘지 않아 그대로 두었다. 딱딱한 낱말 4건은 모두 "결제했었지"처럼 "결제했-"이 든 말로, 입으로도 쓰는 말이라 두었다

### 검수

검수자 1명(1차와 같은 사람)이 AI 초안을 보고 확인하거나 고쳤다. 25건(10%)은 초안을 가렸다.

| | 문항 | 조회·아님·둘 다 허용이 초안과 같음 |
| --- | --- | --- |
| 초안을 보임 | 225 | 225 (100%) |
| 초안을 가림 | 25 | 25 (100%). 이유 코드까지 같은 것은 19 |

- 250건에 13분, 문항 사이 간격의 중앙값이 1.3초였다(1차 2초)
- 검수 페이지에서 Enter가 "초안대로"가 아니라 마우스로 마지막에 누른 버튼을 다시 누르는 문제가 있었다. 지난 문항에서 고른 값이 다음 문항에 저장된다. 이 문제로 1건(t21-13)이 잘못 저장돼 다시 골랐고, 페이지를 고친 뒤 나머지를 검수했다.
  1차 검수도 같은 페이지였지만, 보인 초안 225건이 모두 초안과 같아 이 문제로 다르게 저장된 문항은 없다
- luna(`gpt-5.6-luna`, `meeting-judge-v5`)로 250건을 판단해 검수와 갈린 19건을 다시 봤다. 15건은 검수가 아님, luna가 조회였다. 지금 일 6건, 지난 일을 꺼내며 의견을 낸 말 3건 등 홀드아웃에서 luna가 잘못 띄운 유형과 같았다.
  4건은 검수가 조회, luna가 아님이었다. 지난 값을 물었는데 "기억이 안 나네"처럼 모른다고 답한 말 3건과 지난 행사의 담당자를 묻는 말 1건으로, 기준대로 조회로 두었다
- **1건을 고쳤다.** "신발 대여료가 한 켤레에 이천 원이었나 삼천 원이었나"(t31-05)는 초안이 혼잣말이었고 검수도 그대로 넘겼다. 두 줄 앞에 같은 볼링장의 지난 게임비를 묻는 말이 조회로 붙어 있어 조회로 고쳤다.
  "아 맞다 거기 얼마였지"(t26-08)는 "거기"가 앞 발화에 나오지 않아 대상 모름으로 두었다
- 가린 문항이 모두 초안과 같았고 보인 문항을 하나도 고치지 않았다. 그런데 luna 교차 확인에서 초안이 틀린 것이 1건 나왔다. 검수가 초안을 그대로 넘긴 경우가 적어도 1건 있다는 뜻이다

## 2026-10-25 · 250건으로 한 첫 Laya 학습 (#117)

학습 대본 1차(아래 기록)로 Laya를 처음 학습했다. 이 단계에서 확인하려던 것은 "학습이 되는지"다.
계획([7단계](architecture.md#7-학습측정보관))대로 같은 데이터로 시드만 바꿔 세 번 학습하고, 평가 세트의 **개발용**으로만 쟀다. 홀드아웃은 1,000건을 학습할 때까지 보지 않는다.

- 학습: 데스크톱(WSL 우분투, RTX 4080 SUPER), laya 0.4.7 `laya-train` 기본 설정(4에포크, 64건씩 갱신). 시작 모델 `laya-multilingual`, 시드 0·1·2
- 학습 데이터: 236줄 중 213줄로 학습하고 23줄은 확률 보정에 썼다. 모델 값을 고친 횟수(갱신)는 16번이다
- 측정: 노트북 CPU 2스레드, `check_laya_judge.py --eval-set`, 커밋 `53ac1f1`. 개발용 151건 중 둘 다 허용 10건을 뺀 141건(조회 31, 아님 110)으로 채점했다
- 체크포인트는 Hugging Face 비공개 저장소 `junhyungdev/meeting-judge-laya`의 `t250-s0`~`t250-s2`에 있다. 파일 형식은 `model.safetensors`다

### 결과 (임계값 0.5)

| | 놓침 (조회 31건 중) | 오탐 (아님 110건 중) | 오개입률 | AUROC |
| --- | --- | --- | --- | --- |
| 학습 전 Laya | 9 | 71 | 64.5 | 0.533 |
| **250건 학습, 시드 0** | 15 | 3 | 2.7 | 0.867 |
| **250건 학습, 시드 1** | 12 | 4 | 3.6 | 0.913 |
| **250건 학습, 시드 2** | 21 | 2 | 1.8 | 0.838 |
| luna (10-21) | 2 | 9 | 8.2 | — |

- 놓침은 조회해야 할 말에 카드를 띄우지 않은 수, 오개입률은 조회 아닌 말 100개당 쓸데없이 띄운 카드 수다
- AUROC는 조회할 말에 조회 아닌 말보다 높은 확률을 줬는지 보는 값이다. 임계값과 관계없이 순서만 보며, 0.5면 무작위, 1이면 완벽이다
- 학습 전 Laya는 거의 모든 말에 비슷한 확률(조회 0.65, 아님 0.62)을 줘서 카드를 마구 띄웠다. 학습한 뒤에는 조회 아닌 말에 낮은 확률(평균 0.09~0.11)을 준다

### 읽은 것

- **학습은 됐다.** AUROC가 0.533(무작위 수준)에서 0.84~0.91로 올랐다. 조회할 말을 대체로 위쪽에 줄 세운다
- **아직 교체 기준에는 멀다.** 기준은 "luna가 잡은 조회를 하나도 놓치지 않고 오개입률 16 이하"다([1단계](architecture.md#1-바꾸는-기준)). 지금은 임계값 0.5에서 조회의 39~68%를 놓친다.
  임계값을 낮춰 luna만큼(놓침 2건 이하) 잡으려면 시드 2는 임계값 0.05에서 오개입률 61.8이 되고, 시드 0·1은 0.05에서도 3건을 놓친다(오개입률 43.6, 40.9)
- **카드를 아끼는 쪽으로 기울었다.** 오탐은 2~4건으로 luna보다 적지만, 조회할 말에 준 확률 평균이 0.35~0.57로 낮다
- **시드마다 차이가 크다.** 같은 데이터로 놓침이 12~21건으로 갈렸다. 갱신 16번은 학습 순서 같은 우연의 영향이 큰 양이다. 1,000건이면 갱신이 약 60번이다([2단계](architecture.md#2-학습-데이터의-출처와-양))
- **주로 놓친 말**은 질문 형식이 아닌 말("작년엔 어디였더라 청평이었나"), 대상이 앞 발화에만 있는 말("거기 숙소 비교에 나오지 않았어요? 얼마였죠?"), 음성 인식이 틀린 말("회측에 …")이다. 세 시드 모두 비슷했다
- **지연과 메모리는 학습 전과 같다.** 판단 p50 83ms, p95 118ms, 최대 메모리 1.08GB(시드 0)

### 임계값별로 보면

임계값은 Laya가 낸 조회 확률이 몇 이상이면 카드를 띄울지 정한 값이다. 낮추면 놓침은 줄고 오개입률은 는다. 칸은 놓침 / 오개입률이다.

| 임계값 | 시드 0 | 시드 1 | 시드 2 |
| --- | --- | --- | --- |
| 0.1 | 7 / 24.5 | 4 / 26.4 | 5 / 34.5 |
| 0.15 | 8 / 12.7 | 6 / 16.4 | 9 / 26.4 |
| 0.2 | 10 / 10.0 | 7 / 11.8 | 11 / 17.3 |
| 0.3 | 10 / 6.4 | 9 / 8.2 | 15 / 8.2 |
| 0.5 (기본) | 15 / 2.7 | 12 / 3.6 | 21 / 1.8 |

- **임계값으로는 기준에 닿지 않는다.** 오개입률을 16 이하로 지키면 7건 이상을 놓치고, luna만큼(2건 이하) 잡으려면 오개입률이 기준을 크게 넘는다. 부족한 것은 임계값이 아니라 조회 말과 아닌 말을 가르는 능력이라, 데이터를 늘린다
- **임계값은 아직 정하지 않는다.** 가장 나은 지점이 시드마다 0.15, 0.2, 0.25로 다르고, 모델이 바뀌면 확률 분포도 바뀐다.
  계획대로 1,000건 모델에서 개발용으로 고르고, 학습 데이터(조회 25%)와 실제 회의(약 5%로 가정)의 조회 비율 차이만큼 다시 옮긴다([4단계](architecture.md#4-학습-데이터의-쏠림))

**회차끼리는 임계값과 관계없는 세 숫자로 견준다.** 임계값 0.5 한 지점만 보면 "놓침은 줄고 오탐은 늘었다"처럼 나아졌는지 가리기 어렵다.

| 숫자 | 뜻 | 250건 (시드 0 / 1 / 2) |
| --- | --- | --- |
| AUROC | 임계값과 관계없이 조회 말을 위쪽에 줄 세우는 정도 | 0.867 / 0.913 / 0.838 |
| 오개입률 16 이하에서 가장 적은 놓침 | 오개입 상한을 지킬 때 얼마나 덜 놓치나 | 8 / 7 / 14 |
| 놓침 2건 이하일 때 오개입률 | luna만큼 잡으려면 카드를 얼마나 띄우나 | 닿지 못함 / 닿지 못함 / 61.8 |

500건에서 세 숫자가 세 시드 모두 나아지고 시드끼리 차이가 줄면 "데이터가 늘수록 나아진다"고 본다. "닿지 못함"은 임계값 0.05에서도 3건을 놓쳤다는 뜻이다.

### `laya-train` 로그의 정확도를 쓰지 않는 이유

`laya-train`은 학습 전후 정확도를 함께 찍는다. 이번에는 0.43에서 0.84~0.89로 올랐다. 하지만 개발용 141건 중 110건이 조회 아님이라, 카드를 한 번도 띄우지 않아도 0.78이 나온다.
그래서 교체 판단은 정확도가 아니라 놓침과 오개입률로 하고, 이 둘은 `check_laya_judge.py`로 따로 잰다.
로그의 ECE(확률이 실제 비율과 맞는 정도, 0에 가까울수록 좋음)는 0.37에서 0.05~0.07로 줄었지만, 보정에 쓴 줄이 23개뿐이라는 경고가 함께 나왔다.

## 2026-10-25 · 학습 대본 1차 250건 (#117)

Laya 학습 데이터의 첫 250건을 만들었다. 대본을 쓰고, 절반을 음성으로 거치고, 사람이 검수해 학습 파일로 바꿨다([바꾸는 계획 2·3단계](architecture.md#2-학습-데이터의-출처와-양)).
이 기록은 대본을 쓴 모델별로 낱말 단서가 얼마나 들어갔는지, 검수가 AI 초안에 끌려갔는지, 평가 문항과 얼마나 겹쳤는지를 남긴다. 학습 결과는 아직 없다.

- 대본: 행사 준비 회의 20개, 251발화. Claude Sonnet 5.5(effort medium)가 10개, Gemini 3.8 Flash(medium)가 10개를 썼다. 홀드아웃을 쓴 Codex와 다른 모델이다
- 두 모델은 대본 지시서 한 파일만 보고 썼다. 실행 기록에서 다른 파일을 열지 않은 것을 확인했다. 지시서의 예시 문장은 평가 문항과 글자 비슷도 0.7을 넘는 것이 없게 썼다
- 분위기는 친한 회의(반말·반존대) 8개, 선후배가 섞인 회의 6개, 안 친한 회의(존대) 6개다. AI 호출어 "토리야"(#124)를 부른 말이 13건이다
- 음성: 절반(121발화)을 ElevenLabs로 읽혀 Whisper로 받아 적었다. 대본과 같은 전사가 91/121, CER 평균 3.3%이고 대부분 숫자 표기 차이다("삼만 오천 원" → "35,000원")
- 학습 파일은 커밋 `1d581c1`의 `make_laya_training.py`로 만들었다

### 모델별 낱말 단서

판단 모델이 기준 대신 낱말만 보고 맞힐 수 있는 단서를 셌다. 이런 단서가 몰린 대본으로 배우면 Laya가 "'장부'가 있으면 조회, '지금'이 있으면 조회 아님"처럼 외워서,
실제 회의의 "그때 버스 몇 대 불렀지?"처럼 단서 없는 말을 놓친다.

| 셈 | Sonnet | Gemini 1차 원고 | Gemini 다시 쓴 원고 |
| --- | --- | --- | --- |
| 조회 질문에 기록 이름(장부·보고서·회칙 등)이 들어감 | 4/30 (13%) | 16/31 (52%) | 1/31 (3%) |
| 조회 질문이 "작년·지난·저번"으로 시작 | 1/30 (3%) | 16/31 (52%) | 0/31 (0%) |
| 지금 일을 묻는 말에 "지금·현재"가 들어감 | 2/22 (9%) | 15/25 (60%) | 0/25 (0%) |
| 딱딱한 낱말(책정·집행·~습니까 등)이 든 발화 | 0 | 16 | 0 |

- Gemini 1차 원고는 위 숫자와 원고의 문장을 피드백으로 주고 처음부터 다시 쓰게 했다. 목표는 Sonnet 수준(20% 아래)으로 잡았다
- 다시 쓴 원고에도 "어, 안전벨트가…"처럼 말이 끊긴 혼잣말이 15번쯤 되풀이됐다. 다음 250건 지시서에서 막는다

### 검수

### 바꾸는 기준에 대어 보면

```text
Laya 판단 p95 0.09초 (노트북 CPU 2스레드, 10-19) + 검색어만 p95 2.72초 = 약 2.81초

같은 측정에서 번갈아 잰 지금 판단 p95  3.55초  → 낮다
1단계 기준에 적힌 값 (기준선 측정)      2.38초  → 높다. 다른 날 잰 값끼리의 비교다
```

- 검색어만 받는 호출의 지연은 지금 판단 호출과 같다고 보는 것이 맞다. Laya로 바꿔도 조회 경로의 지연은 줄지 않고 Laya 판단 시간(약 0.1초)만큼 는다
- 줄어드는 것은 조회 아닌 발화의 호출이다. 평가 세트처럼 조회가 20%면 LLM 호출이 약 5분의 1(Laya의 오탐만큼 더)이 되고, 남은 호출도 입력이 짧아 호출 1,000회 비용이 ₩227에서 ₩158이다
- 기준에 적힌 2.38초는 다른 날 잰 값이라, 이번처럼 게이트웨이가 느린 날은 Laya와 관계없이 넘는다
- 그래서 이 측정 뒤 1단계 지연 기준을 "같은 측정에서 번갈아 잰 지금 판단 p95보다 0.2초 넘게 늘지 않음"으로 바꿨다. 이번 값(약 2.81초 대 3.55초)은 이 기준을 넘는다. 다만 Laya를 학습한 뒤 배포 서버에서 다시 잰다

```text
j15-09 "작년 송년회 때 장소 대관료 얼마였지?"  → 2025 송년회 장소 대관료
j15-10 "아 그건 장부 봐야 알아."              → 2025 송년회 장소 대관료   (검색어가 같다)
j16-06 "작년에 숙박비 1인당 얼마씩 냈어요?"      → 2026 겨울 워크샵 1인당 숙박비
j16-07 "그거 정산표 다시 보고 비슷하게 맞추죠" → 2026 겨울 워크샵 숙박비 1인당 (낱말 순서만 다르다)
```

라벨은 앞 발화가 이미 찾았는지와 관계없이 붙이므로(평가 세트 라벨 기준), 겹치는 호출은 검색 단계에서 줄인다. 검색어가 글자까지 같은 것은 4건뿐이라, 줄인다면 글자가 아니라 낱말이나 검색어 임베딩으로 같은지 봐야 한다. 같은 질문을 다시 해도 답을 띄우는 요구사항(AI-MEET-04)은 지키고 결과만 다시 쓰는 방식이다. 아직 만들지 않았다.

### 한계

- 검수자가 1명이다. 두 사람이 같은 라벨을 붙이는지(#115 완료 조건)는 재지 않았다
- 홀드아웃의 조회 필요가 9건이라 1건 차이로 재현율이 0.11 움직인다. 모델 교체 판단에는 실제 회의 녹음을 더한다
- luna를 1회만 쟀다
- 대본은 AI가 썼고 TTS 음성이라 실제 회의보다 깨끗하다. 시간당 오개입은 실제 회의의 발화 수가 없어 내지 않았다

## 2026-10-19 · 학습 전 Laya와 luna (#117)

판단을 Laya 같은 판단 전용 모델로 바꾸려면 학습이 필요하다. 학습한 뒤 얼마나 나아졌는지 보려면 학습 전 값이 있어야 해서, 같은 문항으로 luna와 학습 전 Laya를 쟀다.

- 문항: 회의 판단 평가 문항 110개(조회 필요 34). 커밋 `b3b0088`(변경 없는 상태)
- luna: `gpt-5.6-luna`, `meeting-judge-v5`, `effort=none`, `max_retries=2`, 1회
- Laya: `convaiinnovations/laya-multilingual` 커밋 `e4e9ddf`(laya 0.4.7이 검토한 커밋), laya 0.4.7, torch 2.14.1, 학습 없음, 판단 질문 `meeting-questions-v1`, CPU.
  노트북(Apple M5)에서 torch 기본 4스레드와 2스레드로 한 번씩, 예열 뒤 문항 전체를 3회 판단했다. 3회의 확률이 모두 같아 판단 값은 한 번 잰 것과 같다
- 2스레드는 t3.medium(vCPU 2)과 스레드 수만 맞춘 값이다. 서버에서 잰 값이 아니다

### 정확도

| | 균형 정확도 | 오탐 | 놓침 | AUROC |
| --- | --- | --- | --- | --- |
| luna | **0.980** | 3 / 76 | 0 / 34 | — |
| 학습 전 Laya | 0.487 | 40 / 76 | 17 / 34 | **0.475** |

| 묶음 | luna 균형 정확도 | Laya 균형 정확도 | Laya AUROC |
| --- | --- | --- | --- |
| `query` 72 | 0.981 | 0.528 | 0.486 |
| `pipeline` 26 | 1.000 | 0.287 | 0.250 |
| `vocative` 12 | 0.917 | 0.500 | 0.611 |

- **학습 전 Laya는 조회할 발화를 가려내지 못한다.** AUROC 0.475는 무작위(0.5)와 같은 수준이다. 0.5라는 기준값이 틀린 것이 아니라 확률의 순서부터 맞지 않으므로, 기준값을 다시 정해서는 나아지지 않고 학습이 필요하다
- 확신하고 틀린 예가 많다. "자 그럼 봄 MT 준비 회의 시작할게요."(조회 아님)에 P=0.95, "회측에 참갑이 상한 같은 교정이 있었나요?"(조회)에 P=0.01을 줬다
- 이름을 부른 발화(`vocative`)에는 정답과 관계없이 모두 높은 확률을 줬다(조회 0.90, 조회 아님 0.86 평균). "지은아, 화면 좀 넘겨 줄래?"가 P=0.98이다
- luna의 오탐 3건은 앞선 측정의 경계 사례와 같다(q2-09, q4-02, "현우야 작년 회칙 파일 좀 띄워 줄래?" v-12)

### 지연·자원·비용

| | 판단 지연 p50 / p95 | 판단 1회 자원 | 판단 1,000회 비용 |
| --- | --- | --- | --- |
| luna | 1.61 / 2.32초 (게이트웨이 호출) | 입력 641, 출력 21토큰. 캐시 0, 추론 0 | **₩217** |
| Laya 4스레드 | 74 / 88ms | 최대 메모리 약 1.4GB (불러오기 전 0.3GB) | 0원 (API 없음) |
| Laya 2스레드 | 83 / 91ms | 최대 메모리 약 1.5GB | 0원 (API 없음) |

- luna 비용은 입력이 대부분이다(₩181 + 출력 ₩36). 입력 약 640토큰은 프롬프트 캐시가 걸리는 길이에 못 미쳐 캐시가 0이었다
- Laya는 API 비용 대신 서버 메모리를 쓴다. 모델을 올리면 약 1.1~1.2GB가 는다. t3.medium(4GB)에서 BE와 같은 프로세스에 둘 수 있는지는 재지 않았다
- Laya 모델을 불러오는 데 약 3초가 든다. 서버가 뜰 때 한 번 올려 두는 값이다
- RAG로 판단한 발화는 Laya로 바꿔도 검색어를 만들 LLM 호출이 필요하다. 그 호출의 토큰과 지연은 검색어만 만드는 프롬프트가 없어 재지 않았다

### 결론

- **학습 전 Laya로는 바꿀 수 없다.** 이 값을 학습 전 기준선으로 두고, 학습한 체크포인트를 같은 스크립트(`--model`)로 다시 잰다
- 판단 비용만 보면 luna도 판단 1,000회 약 ₩217로 작다. Laya로 바꿀 이유는 비용보다 지연(게이트웨이 p50 1.61초 대 노트북 CPU 약 0.08초)과 판단 질문을 더해도 호출이 늘지 않는 점이다

### 한계

- 110개 중 `query`와 `vocative`는 luna 프롬프트를 고칠 때 본 문항이라 luna 값은 낙관적이다. 모델을 바꿀지 정하는 비교는 조정에 쓰지 않은 #115 홀드아웃으로 한다
- Laya 지연과 메모리는 노트북 CPU 값이다. 배포 서버나 Laya를 따로 띄운 서버(laya-serve)에서 다시 잰다
- luna는 1회만 쟀다. 정확도는 앞선 측정들과 같은 범위다

## 2026-10-19 · 회의 검색어로 기록 검색, 근거 판단 추론 깊이 (#72)

회의는 판단이 만든 검색어로 기록 검색(`search_records`)을 검색어 정리 없이 부른다.

  q49 "다음 MT 회비 정할 때 참고할 기록 있어?")는 회의에서 찾지 않으므로 빼고 48개를 쟀다
- 기록 검색: 커밋 `9cede1d`(변경 없는 상태), luna, 검색 1회, 검색어 정리 없음, 예시 기록 12종, 확인용 질문 포함, 캐시 없음,

### 결론

- **v5를 쓴다.** 놓치면 아무것도 뜨지 않지만 오탐은 닫으면 되는 카드다(AI-MEET-05). 이름을 부른 기록 질문은 요구사항에 예시로 적힌 경우다.
- **더 다듬지 않는다.** 후보를 늘릴수록 직접 쓴 문항에 맞추게 된다. 참고 자료를 띄우지 못해도 사용자가 AI를 불러 직접 요청할 수 있다(#124). 참고 자료 제안은 `record_reference`로 따로 다루는 방안을 판단 기록으로 확인한다([아키텍처](architecture.md#판단-질문과-처리기)).
- 이름을 부른 문항은 #115 평가 세트에 넣어 다시 본다.

### 한계

- **과적합 위험이 있다.** 이름 문항 12개는 AI가 이번에 쓴 것이고, 같은 문항을 보고 문구를 골랐다. 72발화도 프롬프트 조정에 쓴 문항이다. 조정에 쓰지 않은 26발화에는 이름을 부른 기록 질문이 없다. #115 홀드아웃으로 다시 잰다.
- 이름 문항은 대본 글이라 오인식이 없다. 호칭이 잘못 들리는 경우는 보지 않았다.
- 지연은 비교하지 않았다. 변형을 번갈아 부르지 않았고, 게이트웨이가 느린 구간이 섞였다. v4 대조군 한 호출은 9.98초로 제한 시간 10초에 닿을 뻔했고, v5a 1회차에서는 1건이 시간을 넘겼다.

## 2026-10-14 · 레포 구현 확인 (#114)

측정 폴더에서 정한 v4 프롬프트·앞 발화 4개·회의 날짜를 `features/meeting`으로 옮긴 뒤, 같은 72발화를 레포 코드로 판단했다.

## 2026-10-14 · 검색어 품질

10-13 측정은 조회 필요 여부만 채점했다. 그런데 검색어는 기록 검색 입력이면서 화면에 무엇을 물었는지 보여주는 값이라, 검색어 자체가 쓸 만한지 따로 쟀다.

### 1차 · 앞 발화 수와 검색어 지시

| --- | --- | --- | --- | --- | --- |
| 기존 프롬프트, 앞 발화 2개 | 67% | 35% | 71% | 28.4 | 53% |
| 기존 프롬프트, 앞 발화 4개 | 92% | 100% | 71% | 31.2 | 44% |

terra의 최대 6.37초는 게이트웨이가 가끔 밀린 것으로 보인다.

### 출력 형식 — 이유와 확신도를 빼면 0.65초 빨라진다

luna, 20건 × 3회.

| 출력 | p50 | p95 | 토큰/호출 | 균형 정확도 |
| --- | --- | --- | --- | --- |
| 조회 필요 여부·검색어·확신도·이유 | 2.22초 | 2.90초 | 374 | 1.000 |
| 조회 필요 여부·검색어 | **1.57초** | **2.21초** | 324 | 1.000 |

### 판단 지연을 더 줄이는 변형 — 효과 없음

21건 × 3회 × 4변형 = 252호출. 발화마다 네 변형을 번갈아 호출하고 회차마다 순서를 돌렸다.

| 변형 | p50 | p95 | 평균 | 가장 빨랐던 횟수 | 균형 정확도 |
| --- | --- | --- | --- | --- | --- |
| 기준(조회 필요 여부·검색어) | 1.54초 | **2.15초** | **1.61초** | 16 / 63 | 1.000 |
| + 짧은 프롬프트 | 1.74초 | 2.58초 | 1.81초 | 4 / 63 | 1.000 |
| + 응답 저장 끄기(`store=False`) | **1.43초** | 2.54초 | 1.62초 | 29 / 63 | 1.000 |
| + 짧은 프롬프트 + 응답 저장 끄기 | 1.53초 | 2.20초 | 1.65초 | 14 / 63 | 1.000 |

- **처음에는 변형을 하나씩 차례로 쟀는데 순서 효과가 있었다.** 변형과 관계없이 뒤에 잰 것일수록 빨랐다(2.24초 → 1.44초). 그래서 번갈아 다시 쟀다. 지연을 비교할 때는 번갈아 호출한다.
- **짧은 프롬프트는 오히려 느리다.** 호출당 토큰을 325에서 184로 43% 줄였는데 63번 중 4번만 가장 빨랐다. 입력 길이는 지연과 관계가 없었다.
- **응답 저장 끄기는 중앙값만 좋고 꼬리가 나쁘다.** p50은 0.11초 줄었지만 p95가 0.39초 늘었다.
- **프롬프트 캐싱은 걸리지 않았다.** 모든 변형에서 캐시된 토큰이 0이었다. 입력이 약 310토큰이라 캐시가 걸리는 길이에 못 미친다.

### 바닥값 — 호출 한 번에 약 1.1초

"ok" 한 마디를 보내고 16토큰만 받는 최소 호출과 판단 호출을 번갈아 각 20회.

| 호출 | p50 | p95 | 최소 |
| --- | --- | --- | --- |
| 최소 호출 | **1.11초** | 2.77초 | 1.00초 |
| 판단 호출 | 1.60초 | 2.02초 | 1.22초 |

판단이라는 일 자체에 드는 시간은 약 0.5초다. 네트워크·서버 대기·추론을 따로 재지 않았으므로 1.11초를 왕복 시간으로 해석하지 않는다.

| 옵션 | 결과 |
| --- | --- |
| `language` 생략 · `korean` · `ko` | 셋 다 동작하고 결과가 같다 |

| `return_timestamps=true` | chunks가 비어서 오고, 1.34초에서 6.29초로 4.7배 느려진다 |
| 무음 10초 | `" 감사합니다."`가 나온다 |

응답은 OpenAI 형식이 아니라 `transcript` 안에 `text`와 `chunks`가 온다.

### STT 오인식과 판단

CER 평균 2.4%, 원문과 완전히 같은 발화 77%.

| 판단 입력 | 균형 정확도 | 재현율 | 특이도 |
| --- | --- | --- | --- |
| Whisper 텍스트 | 0.971 | 1.000 | 0.941 |
| 대본 원문 | 0.971 | 1.000 | 0.941 |

두 입력의 판단 결과가 같았다. 가장 많이 틀리게 들은 발화도 판단은 맞았다.

```text
말한 것: 회칙에 참가비 상한 같은 규정이 있었나요?
들은 것: 회측에 참갑이 상한 같은 교정이 있었나요?   (CER 23.5%)
→ 판단: 조회 필요 (정답)
```

| 말한 것 | 들은 것 |
| --- | --- |
| 회칙 | 회측 |
| 규정 | 교정 |
| 참가비 | 참갑이 |
| 서른 명 · 삼십만 원 · 사만 원 | 30명 · 30만원 · 4만원 (숫자로 적힘) |

틀린 1건("음 서른 명 좀 넘었던 것 같은데 정확히는 기억이 안 나네요")은 라벨이 잘못된 것이었다.
대본 원문으로도 똑같이 판단했으므로 STT 탓이 아니다. 질문 형식이 아니어도 기억나지 않는 정보를 찾는 말은 조회 필요로 보기로 하고(AI-MEET-01) 라벨을 고쳤다. 고친 기준으로는 26발화 모두 맞았다.

### 한계

## 2026-11-03 · 데모 회의 자료 검색 점검

기준 `724ded2`와 같은 코드에서 답변의 미확인 문구만 먼저 바꾼 상태를 기준으로 삼았다. 사용자 승인 후 데모 자료함의 가상 문서 13건을 기존 청크 규칙·실제 임베딩으로 37청크로 재구성하고, 메모리 검색과 GPT-5.6 Luna 판단·근거 모델로 회의 질문 8개를 각 1회 확인했다. 운영 pgvector 순위나 실제 마이크 왕복은 아니다. 질문은 참가 인원·총지출, 장소·교통비, 미수집 만족도, 담당·기한, 우천 장소, 계획 예산 합계, 회고, 최근 행사 인원이다.

기준에서는 미수집 사실이 있는 문서가 검색됐지만 NOT_FOUND였고, 계획 예산 CSV가 1위인데도 NOT_FOUND였다. 회고 문장은 벡터 후보 13위로 상위 5개에 없었으며 무관한 예산 사실이 나왔다. 최근 행사 질문에서는 참가 인원 본문이 9위여서 빠졌다. 문서명이 검색됐다는 사실만으로 정답 청크 검색을 성공으로 세지 않는다.

회의 전용 후보는 원발화를 근거 판단에 추가하고, 질문 범위·미수집/미정·계획/실제 구분을 회의 전용 프롬프트로 보완했다. 회고와 최근 참가 인원 질문만 벡터 후보 20개를 가져와 기존 상위 3개를 보존하고 관련 본문 최대 2개를 보충하며 모델에는 5개만 전달한다. 명시 연도가 있으면 보충 청크에 해당 연도가 있어야 한다. 다른 질문은 기존 5개 검색을 유지하고 외부 호출을 추가하지 않는다. 중간 후보 8질문 1회에서 모두 관련 근거 답을 반환했고, 이후 정렬 보완 뒤 회고·최근 질문만 각 1회 별도 재측정해 회고 진행·세부 미확인과 검색된 자료 기준 인원을 출처와 함께 확인했다. 이 두 건과 앞선 8건은 정렬·프롬프트 버전이 달라 같은 실행으로 합산하지 않는다. 미수집·미정 답 뒤에 같은 항목이 미확인으로 중복 표시된 사례는 남았다. CSV에 통화 단위가 없으면 금액에 원을 임의로 붙이지 않았다.

기준 8회 평균 전체 6.39초(4.58~8.54), 판단 2.44초, 검색 0.45초, 답변 3.51초였다. 보완 중간 후보 8회는 전체 평균 5.72초(4.80~7.06), 판단 2.49초, 검색 0.42초, 답변 2.81초였다. 한 번씩의 순차 호출이라 속도 개선이나 일반 정확도를 입증하는 수치가 아니다. 최종 정렬 보완 뒤 두 질문은 각각 6.07초와 6.14초였다. 현재 진행 중인 행사 질문은 별도 단독 판단 1회에서 NO_LOOKUP이었고 실시간 행사 상태를 답하는 경로는 아직 없다. 최신 답변에도 검색된 자료 기준이며 전체 최신 여부는 미확인임을 표시한다. 모델 오판, 제한된 검색 범위, 부분 답변과 답변의 의미·출처 연결 오류 가능성은 남는다.
