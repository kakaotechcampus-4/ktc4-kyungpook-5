# AI 구조와 협업 기준

## 범위

AI 팀원이 기능별로 나누어 작업할 수 있도록 planning, retrieval, operations, meeting을 분리합니다. 폴더·역할과 행사 Agent·회의 어시스턴트의 실행 구조를 정의합니다. 회의 어시스턴트는 판단 기록(trace)과 검수·학습 데이터 형식까지 다루고, 측정값은 `*-evaluation.md`에 둡니다.

## Agent와 Tool

- Agent: 다음 행동을 스스로 계획·수정·평가하고 적절한 Tool과 Agent를 활용해 목적을 해결합니다.
- Main Agent: 전체 판단과 오케스트레이션을 담당합니다.
- Sub Agent: 위임받은 범위에서 어떤 Tool을 어떻게 사용할지 판단합니다. 독립적인 판단이 필요할 때 추가합니다.
- Tool: 정해진 입력과 수행 과정에 따라 실행합니다. 회계·계산은 Tool입니다.

기능 폴더나 그래프 노드 하나가 반드시 Agent 하나를 의미하지는 않습니다.

## 행사 Agent

행사계획 내부의 현재 개발 방향은 [행사계획 대화 Agent 초안](planning-agent-design.md)입니다. 사용자 발화·현재 초안·최근 대화를 읽은 LLM이 필요한 Tool과 답변을 선택하는 구조를 설계합니다. 기존 [단계별 설계](plan_architecture.md)는 legacy 참고입니다. 새 그래프는 미구현이며, 아래 전체 행사 Agent의 수명과 현재 공개 계약을 이미 변경한 것은 아닙니다. Tool의 초안 state 갱신은 BE 데이터 저장·확정과 구분합니다.

행사 하나를 행사 Agent 하나가 담당합니다. 행사 Agent는 계획을 시작할 때 만들어지고, 행사가 끝날 때까지 같은 실행 상태를 이어서 사용합니다. 필요할 때만 불려 한 번 실행하고 끝나는 함수가 아닙니다. 신호를 기다리다 깨어나 스스로 처리하고 다시 기다립니다.

| 단계 | 하는 일 |
| --- | --- |
| 대기 | 신호가 올 때까지 멈춰 있습니다 |
| 인식 | 받은 신호를 모으고 BE에서 행사의 최신 상태를 다시 읽습니다 |
| 계획 | 이번에 할 일을 정하거나 이전 계획을 수정합니다. 할 일이 없으면 보고로 넘어갑니다 |
| 실행 | 할 일을 하나씩 처리하며 필요한 Tool과 Sub Agent를 고릅니다 |
| 평가 | 결과를 검사하고, 부족하면 이유와 함께 계획으로 돌아갑니다. 반복 횟수는 제한합니다 |
| 보고 | 답변·제안·확인 요청·실행 기록을 BE에 전달하고 대기로 돌아갑니다 |

평가에서는 다음을 확인합니다.

- 금액·인원이 BE 계산 결과와 같은지
- 제시한 출처가 실제로 있는지
- 확인된 사실, 과거 기록, AI의 제안·가정, 확인하지 못한 내용이 구분되는지
- 같은 대상에 같은 행동을 이미 제안했거나 처리했는지
- `contracts.py`의 검증을 통과하는지

### 신호

BE는 행사 변화를 감지해 해당 행사 Agent에 신호로 전달합니다. 사용자 발화, 계획 생성·수정 요청, 운영 시작, 승인·거절, 확인 요청 답변, 참가 취소·입금 같은 변화, 마감·일정에 따른 시간 신호가 여기에 해당합니다. 시간 신호가 있으므로 사용자가 요청하지 않아도 Agent가 마감 전 미응답·미납 확인처럼 필요한 일을 먼저 살핍니다. 제공할 신호의 종류와 전달 시점은 BE와 합의합니다(D-07).

### 기다리는 곳과 사람의 판단

행사 Agent가 멈춰 기다리는 곳은 대기 단계 한 곳입니다. 운영진에게 묻는 확인 요청과 승인이 필요한 제안은 그래프 안에서 답을 기다리지 않고, BE의 Action으로 남긴 뒤 대기로 돌아갑니다. 운영진의 답과 승인·거절은 새 신호로 받습니다. 그래프 안에서 답을 기다리면 그사이 들어온 다른 신호를 그 답으로 잘못 받을 수 있고, 운영진이 결정을 미루는 동안 행사 Agent 전체가 멈춥니다.

행사 Agent는 BE 상태를 직접 바꾸지 않습니다. 쓰기 Tool은 제안·확인 요청 등록과 결과 전달로 한정하고, 발송·이체 같은 실행 Tool은 제공하지 않습니다.

행사의 기준은 BE 데이터입니다. 행사 Agent는 깨어날 때마다 최신 상태를 다시 읽고, 실행 체크포인트에는 할 일·제안 내역·요약 같은 작업 기록만 둡니다.

### 행사 단계와 그래프

행사 Agent의 실행 흐름은 행사 단계에 따라 planning과 operations로 나뉩니다. 대기·인식·보고는 두 단계가 함께 쓰고, 인식 단계에서 BE의 행사 상태를 읽어 해당 단계의 계획·실행·평가로 보냅니다.

| 행사 상태 | 단계 | 주로 받는 신호 | 주요 결과 |
| --- | --- | --- | --- |
| PLANNING | planning | 사용자 발화, 계획 생성·수정 요청 | 조건 정리·질문, 계획안 |
| ON_GOING | operations | 행사 변화, 승인·거절, 확인 요청 답변, 시간 신호 | 영향 설명, 대응안·확인 요청 |
| COMPLETE | 종료 | — | — |

계획 확정은 운영진과 BE가 합니다. BE가 행사를 운영 상태로 바꾸고 신호를 보내면 행사 Agent가 operations로 넘어갑니다. 같은 실행 상태를 이어서 사용하므로 계획 단계에서 둔 가정과 결정 이유를 운영 중에도 참고합니다. 운영 중 재계획은 planning으로 돌아가지 않고, operations에서 planning의 계획 생성 기능을 사용합니다.

### Agent 구성

| 구분 | 대상 | 기준 |
| --- | --- | --- |
| Main Agent | 행사 Agent | 행사 전체의 판단과 오케스트레이션 |
| Sub Agent | retrieval | 검색어 수정, 근거의 충분성, 자료 간 충돌을 스스로 판단 |
| 단계별 흐름 | planning, operations | 행사 단계에 따라 Main Agent가 사용하는 계획·실행·평가 흐름과 프롬프트·출력 형식 |
| Tool | 행사 조회, 회계·계산, 기록 검색 호출, 제안 등록 | 정해진 입력·출력에 따라 실행 |

기록 챗봇(AI-RET-01)은 대화를 저장하지 않으므로 행사 Agent에 넣지 않고, retrieval Sub Agent를 체크포인트 없이 실행합니다.

| 개념 | LangGraph |
| --- | --- |
| 행사 Agent 하나 | `thread_id` 하나 (예: `event:<event_id>`) |
| 대기 | `interrupt()` |
| 신호 전달 | `Command(resume=...)` |

재개하면 멈췄던 노드를 처음부터 다시 실행하므로 대기 단계에는 저장·호출 같은 부작용을 두지 않습니다.

## 회의 어시스턴트

대면 회의를 듣다가 기록 조회가 필요한 발화를 감지하면, 기록을 찾아 출처와 함께 화면에 띄웁니다(AI-MEET). 코드는 `features/meeting`에 둡니다.

```text
브라우저 마이크 → WebSocket → BE 음성 처리(VAD로 발화 구간 분할) → Whisper
  → AI: 문맥 관리 → 판단("이 발화에 기록 조회가 필요한가")
  → 필요하면 검색어 구성 → retrieval → 답변과 출처
  → BE가 화면으로 전송
```

```text
"작년 MT 때 숙소비 얼마 나왔지?"
  → 조회 필요 → 기록 검색
  → 화면에 "550,000원 (2025 봄 MT 결과보고 · 2쪽 · 2. 예산)"

"민수야 예약했어?"
  → 기록 밖의 일을 사람에게 묻는 말 → 아무것도 띄우지 않음
```

### 행사 Agent와 나누는 이유

회의와 행사는 수명이 다릅니다. 회의는 몇 초마다 들어오는 발화를 빠르게 처리하고 회의가 끝나면 함께 끝납니다. 행사 Agent는 행사가 끝날 때까지 같은 실행 상태를 이어 갑니다. 회의의 빠른 입력 처리를 행사 업무 처리와 섞지 않기 위해 회의 어시스턴트는 행사 Agent 밖에 두고 retrieval을 직접 호출합니다.

기록 챗봇(AI-RET-01)도 행사 Agent 밖에 있지만 이유가 다릅니다. 챗봇은 대화를 저장하지 않기 때문입니다. retrieval을 직접 호출한다는 점만 같습니다.

회의가 끝난 뒤 결정 사항을 행사 Agent에 신호로 넘기는 일은 아직 다루지 않습니다.

### 판단 질문과 처리기

기능 하나는 판단 질문 하나와 처리기 하나로 이루어집니다. 발화가 들어오면 등록된 판단 질문을 같은 문맥에 묻고, 통과한 질문의 처리기만 실행합니다. 기능을 더할 때는 판단 질문과 처리기를 하나씩 등록합니다.

| 판단 질문 | 뜻 | 상태 |
| --- | --- | --- |
| `record_lookup` | 동아리 기록으로 답할 수 있는 정보 요청이 있다 | 등록 |
| `decision_made` | 방금 무언가가 결정되었다 | 같은 틀로 추가 검토 |
| `action_item` | 누군가에게 할 일이 배정되었다 | 같은 틀로 추가 검토 |
| `record_reference` | 과거 기록을 비교 기준이나 참고 자료로 삼자는 말이 나왔다 | 같은 틀로 추가 검토 |

`record_lookup`은 구체적인 값을 묻는 말만 통과시킵니다. "2025년 가을 축제를 기준으로 비교하죠"처럼 문서 하나 전체가 답인 말을 같은 처리기에 넣으면, 값 하나로 답하는 구조라 답이 길고 모호해집니다. 이런 말은 `record_reference`로 나누고, 처리기는 답을 쓰지 않고 관련 문서 제목과 열기 링크만 띄우는 방향으로 검토합니다. 실제 회의에서 얼마나 자주 나오는지 판단 기록(#117)으로 확인한 뒤 정하고, 그때까지 평가 세트와 판단 기록에는 이런 발화를 따로 표시해 둡니다.

판단에서 조회가 필요 없다고 나온 발화도 문맥에는 남깁니다. 말 하나만으로는 판단할 수 없던 질문을 다음 발화와 함께 다시 판단하기 위해서입니다(AI-MEET-01).

### 판단 모델

판단은 `gpt-5.6-luna`로 하고, 실시간 호출은 추론을 끕니다(`reasoning={"effort": "none"}`). 실시간에는 조회 필요 여부와 검색어 두 값만 받습니다.

luna는 확정한 모델이 아니라 기준 시스템입니다. 실제로 돌아가는 것을 먼저 만들고, 그 과정에서 쌓인 판단을 사람이 검수해 학습 데이터로 씁니다. 목표는 Laya 같은 판단 전용 모델로 바꾸는 것입니다. 모델은 `AI_MODEL` 설정으로 받고, 프롬프트는 `features/meeting/prompts/judge.md` 원문과 `PROMPT_VERSION`으로 관리합니다. 원문을 고치면 버전을 올려야 테스트가 통과하고, 버전은 판단 기록에 남아 바뀌기 전후를 나눠 볼 수 있습니다.

판단 입력은 회의 날짜(발화 시각을 한국 시간으로 바꾼 날짜), 회의에 묶인 행사, 앞 발화 4개, 방금 발화입니다. 조회 여부(`route`), 무엇을 물었는지(`question`), 판단 기록(`trace`)은 모델이 아니라 코드가 채웁니다. 판단 호출은 10초를 넘기면 `AITimeoutError`로 "처리하지 못함"을 알립니다. 늦은 답도 띄우므로 빨리 끊으려는 값이 아니라 무한히 기다리지 않으려는 값이고, 측정에서 호출 100번 중 1번꼴로 5초를 넘겨 넉넉히 두었습니다.

바로 판단 전용 모델로 가지 않는 이유는 다음과 같습니다.

- **학습 데이터가 없습니다.** 판단 전용 모델은 학습 없이 쓰면 거의 맞히지 못합니다. Laya 공식 벤치마크에서 기본 모델이 0.35, 해당 과제로 학습한 모델이 0.766이었습니다. 회의 판단 평가 문항 110개에서도 학습 전 `laya-multilingual`은 균형 정확도 0.487, AUROC 0.475로 무작위와 같았고, luna는 0.980이었습니다.
- **배포 서버에 GPU가 없습니다.** Laya의 33ms는 T4 GPU 기준입니다. 노트북 CPU 2스레드에서는 p50 83ms였고 모델을 올리면 메모리가 약 1.2GB 늘었습니다. t3.medium에서 잰 값은 없습니다.
- **판단 전용 모델은 검색어를 만들지 못합니다.** 문장을 만들지 못하므로 검색어는 어차피 LLM 호출로 만들어야 합니다. 지금은 한 번의 호출로 판단과 검색어를 같이 받습니다. 그래서 판단과 검색어 구성을 인터페이스에서 나눠 두고, 판단만 바꿀 수 있게 합니다.
- **처리량·비용·안정성에서 유리하다는 것은 가설입니다.** 대부분의 발화는 조회가 필요 없어 호출이 쌓이고, 판단 질문이 늘수록 차이가 커질 것으로 봅니다. 다만 luna 판단은 1,000회에 약 ₩217로 비용 차이는 작습니다. 차이는 지연과 호출 수에서 나고, 배포 서버와 한국어 회의 데이터로 확인해야 합니다.

**luna를 쓰는 이유.** 20문항 × 3회에서 luna와 terra 모두 균형 정확도 1.000이었고 지연도 갈리지 않았습니다(p95 2.89초와 3.02초). 차이를 관찰하지 못했다는 뜻이지 같다는 증명은 아니므로, 구분되지 않는 동안은 작은 쪽을 씁니다.

**지연을 더 손보지 않는 이유.** 출력에서 판단 이유와 확신도를 빼서 p50을 2.22초에서 1.57초로 줄였습니다. 입력을 43% 줄이거나 응답 저장을 끄는 방법은 효과가 없거나 꼬리 지연이 나빠졌습니다. 몇 토큰만 주고받는 최소 호출도 p50 1.11초여서, 호출 한 번의 바닥이 약 1.1초로 관측됐습니다. 호출을 없애지 않는 한 이 시간은 남으므로 판단을 로컬 모델로 옮길 근거로 둡니다. 이 값은 노트북에서 인터넷을 거쳐 잰 것이라 배포 서버에서 다시 잽니다.

판단 전용 모델로 바꾸는 기준과 학습 데이터를 모으는 방법은 [판단 전용 모델로 바꾸는 계획](#판단-전용-모델로-바꾸는-계획-117)에 있습니다. 학습 전후는 회의 판단 평가 문항 110개로 비교하므로 이 문항은 학습 데이터에 넣지 않습니다.

### 판단 기록과 검수

luna의 판단은 정답이 아니라 정답 후보입니다. 판단 전용 모델이 luna의 실수까지 배우지 않도록 정답은 사람이 정합니다(#117).

```text
회의 중   AI가 판단 결과와 판단 기록(trace)을 돌려주고 BE가 저장합니다. 실패한 판단도 저장합니다
회의 뒤   사람이 판단을 골라 정답을 붙입니다 → 검수 기록(JudgeReview)
이후      검수 기록을 판단 전용 모델의 학습 데이터로 씁니다
```

검수 기록은 BE의 판단 기록에 넣지 않고, 그 id를 가리키는 별도 기록으로 둡니다. 제품 화면이 쓰는 값이 아니라 학습 데이터이기 때문입니다. 저장 위치는 BE와 정합니다.

| 칸 | 뜻 |
| --- | --- |
| `label` | 사람이 정한 정답(`RAG`·`NONE`). 둘 다 허용이어도 더 가깝다고 본 쪽을 고릅니다 |
| `reason_code` | `NONE`일 때 조회하지 않은 이유. 판단 프롬프트의 "조회가 필요 없는 경우"와 하나씩 맞춘 코드입니다(`ReasonCode`) |
| `either` | 조회해도 되고 안 해도 되는 말(둘 다 허용)인지. 학습 파일을 만들 때는 이 값이 `label`보다 앞섭니다([5단계](#5-둘-다-허용인-말)) |
| `direct_request` | AI에게 무언가를 시킨 말인지(#124). 묻지 않았으면 `null`입니다 |
| `blind` | 모델 판단을 가리고 붙였는지. 가린 라벨과 보여준 라벨이 자주 다르면 검수가 모델 답에 끌려간다는 뜻입니다 |
| `schema_version` | 형식 버전. 지금은 2입니다. 칸을 바꾸면 올리고, 이전 버전 기록도 읽습니다 |

둘 다 허용인 말에도 `label`을 받는 것은 평가 세트와 같은 방식입니다. 학습 파일을 만드는 방식을 나중에 바꿔도 다시 검수하지 않아도 되고, `REFERENCE_MATERIAL`이 붙은 발화 수로 `record_reference`를 만들지 정할 수 있습니다.

버전 1 기록은 버전 2로 바꿔 읽습니다. 버전 1에는 둘 다 허용을 고르는 칸이 없었으므로 `either`는 false로 읽고 `label`을 그대로 씁니다. AI에게 시킨 말인지는 묻지 않았으므로 `direct_request`는 false가 아니라 `null`입니다. false로 채우면 "시킨 말이 아니다"라고 확인한 것처럼 보입니다.

```text
버전 1  {"label": "NONE", "reason_code": "REFERENCE_MATERIAL", ..., "schema_version": 1}
읽은 값  {"label": "NONE", "reason_code": "REFERENCE_MATERIAL", "either": false, "direct_request": null, ..., "schema_version": 2}
```

경계 사례는 두 명 이상이 보므로 판단 하나에 검수 기록이 여러 개 붙을 수 있습니다.

판단 전용 모델은 luna의 긴 지시문 대신 짧은 판단 질문과 양쪽 설명을 입력과 함께 읽습니다. 학습할 때와 판단할 때 같은 문구여야 하므로 `features/meeting/questions.py` 한 곳에 두고 `QUESTIONS_VERSION`을 붙입니다. 기준은 판단 프롬프트와 같게 줄여 씁니다.

```json
"record_lookup": {
  "type": "noul",
  "instructions": "방금 발화에 동아리의 과거 기록(회칙·장부·행사 보고서)을 찾아봐야 답할 수 있는 과거 금액·인원·일정·규정 질문이 있나요? …",
  "criteria": {"false": "기록을 찾아봐야 답할 질문이 없음", "true": "기록을 찾아봐야 답할 질문이 있음"}
}
```

- **설명 문구도 판단 기준입니다.** Laya는 문구만 바꿔도 같은 입력의 확률이 달라집니다. 그래서 양쪽을 같은 무게로 쓰고, 문구를 바꾸면 버전을 올려 이전 학습 데이터와 섞지 않습니다.
- **양쪽 설명을 비우지 않습니다.** 비우면 영어 기본 문구("no, the statement does not hold")가 한국어 입력 사이에 들어갑니다.

검수한 판단은 `features/meeting/training.py`의 `export_training_lines`로 Laya 학습 파일(JSONL) 줄로 바꿉니다. `state`는 그때 luna가 본 입력 글을 같은 함수(`build_judge_input`)로 다시 만든 것이고, 정답은 검수 기록에서만 만듭니다.

검수자 한 명은 표 하나를 냅니다. `either`가 true면 둘 다 허용, 아니면 `label`입니다. 표가 가장 많은 쪽으로 정합니다.

| 경우 | 줄 |
| --- | --- |
| 한 명이 검수했거나 모두 같은 표 | 조회·아님이면 `expected`만. 둘 다 허용이면 내보내지 않습니다(`either`) |
| 의견이 갈렸고 조회나 아님이 가장 많음 (예: NONE 2, RAG 1) | 가장 많은 쪽을 `expected`로, 비율을 `gold`로 (`false` 0.6667, `true` 0.3333) |
| 둘 다 허용이 가장 많음 (예: 둘 다 허용 2, RAG 1) | 내보내지 않습니다(`either`) |
| 가장 많은 쪽이 둘 (예: RAG 1, NONE 1 / 둘 다 허용 1, RAG 1) | 내보내지 않고 `needs_review`로 돌려줍니다. 한 명이 더 봅니다 |
| 셋이 같은 수 (예: RAG 1, NONE 1, 둘 다 허용 1) | 내보내지 않습니다(`three_way`). 세 사람이 모두 다르게 본 말이라 한 명이 더 봐도 정해지기 어렵습니다 |
| 검수 기록 없음 | 내보내지 않습니다(`unreviewed`) |
| 같은 사람이 다시 검수 | 마지막 검수만 씁니다 |
| 입력 글이 같은 판단 | 한 줄로 합치고 검수도 합칩니다. 같은 줄이 두 번 들어가면 그 판단만 두 배로 배웁니다 |

`gold`의 비율은 조회와 아님 표로만 셉니다. RAG 2, NONE 1, 둘 다 허용 1이면 `true` 0.6667, `false` 0.3333입니다. 둘 다 허용 표를 0.5씩 나눠 넣으면 5단계에서 고르지 않은 "확률 0.5 / 0.5로 넣기"가 들어오게 됩니다.

AI는 검수 표를 던지지 않습니다. 다른 모델의 판단은 사람이 검수할 발화를 고르는 데만 씁니다(#117 2단계). 회의 뒤 `gpt-6-luna`로 다시 판단해 실시간 판단과 갈린 발화를 고르고, 갈리지 않은 발화도 무작위로 일부 고릅니다. 평가 세트에서 실시간 판단의 오답 14건 중 6건이 갈린 발화 12건 안에 들었고, Haiku보다 검수량은 적고 잡은 오답은 많았습니다. 모든 모델이 같이 틀린 오답도 5건 있어서 무작위로도 고릅니다([측정 기록](meeting-evaluation.md#2026-10-20--회의-뒤-다시-판단할-모델-117)). 학습은 공식 `laya-train`으로 `multilingual`에서 시작하고, 먼저 `--dry-run`으로 빠지는 줄을 확인합니다. 측정 문항 110개에 반반 검수·검수 없음 같은 경우를 시험하는 판단을 더해 112개를 이 함수로 내보내자, 의도대로 3개가 빠지고(반반 1, 검수 없음 1, 같은 입력 합침 1) 109줄이 나왔습니다. 이 109줄은 laya 0.4.7 `--dry-run`에서 빠진 줄 없이 모두 읽혔습니다. 입력 글은 길어야 148토큰, 질문과 설명은 143토큰으로 한도(1024, 질문 256) 안입니다.

### 판단 전용 모델로 바꾸는 계획 (#117)

실시간 판단을 luna에서 Laya 같은 판단 전용 모델로 바꾸려면 학습이 필요하고, 학습에는 사람이 정답을 붙인 발화가 필요합니다. 학습 전 Laya는 무작위와 같은 수준이었습니다([측정 기록](meeting-evaluation.md#2026-10-19--학습-전-laya와-luna-117)). 이 절은 무엇을 넘으면 바꾸는지와 학습 데이터를 어떻게 모으는지를 정합니다.

바꾸는 목적은 조회가 필요 없는 발화의 LLM 호출을 없애는 것입니다. 회의 발화는 대부분 조회가 필요 없는데, 지금은 발화마다 luna를 부릅니다. Laya로 바꾸면 Laya가 조회로 본 발화에만 검색어를 받으러 LLM을 부릅니다. 조회할 발화의 지연은 줄지 않습니다([1단계](#1-바꾸는-기준)).

```text
회의 하나 (발화 300개, 조회 필요 5%라고 가정)
지금      luna 300번                         판단 비용 약 ₩68
Laya 뒤   검색어 호출 약 46번 (조회 15 + 오탐 약 31, 오개입률 10.8로 가정)   약 ₩7
```

비용은 회의 하나에 수십 원이라 크지 않습니다. 호출 수가 줄면 게이트웨이 지연·오류에 걸리는 발화가 함께 줄고, 판단 질문을 더해도(#124) 호출이 늘지 않습니다.

| 단계 | 정할 것 | 상태 |
| --- | --- | --- |
| 1 | 바꾸는 기준 | 정함 |
| 2 | 학습 데이터의 출처와 양, 검수 방식 | 정함 |
| 3 | 실제 회의에서 사람이 검수할 발화 고르기 | 정함 |
| 4 | 학습 데이터가 어려운 말로 쏠리지 않게 하기 | 정함 |
| 5 | 둘 다 허용인 말을 학습에서 다루는 법 | 정함 |
| 6 | 학습 데이터가 평가 문항과 겹치지 않게 막기 | 정함 |
| 7 | 학습·측정·보관과 작업 순서 | 정함 |

이 절에서 쓰는 용어입니다.

| 용어 | 뜻 |
| --- | --- |
| 학습 | 정답이 붙은 예시를 모델에 보여 주며 모델의 값을 고쳐, 비슷한 입력에 정답을 내도록 만드는 일입니다 |
| 라벨 | 발화마다 사람이 붙인 정답입니다. 여기서는 조회 필요(`RAG`), 조회 아님(`NONE`), 둘 다 허용입니다 |
| 둘 다 허용 | 조회해도 되고 안 해도 되는 말입니다. 채점하지 않습니다 |
| 경계 사례 | 사람끼리도 라벨이 갈리기 쉬운 말입니다. 예: "작년엔 2만 원이었잖아요 그거 보고 정하죠" |
| 개발용·홀드아웃 | 평가 문항을 둘로 나눈 것입니다. 개발용은 고치면서 계속 보는 문항, 홀드아웃은 고치는 동안 보지 않고 결정할 때만 재는 문항입니다 |
| 놓침·오탐 | 놓침은 조회해야 할 말에 카드를 띄우지 않은 것, 오탐은 조회가 필요 없는 말에 카드를 띄운 것입니다 |
| 재현율 | 조회가 필요한 말 중 카드를 띄운 비율입니다. 놓침이 없으면 1입니다 |
| 정밀도 | 띄운 카드 중 실제로 조회가 필요했던 비율입니다. 조회가 드문 회의일수록 낮아집니다 |
| 오개입률 | 조회가 필요 없는 말 100개당 카드를 띄운 수입니다. 문항의 조회 비율과 관계없이 비교할 수 있습니다 |
| 조회 확률·임계값 | Laya는 발화마다 조회가 필요할 확률(0~1)을 냅니다. 임계값은 이 확률이 몇 이상이면 조회로 볼지 정한 값이고, 기본은 0.5입니다 |
| AUROC | 조회가 필요한 말에 조회 아닌 말보다 높은 확률을 줬는지 보는 값입니다. 임계값과 관계없이 순서만 봅니다. 1이면 모든 조회 필요 발화가 위에 있고, 0.5면 무작위입니다 |
| 오즈 | 확률을 "일어날 확률 ÷ 안 일어날 확률"로 바꾼 값입니다. 확률 0.2는 오즈 0.25(1 대 4)입니다 |
| 확률 보정·ECE | 확률 보정은 모델이 낸 확률이 실제 비율과 맞게 고치는 일입니다. ECE는 맞는 정도를 잰 값으로, "조회 확률 0.9"라고 한 발화 100개 중 실제 조회가 90개 안팎이면 0에 가깝습니다 |
| 에포크·갱신 | 에포크는 학습 데이터 전체를 한 번 다 보는 것, 갱신은 데이터 몇 건을 보고 모델의 값을 한 번 고치는 것입니다 |
| 시드 | 학습 순서처럼 무작위로 정하는 값의 시작점입니다. 시드를 바꾸면 같은 데이터로도 결과가 조금 달라지므로 여러 시드로 학습해 우연을 가립니다 |
| 체크포인트 | 학습을 마친 모델의 값을 저장한 파일입니다 |
| 임베딩·코사인 비슷도 | 임베딩은 문장의 뜻을 숫자 목록으로 바꾼 것입니다. 코사인 비슷도는 두 임베딩이 얼마나 같은 방향인지로, 뜻이 가까울수록 1에 가깝습니다 |

#### 1. 바꾸는 기준

바꿀지는 [회의 판단 평가 세트](../tests/fixtures/eval/README.md#회의-판단-평가-세트)의 홀드아웃으로 정합니다. 평가 세트 200건은 회의 단위로 개발용 151건과 홀드아웃 49건으로 나뉩니다. 개발용은 프롬프트나 모델을 고치면서 계속 돌려 보는 문항이고, 홀드아웃은 고치는 동안 보지 않고 결정할 때만 재는 문항입니다. 고치면서 본 문항의 점수는 그 문항에 맞춘 결과라 실제보다 좋게 나옵니다. 10-14에 72발화를 보며 프롬프트를 고쳐 오탐이 16건에서 1건으로 줄었을 때도, 실제로 나아졌는지는 고칠 때 보지 않은 26발화로 따로 확인했습니다.

홀드아웃 49건은 조회 필요 9건, 조회 아님 37건, 둘 다 허용 3건(채점하지 않음)입니다. luna는 조회 필요 9건을 모두 잡았고, 조회 아님 37건 중 4건에 카드를 띄웠습니다.

| 기준 | luna (홀드아웃) | Laya가 넘어야 할 선 |
| --- | --- | --- |
| 놓침: 조회해야 할 말에 아무것도 띄우지 않음 | 0 / 9 | luna가 잡은 발화를 하나도 놓치지 않음 |
| 오개입률: 조회 아닌 말 100개당 띄운 카드 수 | 10.8 (4 / 37) | 약 16 이하. 지금 홀드아웃에서는 37개 중 6건(16.2)까지로, luna보다 2건 더 허용 |
| 반복 | — | 시드를 바꿔 세 번 학습해 셋 다 위 두 기준을 넘음 |
| 조회 경로 지연 | 같은 측정에서 잰 판단 p95 (10-20: 3.55초) | Laya 판단 p95와 검색어만 만드는 호출 p95의 합이, 같은 측정에서 번갈아 잰 지금 판단 p95보다 0.2초 넘게 늘지 않음 |

- luna가 잘못 띄운 4건은 "오늘 합주 몇 시였지?"(지금 일), "한 스무 명 그중에 남은 건 열 명 정도."(사람이 답한 말) 같은 말입니다. 오개입률 10.8은 조회가 필요 없는 말 100마디마다 쓸데없는 카드가 약 11장 뜬다는 뜻입니다.
- 놓침을 오탐보다 엄격하게 봅니다. 놓치면 아무것도 뜨지 않아 사용자가 알 수 없지만, 잘못 띄운 카드는 닫으면 됩니다(AI-MEET-05).
- 지연은 조회 경로로 봅니다. Laya는 검색어를 만들지 못하므로 조회할 때는 LLM 호출이 남습니다. 조회 아닌 발화는 호출이 없어지지만 화면에 띄우는 것이 없어 사용자가 느끼는 차이가 없습니다. 검색어만 만드는 호출은 지금 판단 호출과 번갈아 쟀을 때 p50이 1.74초와 1.78초로 같았습니다([측정 기록](meeting-evaluation.md#2026-10-20--검색어만-받는-호출의-지연-117)). 그래서 조회 경로의 지연은 Laya로 바꿔도 줄지 않고 Laya 판단 시간(노트북 CPU p95 약 0.09초)만큼 늘어납니다.
- 지연 기준은 고정된 초가 아니라 같은 측정에서 번갈아 잰 지금 판단과 견줍니다. 게이트웨이 지연은 날마다 달라 같은 판단 호출의 p95가 2.38초(평가 세트 기준선)와 3.55초(10-20 검색어 측정)로 나왔습니다. 고정된 값으로 두면 느린 날은 Laya와 관계없이 넘고, 빠른 날은 늘어난 시간을 가리지 못합니다. 0.2초는 Laya 판단 시간(약 0.09초)에 여유를 둔 값이고, 배포 서버에서 Laya를 재면 다시 정합니다.
- ECE와 둘 다 허용에서 조회한 비율은 기록만 하고 기준에 넣지 않습니다. ECE는 확률이 맞는지 보는 값입니다. "조회 확률 0.9"라고 한 발화 100개 중 실제 조회가 90개 안팎이면 잘 맞은 것입니다. 홀드아웃 46건으로는 이 값을 믿기 어렵습니다.

**홀드아웃을 키웁니다.** 조회 필요가 9건이라 1건만 놓쳐도 재현율이 1.000에서 0.889로 떨어지고, 9건을 다 맞혀도 우연인지 가리기 어렵습니다. 30건이면 1건 차이가 0.033입니다. 학습에 쓰지 않을 합성 대본으로 조회 필요를 30건 이상 더하고, 동의받은 실제 회의 녹음이 생기면 더합니다. 새 대본은 학습 대본과 겹치지 않게 씁니다.

- 회의의 주제와 형식을 다르게 합니다. 학습 대본이 행사 준비 회의 중심이면, 홀드아웃에는 결정 사항을 브리핑하는 회의나 정산 보고 회의를 넣습니다.
- 가능하면 학습 대본과 다른 모델로 씁니다. 같은 모델이 쓴 글로 학습하고 재면, Laya가 판단 기준이 아니라 그 모델의 말투를 배워도 점수가 오릅니다.
- 라벨은 평가 세트처럼 AI 초안을 가리고 붙입니다.

#### 2. 학습 데이터의 출처와 양

지금 학습에 쓸 수 있는 데이터는 없습니다. 회의 판단 평가 문항 110개와 평가 세트 200건은 학습에 넣지 않습니다.

| 출처 | 만드는 방법 | 쓰는 때 |
| --- | --- | --- |
| 합성 대본 | AI가 회의 대본을 쓰고, 절반은 TTS로 읽혀 Whisper를 거친 뒤 사람이 검수합니다 | 지금부터 |
| 실제 회의 판단 기록 | 회의 뒤 다시 판단해 고른 발화를 사람이 검수합니다([판단 기록과 검수](#판단-기록과-검수)) | 판단 기록 저장과 참석자 동의가 생기면 섞습니다 |
| 공개 한국어 회의 데이터 | 전사문에 사람이 라벨을 붙입니다 | 실제 말투가 부족할 때 이용 조건을 확인하고 검토합니다 |

첫 목표는 합성 1,000건이고 조회 필요는 약 25%입니다. 한 번에 다 쓰지 않고 250·500·1,000건으로 나눠 학습해, 데이터가 늘수록 나아지는지 봅니다. 500건과 1,000건의 결과가 비슷하면 양이 아니라 라벨이나 판단 질문 문구를 봐야 합니다.

수백 건이 아니라 1,000건부터 잡는 것은 학습 갱신 횟수 때문입니다. 학습은 데이터를 64건씩 묶어 보고 모델을 한 번 고치는 일(갱신)을 되풀이합니다. 데이터 전체를 한 바퀴 보는 것을 에포크라 하고 기본은 4바퀴입니다. `laya-train`은 확률 보정에 쓸 줄을 일부 떼어 두고 나머지로 학습합니다.

```text
갱신 수 = 4바퀴 × (학습 줄 수 ÷ 64, 올림)

109줄 (형식 확인)   학습 99줄    → 한 바퀴 2번  × 4 = 8번
1,000줄            학습 약 900줄 → 한 바퀴 15번 × 4 = 60번   (10%를 떼어 둔다고 가정)
6,000줄 (공식 예시) 학습 5,600줄  → 한 바퀴 88번 × 4 = 352번
```

8번으로는 모델이 거의 바뀌지 않습니다. 352번은 넘어야 할 선이 아니라 공식 예시의 값이고, 데이터가 적으면 바퀴 수를 늘리는 방법도 있습니다.

검수는 AI가 붙인 라벨 초안을 사람이 보고 확인하거나 고칩니다. 1,000건을 모두 가리고 붙이면 평가 세트 속도(200건에 1시간 안쪽)로 약 5시간이 걸리기 때문입니다. 대신 10%는 초안을 가리고 붙여 두 쪽을 비교합니다. 가리고 붙인 라벨과 보고 붙인 라벨이 자주 다르면 검수가 초안에 끌려간다는 뜻입니다(`JudgeReview.blind`). 정답은 사람이 정하고, 모델의 판단은 정답으로 쓰지 않습니다.

#### 3. 실제 회의에서 검수할 발화

실제 회의의 판단을 모두 검수할 수는 없으므로, 회의 뒤 `gpt-6-luna`로 다시 판단해 실시간 판단과 비교한 뒤 세 묶음으로 나눠 고릅니다([판단 기록과 검수](#판단-기록과-검수)).

| 묶음 | 고르는 양 | 이유 |
| --- | --- | --- |
| 갈림 | 전부 | 실시간 판단의 오답이 몰려 있습니다 |
| 둘 다 조회 | 전부 | 두 모델이 같이 틀린 오답이 여기 있습니다. 실제로 화면에 뜬 카드이고 수가 적습니다 |
| 둘 다 아님 | 무작위 15% | 두 모델이 같이 놓친 조회를 찾고, 회의에 흔한 평범한 말을 학습 데이터에 넣습니다 |

평가 세트 200건으로 나눠 보면 이렇습니다. 실시간 판단의 오답 14건 중 갈리지 않은 8건은 모두 둘 다 조회에 있었습니다. "가을 MT 신청 지금 몇 명 했어요?"(지금 일), "그 뭐지 지난번에 말한 그거 얼마였지?"(대상을 모름)처럼 두 모델이 같이 쓸데없는 카드를 띄운 말입니다.

| 묶음 | 발화 | 실시간 판단 오답 |
| --- | --- | --- |
| 갈림 | 12 | 6 |
| 둘 다 조회 | 47 | 8 |
| 둘 다 아님 | 141 | 0 |

둘 다 아님에서 오답이 나오지 않았어도 계속 일부를 봅니다. 여기서 나오는 오답은 두 모델이 모두 놓친 조회라 가장 손해가 큽니다. 평가 세트는 조회 필요를 20%로 맞춰 썼으므로, 실제 회의의 묶음별 비율과 검수량은 판단 기록이 쌓인 뒤 다시 셉니다.

```text
회의 하나 (발화 300개라고 가정)
  갈림         약 18개 → 전부
  둘 다 조회   예: 15개 → 전부
  둘 다 아님   약 267개 → 15% 무작위, 40개
  = 약 73개. 평가 세트 검수 속도(200건에 1시간 안쪽)로 약 20분
```

무작위로 고른 발화에 사람이 붙인 라벨이 두 모델과 모두 다르면 두 번째 검수자가 한 번 더 봅니다. 두 모델이 같이 틀렸거나 검수 실수일 수 있습니다. 두 모델이 같이 틀린 것이 맞다면 가장 값진 학습 데이터입니다.

#### 4. 학습 데이터의 쏠림

3단계처럼 고르면 학습에 들어가는 발화의 비율이 실제 회의와 달라집니다. 합성 대본도 조회 필요를 25%로 넣으므로 실제보다 높을 가능성이 큽니다. 아래는 실제 회의의 조회 필요를 5%로 가정한 예입니다. 실제 비율은 아직 모릅니다.

```text
                실제 회의 300발화    고른 73발화 (학습에 들어감)
갈림              18 (6%)       →    18 (25%)
둘 다 조회        15 (5%)       →    15 (21%)
둘 다 아님       267 (89%)      →    40 (55%)
조회 필요 비율    약 5%         →    약 30%
```

조회가 25%인 데이터로 배운 Laya는 조회가 5%인 회의의 말을 조회 쪽으로 기울여 봅니다. 두 비율의 차이만큼 조회 쪽 오즈가 약 6.3배가 되므로, 실제 회의 기준으로 조회 확률 0.15인 평범한 말이 약 0.53이 되어 임계값 0.5를 넘습니다. 일반 대화에도 카드가 뜨는 쪽으로 기운다는 뜻입니다.

- **학습 파일의 조회 필요 비율은 25% 안팎으로 맞춥니다.** 실제 기록에서 고른 줄을 섞다가 비율이 올라가면 평범한 말(둘 다 아님 표본, 합성)을 더 넣습니다. 어려운 사례는 경계를 배우는 데 필요하므로 빼지 않습니다. 같은 줄을 복제해 비율을 맞추지는 않습니다. 같은 문장을 외우게 되고, 학습 파일을 만드는 함수도 같은 입력을 하나로 합칩니다. 학습 파일을 만드는 스크립트(`scripts/make_laya_training.py`)가 조회 비율과 25%에 맞추려면 더 넣어야 할 줄 수를 알려 줍니다. 비율을 맞추는 일은 사람이 대본을 더 써서 합니다.
- **기운 만큼은 임계값으로 바로잡습니다.** 임계값은 0.5에서 시작하고, 오탐이 많으면 개발용 151건에서 다시 고릅니다. 홀드아웃은 고른 값을 확인하는 데만 씁니다. 조회 비율만 다를 때는 임계값을 옮기는 것이 비율을 맞추는 것과 같습니다. 위 예라면 25%로 배운 Laya의 0.86이 실제 회의 비율의 0.5에 해당합니다. 실제 비율은 판단 기록이 쌓이면 둘 다 아님 15% 표본과 전부 검수한 묶음으로 추정합니다.
- **줄마다 가중치를 주는 방법은 나중에 검토합니다.** `laya-train`(0.4.7)에는 가중치 옵션이 없고, 손실을 묶음 평균으로 계산합니다. 가중치를 넣으려면 학습 코드와 확률 보정 코드를 고쳐 따로 관리해야 합니다. 임계값으로 바로잡히지 않는 경우에 검토합니다. 개발용에서 아래처럼 나누어 봅니다.

  | 개발용에서 보이는 것 | 원인 | 처리 |
  | --- | --- | --- |
  | AUROC는 높은데 오탐이 많음 | 순서는 맞고 확률만 전체적으로 높음. 조회 비율 차이 때문입니다 | 임계값을 올립니다 |
  | 임계값을 올리면 놓침이 생기고 내리면 오개입률이 기준을 넘음. 오답이 "아 다리 아파" 같은 평범한 말에 몰림 | 평범한 말에 조회 말보다 높은 확률을 주는 등 순서가 틀림. 어려운 사례가 많아 평범한 말을 덜 배웠을 수 있습니다 | 평범한 말을 더 넣고, 그래도 안 되면 가중치를 넣도록 학습 코드를 고칩니다 |

**정밀도는 조회 비율에 따라 달라집니다.** 정밀도는 띄운 카드 중 실제로 조회가 필요했던 비율이고, 재현율은 조회가 필요한 말 중 카드를 띄운 비율입니다. 재현율과 오개입률은 문항의 조회 비율과 관계없이 비교할 수 있지만, 정밀도는 조회가 드물수록 낮아집니다.

```text
luna (재현율 1.000, 오개입률 10.8)
  평가 세트 홀드아웃 (조회 약 20%)   카드 13장 중 9장이 필요한 카드   정밀도 0.69
  조회 5%인 회의 300발화 (가정)       카드 약 46장 중 15장            정밀도 약 0.33
  같은 회의에서 오개입률 16이면       카드 약 61장 중 15장            정밀도 약 0.25
```

그래서 교체 기준은 오개입률로 두고, 정밀도는 실제 회의의 조회 비율이 나오면 그 비율로 환산해 함께 기록합니다. 환산한 정밀도가 너무 낮으면 오개입률 상한(16)을 다시 정합니다.

#### 5. 둘 다 허용인 말

"음향 업체는 작년이랑 같은 데로 가죠", "작년 자료 같이 보면서 짜요"처럼 조회해도 되고 안 해도 되는 말은 평가에서 채점하지 않습니다([라벨 기준](../tests/fixtures/eval/README.md#라벨-기준)). 평가 세트 200건 중 13건이었습니다.

**학습 파일에서도 뺍니다.** 채점하지 않는 말에 정답을 가르치면 판단의 경계가 정하지 않은 쪽으로 움직입니다. 다른 안은 이래서 고르지 않았습니다.

| 안 | 고르지 않은 이유 |
| --- | --- |
| 확률 0.5 / 0.5로 넣기 | 임계값을 올리면(4단계) 사실상 늘 조회 아님이 되고 확률 보정이 흔들립니다 |
| 검수자가 고른 쪽 그대로 | 평가 세트에서 비슷한 말이 조회 4건, 아님 9건으로 갈렸습니다. 같은 말에 다른 정답을 가르칩니다 |
| 모두 조회로 통일 | 일반 대화 쪽 오탐이 더 늘 수 있습니다(4단계) |

Laya가 이런 말에서 어떻게 판단하는지는 평가 세트의 "둘 다 허용에서 조회한 비율"로 계속 봅니다.

**검수 기록에 둘 다 허용을 남깁니다.** 라벨이 `RAG`·`NONE` 둘뿐이면 둘 다 허용인 말도 한쪽 정답으로 학습에 들어갑니다. 그래서 검수 화면에 "둘 다 괜찮음"을 두고 검수 기록에 `either` 칸을 둡니다(형식 버전 2). 평가 세트처럼 더 가깝다고 본 쪽(`label`)도 함께 받으므로, 학습 파일을 만드는 방식을 나중에 바꿔도 다시 검수하지 않아도 됩니다. 검수자끼리 갈렸을 때 어떻게 정하는지는 [판단 기록과 검수](#판단-기록과-검수)의 표에 있습니다.

같은 형식 버전 2에 "AI에게 시킨 말"(`direct_request`) 칸도 있습니다. 이유와 정의는 [판단 질문을 더할 때](#판단-질문을-더할-때-124)에 있습니다.

#### 6. 평가 문항과 겹침

학습에 넣은 문장과 같거나 거의 같은 문장이 평가에도 있으면, Laya는 판단 기준을 배우지 않고 문장을 외워도 맞힙니다. 그러면 학습 뒤 점수가 실제보다 좋게 나와 교체 결정이 틀어집니다.

`laya-train --eval`에 평가 파일을 주면 겹침을 알려 주지만, 입력 글 전체가 글자까지 같을 때만 잡습니다. 입력 글에는 회의 날짜와 앞 발화 4개가 함께 들어가므로, 같은 문장이라도 앞 대화가 다르면 겹침으로 보지 않습니다.

```text
평가 세트  [최근 대화] 그럼 공연 얘기...   [방금] 작년에 재료비로 얼마 썼더라?
학습 대본  [최근 대화] 축제 준비하면서...  [방금] 작년에 재료비로 얼마 썼더라?
→ laya-train은 겹침으로 보지 않지만, Laya는 방금 발화를 외워 맞힐 수 있습니다
```

그래서 방금 발화끼리 따로 비교합니다. 무엇으로 비교할지 정하려고 몇 쌍을 쟀습니다(2026-10-20, `text-embedding-3-small`).

| 평가 문장 | 비교 문장 | 관계 | 글자 2개씩 비슷도 | 임베딩 코사인 |
| --- | --- | --- | --- | --- |
| 작년에 재료비로 얼마 썼더라? | 작년에 재료비 얼마 썼었지? | 거의 같은 말 | 0.50 | 0.977 |
| 작년 정기공연 대관료 얼마 냈었는지 기억나는 사람? | 작년 정기공연 대관료 얼마였는지 아는 사람? | 거의 같은 말 | 0.54 | 0.884 |
| 오늘 합주 몇 시였지? | 오늘 합주 몇 시에 하지? | 거의 같은 말 | | 0.959 |
| 작년에 재료비로 얼마 썼더라? | 작년에 간식비로 얼마 썼더라? | 대상이 다름 | 0.57 | 0.677 |
| 작년 정기공연 대관료 얼마 냈었는지 기억나는 사람? | 작년 체육대회 참가비 얼마 냈었는지 기억나는 사람? | 대상이 다름 | 0.43 | 0.729 |
| 작년에 재료비로 얼마 썼더라? | 재료비 작년에 얼마 썼더라? | 낱말 순서만 바뀜 | 0.62 | 0.733 |

글자 비슷도는 거의 같은 말(0.50)보다 대상이 다른 말(0.57)을 더 높게 쳐서 쓰지 않습니다. 임베딩은 거의 같은 말이 0.88~0.98, 대상이 다른 말이 0.61~0.73으로 나뉘었습니다. 대상이 다른 말은 겹침이 아닙니다. 같은 말투로 다른 대상을 묻는 것은 Laya가 배워야 할 판단이고, 이것까지 막으면 조회 질문 대부분이 학습에서 빠집니다.

- **쓸 때 막습니다.** 대본을 쓰는 모델에 평가 문항을 보여 주지 않습니다. 새 홀드아웃은 주제와 형식을 다르게 씁니다(1단계).
- **학습 파일을 만들 때 검사합니다.** 학습 문장마다 평가 문항 110개, 평가 세트 200건, 새 홀드아웃의 문장과 견줍니다. 평가 쪽은 대본(`spoken`)과 판단에 넣은 글(`heard`)을 모두 씁니다. 공백과 문장부호를 뺀 글자가 같거나 임베딩 코사인이 0.85 이상이면 겹침입니다. 검사는 `scripts/make_laya_training.py`가 하고, 학습 줄로 바꾸기 전에 판단 단위로 뺍니다. 어느 판단이 어느 평가 문항과 겹쳤는지 남기기 위해서입니다.
- **비교는 학습 문장과 평가 쪽 문장 사이에서만 합니다.** 학습 문장끼리는 비교하지 않습니다. 학습 데이터 안에서 비슷한 말이 되풀이되는 것은 점수를 부풀리지 않고, 입력 글이 같은 줄은 학습 파일을 만드는 함수가 하나로 합칩니다. 평가 쪽 문장(약 460개)의 임베딩은 한 번 만들어 저장해 두고, 새로 쓴 학습 문장만 임베딩합니다. 학습 1,000문장이면 46만 쌍이고, 노트북에서 순수 파이썬으로 약 15초, numpy로 0.01초가 걸렸습니다. 스크립트는 BE 의존성에 numpy가 없어 순수 파이썬으로 계산하고, 1,000문장 × 448문장이 약 6초였습니다.
- **걸린 문장은 학습에서 빼고 수를 기록합니다.** 다시 쓰면 다시 쓴 문장도 다시 검사해야 합니다. 걸린 비율이 5%를 넘으면 대본을 쓰는 방식을 점검합니다.
- **짧은 말은 검사하지 않습니다.** 공백과 문장부호를 빼고 6자 이하인 "네 맞아요" 같은 맞장구와 진행 말은 어느 회의에나 나옵니다. 이런 말을 빼면 4단계에서 필요하다고 한 평범한 말이 줄어듭니다.
- **입력 글 전체가 같은 것도 잡습니다.** 짧은 말이라도 앞 발화와 회의 날짜까지 평가 문항과 같으면 겹침입니다. 홀드아웃까지 이 스크립트가 봅니다.
- **`laya-train --eval`에는 개발용만 넣습니다.** `--eval`은 학습 전후 점수를 내므로, 홀드아웃을 넣으면 학습할 때마다 홀드아웃 점수를 보게 됩니다(7단계). 개발용 파일은 같은 스크립트가 `--eval-out`으로 만듭니다. `laya-train`도 입력 글 전체가 같은 줄을 알려 주므로 개발용 쪽은 한 번 더 잡힙니다.
- **한계.** 기준 0.85는 위 몇 쌍으로 정했고, 낱말 순서만 바뀐 말(0.733)은 놓쳤습니다. 첫 학습 대본 250건을 쓰면 실제 분포를 보고 기준을 다시 확인합니다.

#### 7. 학습·측정·보관

학습은 데스크톱 GPU(RTX 4080 Super)에서 `laya-train` 기본 설정으로 합니다. 시작 모델은 `laya-multilingual`, 4에포크, 64건씩 갱신입니다. 설정은 한 번에 하나만 바꿉니다.

| 실행 | 학습 데이터 | 시드 | 결과를 보는 문항 | 확인하는 것 |
| --- | --- | --- | --- | --- |
| 1~3 | 250건 | 0, 1, 2 | 개발용 | 학습이 되는지 |
| 4~6 | 500건 | 0, 1, 2 | 개발용 | 데이터가 늘수록 나아지는지 |
| 7~9 | 1,000건 | 0, 1, 2 | 개발용 | 나아지는지, 임계값 고르기 |
| 대조 | 1,000건, 라벨을 무작위로 섞음 | 0 | 개발용 | 무작위 수준이어야 정상 |
| 최종 | 1,000건 시드 3개 | | 홀드아웃 한 번 | 1단계 기준을 넘는지 |

- **홀드아웃은 마지막에 한 번만 봅니다.** 실행마다 홀드아웃으로 재서 가장 좋은 것을 고르면 홀드아웃이 개발용이 됩니다. 실행끼리 비교하고 임계값을 고르는 일은 개발용으로만 합니다.
- **라벨을 섞은 대조 실험.** 정답을 무작위로 섞어 학습했는데도 개발용 점수가 높으면, Laya가 라벨이 아닌 다른 경로(예: 학습과 평가에 같은 문장)로 맞히고 있다는 뜻입니다.
- **태그별 오답.** 합성 대본에서 조회 필요 문장이 늘 "?"로 끝나면 Laya는 물음표만 보고 맞힐 수 있습니다. 평가 세트의 `평서형`(물음표 없는 정보 요청)과 사람에게 묻는 말에서 오답이 몰리는지 봅니다.

측정은 `check_laya_judge.py --model <체크포인트> --eval-set`으로 하고, 최종 측정에만 `--holdout`을 붙입니다. 임계값은 `--threshold`로 바꿔 재고, 개발용에서 임계값 후보마다 재현율과 오개입률을 표로 봅니다(`--sweep`). 이 표에는 홀드아웃을 넣지 않습니다. 지연은 Laya 판단(CPU 2스레드)과 검색어만 만드는 LLM 호출을 따로 잽니다. 검색어만 만드는 호출은 `scripts/check_meeting_query.py`로 지금 판단 호출과 번갈아 잽니다. 결과는 조건(커밋, 학습 건수, 시드, 임계값)과 함께 [측정 기록](meeting-evaluation.md)에 남깁니다.

| 대상 | 두는 곳 |
| --- | --- |
| 체크포인트 | Hugging Face 비공개 저장소. 버전별로 둡니다 |
| 학습 데이터 (검수한 JSONL) | Hugging Face 비공개 데이터셋. 체크포인트와 버전을 맞춥니다 |
| 학습 데이터를 만드는 코드와 검사 | 레포. 누구나 같은 방법으로 다시 만들 수 있게 합니다 |
| 실제 회의 데이터 | 레포에 넣지 않습니다. 참석자가 동의한 회의만 쓰고, 학습 전에 실명을 가명으로 바꿉니다 |

실명을 가명으로 바꾸는 것은 Laya가 배울 것이 "이름을 부른 말"이라는 형태이지 그 사람의 이름이 아니기 때문입니다. "민수야, 작년 회칙상 환불 기준이 뭐였지?"는 "가명1아, 작년 회칙상 환불 기준이 뭐였지?"가 됩니다.

**작업 순서**

1. 코드 준비 (레포)
   1. `JudgeReview`에 둘 다 허용 칸과 AI에게 시킨 말 칸을 더하고(형식 버전 2), 학습 파일을 만들 때 둘 다 허용인 줄을 뺍니다(5단계)
   2. `check_laya_judge.py`에 `--threshold`와 임계값별 표를 더합니다
   3. 학습 파일을 만드는 스크립트: 검수 결과 → 겹침 검사(6단계) → 학습 줄 → 조회 비율 확인(4단계) → JSONL
   4. 검색어만 만드는 프롬프트와 지연 측정(1단계 지연 기준)
2. 새 홀드아웃을 먼저 씁니다. 학습 대본과 다른 모델·다른 주제로 쓰고, 라벨은 초안을 가리고 붙입니다. 먼저 확정해야 겹침 검사에 넣을 수 있고, 학습 데이터를 보고 홀드아웃을 고치는 일을 막습니다
3. 합성 학습 대본을 250건씩 쓰고 검수합니다. 검수 화면에는 "둘 다 괜찮음"과 10% 가림을 넣습니다
4. 위 표의 순서로 학습하고 잽니다

#### 판단 질문을 더할 때 (#124)

회의 중 AI에게 직접 시키기(#124)를 더하면 판단이 하나 늘 수 있습니다. 이때 Laya를 다시 학습해야 하는지는 #124에서 시키는 말을 어떻게 알아들을지에 달려 있습니다.

| #124의 방식 | 알아듣는 방법 | 다시 학습 |
| --- | --- | --- |
| AI 이름("운영해야")을 불러야만 시킬 수 있음 | 전사문에서 호출어를 찾는 규칙 | 필요 없습니다 |
| 이름 없이도 시키는 말을 알아들음 | Laya에 판단 질문 `direct_request`를 더함 | 필요합니다 |

규칙으로 가도 확인할 것이 있습니다. "운영해야"는 앱 이름이면서 "이 부스는 두 명이서 운영해야 돼요"처럼 회의에서 흔히 쓰는 낱말이라, 이 낱말만 찾으면 AI가 잘못 깨어납니다. 호출어를 잘못 듣는 정도는 평가 세트의 TTS 3건이 모두 맞았을 뿐이라 실제 회의 녹음으로 잽니다.

Laya 질문으로 가면 학습은 이렇게 됩니다. `laya-train`은 학습 파일 한 줄의 질문마다 학습 항목을 따로 만들고, 정답이 없는 질문은 건너뜁니다.

```json
{"state": "...[방금] 운영해야 이 공지 좀 친근하게 바꿔 줘",
 "questions": {"record_lookup": {...}, "direct_request": {...}},
 "expected": {"record_lookup": false, "direct_request": true}}
```

- `record_lookup` 정답만 있는 기존 줄은 그대로 씁니다. `record_lookup` 문구를 바꾸지 않아야 합니다.
- `direct_request` 정답이 붙은 줄이 새로 필요합니다. 학습하지 않은 질문은 학습 전 Laya처럼 거의 무작위로 판단합니다.
- 새 질문 데이터만으로 이어서 학습하면 `record_lookup` 성능이 떨어질 수 있으므로 두 질문의 줄을 함께 넣어 다시 학습하고, `record_lookup`이 1단계 기준을 여전히 넘는지 홀드아웃으로 다시 봅니다.
- 판단할 때는 같은 입력 글에 질문을 하나 더 묻는 것이라 호출 수는 늘지 않습니다. 지연은 다시 잽니다.

**그래서 검수 기록에 "AI에게 시킨 말" 칸을 미리 둡니다.** 지금 검수할 때 체크 하나를 더 받아 두면, #124가 Laya 질문으로 정해져도 검수한 학습 데이터를 다시 보지 않아도 됩니다. 칸이 없으면 1,000건을 처음부터 다시 봐야 합니다(평가 세트 속도로 약 5시간). 규칙으로 정해지면 칸을 비워 두면 되고, 형식 버전을 또 올리지 않아도 됩니다. 평가 세트에는 같은 내용이 `직접요청`·`AI호출` 태그로 이미 붙어 있습니다.

칸의 정의는 평가 세트의 `직접요청` 태그와 같습니다. **무언가를 해 달라고 시키는 말이고, 찾기·만들기·바꾸기를 모두 넣습니다.** 조회 여부(`label`)와는 따로 붙이므로 둘 다 참일 수 있습니다. 어떤 처리로 보낼지는 #124에서 두 값을 함께 보고 정합니다.

| 발화 (평가 세트) | 조회 필요 | AI에게 시킨 말 | 처리 (#124에서 정함) |
| --- | --- | --- | --- |
| 운영해야, 작년 송년회 회비 얼마 걷었는지 알려 줘 | 조회 | ✔ | 기록 검색. 지금도 처리됩니다 |
| 운영해야 선배님들한테 보낼 초대 문자 좀 정중하게 바꿔 줘 | 아님 | ✔ | LLM이 글을 씀 |
| 선거 공고문 형식 작년 거랑 똑같이 만들어 줘 | 둘 다 허용 | ✔ | 기록을 찾은 뒤 그걸로 글을 씀 |
| 이 부스는 두 명이서 운영해야 돼요 | 아님 | | 띄우지 않음 |

### 검색어

검색어는 기록 검색에 넣는 값이면서, 화면에 무엇을 물었는지 보여줄 때도 씁니다(#113 계약 초안의 `question`). 그래서 검색에 필요한 대상을 빠짐없이 담되 카드에 띄울 만큼 짧게 만듭니다.

```text
회의 날짜 2026-03-05
앞 발화  "자, 봄 MT 예산부터요. 비교 기준은 2025년 봄 MT로 할게요."
         (주제어 없는 발화 세 개)
방금     "어, 그때 숙소비로 총 얼마 썼죠?"
검색어   "2025 봄 MT 숙소비 총액"
```

| 규칙 | 이유 |
| --- | --- |
| **앞 발화 4개를 문맥으로 넘깁니다** | 주제가 3~4발화 전에만 나온 질문에서, 앞 발화 2개로는 검색어에 대상이 들어간 비율이 35~40%였고 4개로는 100%였습니다. 2개일 때는 "과거 행사에서 숙소비로 지출한 총액"처럼 대상이 빠졌습니다 |
| **회의 날짜를 함께 넘기고 "작년"을 연도로 바꿉니다** | 날짜가 없으면 "작년"을 그대로 두거나 틀린 연도를 지어냈습니다. 2027-02-18 회의의 "작년 관측회"를 "2025년"으로 썼습니다. 날짜는 발화 시각에서 얻습니다 |
| **짧은 명사구로 쓰고, "확인" 같은 지시와 찾을 문서 종류를 넣지 않습니다** | 지시하지 않으면 "...행사 보고서나 장부에서 확인"처럼 문장이 됐습니다. 평균 31자에서 17자로 줄었고, 지시문이 섞인 비율은 44%에서 0%가 됐습니다 |
| **회의에 묶인 행사를 함께 넘깁니다** | "이번 거", "거기"의 대상이 앞 발화에 없으면 검색어에서 빠졌습니다. 프롬프트를 바꾸지 않고 행사 칸만 더해 "2025년 숙소비"가 "2025 봄 MT 숙소비"가 됐습니다(3문항 관찰, #114) |
| **"자료를 같이 보자", "기준으로 삼자"는 조회로 보지 않습니다** | 구체적인 값을 묻지 않는 말입니다([판단 질문과 처리기](#판단-질문과-처리기)의 `record_reference`). 이 줄을 더해 오탐이 107건 중 16건에서 1건으로 줄었고, 이 조정에 쓰지 않은 문항에서 놓친 질문은 없었습니다 |
| **사람을 불러 물어도 과거 값을 물으면 조회로 봅니다** | "민수야 예약했어?"처럼 기록에 없는 지금 일만 조회에서 뺍니다. "특정 사람에게 확인하는 말"을 빼라고만 했을 때는 "민수야 너 작년에 MT 숙소 어디로 잡았었지?"를 3번 모두 놓쳤습니다. 문구를 고친 v5는 이름을 부른 기록 질문 18번을 모두 잡았고, 참고 자료 제안의 오탐이 54건 중 0~1건에서 2건으로 늘었습니다(#117) |

측정 조건과 원시 값은 [회의 어시스턴트 측정 기록](meeting-evaluation.md)에 있습니다.

**검색어만 만드는 호출.** 판단을 Laya로 바꾸면 Laya가 조회로 본 발화에만 LLM을 불러 검색어를 받습니다. 지시문은 `features/meeting/prompts/query.md`이고 `QUERY_PROMPT_VERSION`으로 관리합니다. 입력 글은 판단과 같은 `build_judge_input`이고, 검색어 규칙은 판단 프롬프트의 검색어 부분을 그대로 옮겼습니다. 같은 규칙이어야 위 측정값이 이 호출에도 이어집니다. 조회 여부는 묻지 않으므로 출력은 `query` 한 칸입니다.

```text
판단 + 검색어 (지금)   luna: needs_lookup, query
검색어만 (Laya 뒤)     Laya: 조회 → luna: query
```

### 음성 인식

음성 인식은 게이트웨이의 Whisper large v3를 씁니다. 스트리밍이 아니라 발화 구간 하나를 보내면 텍스트가 돌아옵니다.

| 항목 | 결과 | 처리 |
| --- | --- | --- |
| `prompt` | 게이트웨이가 받지 않고 오류 없이 무시합니다 | 고유명사를 미리 알려줄 수 없으므로 검색어 단계에서 보정합니다 |
| `return_timestamps` | chunks가 비어서 오고 4.7배 느려집니다 | 쓰지 않습니다. 그래서 문장별 시각이 없습니다 |
| 무음 | 무음 10초에 `" 감사합니다."`가 나왔습니다 | VAD를 통과하지 못한 구간은 보내지 않습니다 |
| 응답 형식 | OpenAI 형식이 아니라 `transcript` 안에 `text`와 `chunks`가 옵니다 | 클라이언트를 직접 만듭니다 |

음성 인식이 잘못 들은 말은 검색어를 만들 때 모델이 고칩니다(AI-MEET-02).

```text
들은 말                                검색어
"회측에 참갑이 상한 같은 교정이…"   →  "회칙 참가비 상한"
"2025년 결산 장부에 입월금이…"      →  "2025년 결산 장부 입월금"   (확실하지 않아 그대로 둠)
```

- **전사 원문은 고치지 않습니다.** "교정"을 "규정"으로 일괄 치환하면 "문서 교정이 필요하다" 같은 정상 발화가 망가집니다.
- **판단에는 보정이 필요 없습니다.** Whisper 텍스트로 판단한 결과와 대본 원문으로 판단한 결과가 같았고, CER 23.5%인 발화도 판단은 맞았습니다.
- **검색어를 만드는 모델에 "잘못 들은 말을 고쳐 쓰라"고 넓게 지시하지 않습니다.** 그렇게 지시하자 "입월금"(이월금)을 6번 중 4번 "입회비"나 "입회금"으로 바꿨습니다. 그럴듯한 다른 용어로 바뀌면 화면에서 틀린 줄 알 수 없고 엉뚱한 기록을 찾습니다. 모델에는 분명할 때만 고치고 확실하지 않으면 들린 그대로 두라고 지시합니다. "회측", "정적수", "도로글"(도록)은 이렇게 지시해도 고쳤습니다.
- **잘못 들은 말과 원래 말의 사전은 두지 않습니다.** 관찰한 오인식 6건 중 5건을 모델이 고쳤고, 남은 "입월금"도 검색에 실패하는지는 재지 않았습니다. 사전은 틀린 사례가 나올 때마다 사람이 더해야 합니다. 기록 검색(#72)이 생기면 오인식이 남은 검색어로 정답 조각을 찾는지 재고, 못 찾는 경우가 많으면 기록에 나오는 낱말 중 글자가 거의 같은 말을 자동으로 후보에 넣는 방법을 검토합니다(#114).
- 판단을 Laya로 바꿔도 검색어는 LLM이 만들므로 이 방식은 그대로입니다. 대신 Laya의 판단이 오인식 섞인 입력에 흔들리는지를 평가 세트의 Whisper 텍스트 문항으로 확인합니다(#115).

### 조회 시작과 결과 표시

조회를 시작한 결과는 늦게 도착해도 띄웁니다(AI-MEET-06). 답이 느리면 기다리며 다른 이야기를 하는 것이 자연스럽고, 필요 없는 답은 닫으면 되지만(AI-MEET-05) 물어본 답이 뜨지 않으면 사용자는 고장인지 알 수 없습니다. 대신 답에 무엇을 물었는지와 언제 물었는지를 붙여, 대화가 넘어간 뒤에 떠도 어느 질문에 대한 답인지 알 수 있게 합니다. 질문은 Whisper 원문이 아니라 앞 발화로 지시어를 풀어 만든 검색어로 보여줍니다. 판단을 판단 전용 모델로 바꿔도 검색어는 LLM이 만들므로 이 방식은 그대로 유지됩니다. 제한 시간을 넘기면 결과를 조용히 버리지 않고 처리하지 못했다고 알립니다. 검색이 도는 동안에도 다음 발화는 계속 처리합니다.

결과가 없을 때는 원인을 나눠 전달합니다(AI-MEET-07). 근거를 찾지 못한 것은 정상 결과이고, 음성 인식 실패와 검색 실패는 처리 실패입니다.

### 답과 출처

조회가 필요하다고 판단하면 retrieval의 기록 검색(#72)을 그대로 씁니다. 같은 규칙과 측정값을 계획·운영과 함께 쓰기 위해서입니다.

```text
판단이 만든 검색어 "2025 봄 MT 숙소비", 기준일 = 회의 날짜
  → find_chunks    검색어 임베딩 → 청크 검색                         (SEARCHING, records.search)
  → assess_chunks  찾은 청크로 근거 판단: 확인한 사실, 확인하지 못한 것, 자료 간 차이   (ANSWERING, llm.generate)
  → 카드 문구      "2025 봄 MT 숙박비 550,000원" + 출처               (코드가 옮김)
```

- `search_records(rewrite=False)`와 같은 단계를 같은 입력으로 거칩니다. 검색과 근거 판단을 나눠 부르는 것은 그 사이에 처리 단계를 알리고 구간 시간을 판단 기록에 따로 남기기 위해서입니다.
- 검색어를 다시 정리하지 않고 다시 찾지도 않습니다. 판단이 이미 검색어를 만들었고, 다시 정리하면 LLM 호출이 하나 늘며, 재검색은 측정에서 나아진 것이 없었습니다(#72).
- 근거 판단 결과를 카드 문구로 옮기는 규칙은 [BE-AI 데이터 계약](contracts.md#답-문구--기록-검색-결과를-옮긴다)에 있습니다. 확인한 것이 없으면 "기록에 없음"(`NOT_FOUND`)입니다.

### 지연

발화가 끝난 때부터 화면에 뜰 때까지를 구간별로 봅니다. 잰 구간은 측정값을 적고, 재지 않은 구간은 추정하지 않고 비워 둡니다.

| 구간 | p50 | p95 |
| --- | --- | --- |
| VAD 말 끝 판단 | 미측정 | 미측정 |
| Whisper | 0.41초 | 0.55초 |
| 판단과 검색어 | 1.49초 | 2.45초 |
| **Whisper부터 검색 직전까지** | **1.86초** | **3.05초** |
| 임베딩 | 0.46초 | 0.61초 |
| 청크 검색 (메모리 port) | 0.00초 | 0.01초 |
| 근거 판단 (추론 끔) | 2.02초 | 3.30초 |
| **기록 검색 전체 (임베딩부터 근거 판단까지)** | **2.52초** | **3.78초** |

전체 지연 목표는 남은 구간을 잰 뒤 정합니다. 측정 조건과 원시 값은 [회의 어시스턴트 측정 기록](meeting-evaluation.md)에 남깁니다.
기록 검색 구간은 기록 검색 평가 질문을 회의 판단에 넣어 만든 검색어 48개로, 회의와 같은 설정(검색어 정리 없음, 근거 판단 추론 끔)으로 두 번 잰 값입니다.
근거 판단의 추론을 끄면 p50이 약 0.8초, p95가 약 2.6초 줄었고 사실 맞힘은 줄지 않았습니다. 대신 답이 길어지는 경향이 있습니다(2026-10-19 측정).
청크 검색은 BE pgvector가 아니라 메모리 port 값입니다. 회의 카드 문구는 근거 판단 결과를 코드가 옮겨 만들므로 모델 호출이 늘지 않습니다([답과 출처](#답과-출처)).

### 역할 분담

| 영역 | 담당 |
| --- | --- |
| BE | 회의 세션, 오디오 수신, VAD로 발화 구간 분할, Whisper 호출, 화면으로 결과 전송 |
| AI | 문맥 관리, 판단, 검색어 구성, 답변과 출처 구성 |
| retrieval | 기존 기록 검색을 그대로 사용 |

회의 세션의 위치, 연결 방식, 발화 식별자와 순번, 최근 문맥의 소유, 검색 권한 범위는 BE와 합의합니다. AI 초안은 [BE-AI 데이터 계약의 회의 발화 처리 초안](contracts.md#회의-발화-처리-초안)에 있습니다(#113). BE가 연결해 볼 수 있도록 `app.ai.judge_utterance`로 초안을 공개했습니다. 실제 기록을 찾으려면 BE의 청크 저장소와 `RecordSearchPort` 구현이 있어야 합니다.

### 다루지 않는 것

- **말한 사람 구분(화자분리).** 마이크 하나로 겹쳐 말하는 한국어를 실시간으로 나누는 것은 정확도가 낮습니다. 기록 조회에는 누가 말했는지가 필요하지 않습니다. 회의록용으로 필요해지면 회의가 끝난 뒤 한 번에 처리하는 편이 더 정확하고 단순합니다.
- **회의록 작성과 요약.**
- **온라인 회의.** 오프라인 대면 회의만 다룹니다.

## 책임 경계

| 영역 | 책임 |
| --- | --- |
| AI | 조건 해석, 질문·계획·대응안 생성, 근거 구성 |
| BE | 행사 원본 상태, 금액·미납·환불 계산, 권한·승인 검증, 확정 변경과 실행 |
| workflow | 행사 Agent의 실행 흐름·분기와 실행 상태 관리 |
| tools | Agent가 사용할 도구의 입력·출력과 호출 처리 |
| facade / contracts | BE가 사용하는 공개 기능과 데이터 계약 |
| ports | AI가 사용하는 BE 기능 계약과 구현체 주입 |

LangGraph는 행사 Agent의 대기·계획·평가 반복과 분기를 연결하기 위해 사용합니다. 행사 변화는 BE에서 감지하여 해당 행사 Agent에 신호로 전달합니다.

행사의 업무 단계는 BE 데이터로 관리하며, 화면의 단계마다 그래프 노드를 만들지 않습니다. `state.py`는 AI 실행 상태 형식이고 `checkpoint.py`는 그 상태의 저장·복원 담당입니다. 행사 상태·채팅 기록·실행 체크포인트는 구분합니다. 저장 방식은 구현 시 BE와 합의합니다.

기록 검색은 실제 출처와 원문 위치를 반환하고 근거가 없으면 없다고 답합니다. 색인과 검색은 다음 순서로 AI와 BE가 나눠 처리합니다.

```text
[색인]
BE가 파일 파싱 (parse_result)
→ app.ai.index_record: AI가 청킹·임베딩한 청크(텍스트·위치·임베딩) 반환
→ BE가 기록 메타데이터를 붙여 청크 저장 + INDEXED (실패하면 FAILED)

[검색] features/retrieval/nodes.py search_records
AI가 찾을 내용·기준일·계획 중인 행사의 종류와 시기로 검색어 정리 → 검색어 임베딩
→ RecordSearchPort.search_chunks: BE가 동아리 범위로 제한해 비슷한 청크와 메타데이터 반환
→ AI가 근거가 충분한지 판단하고 결과 구성 (재검색은 측정에서 효과가 없어 기본은 검색 1회, `max_rounds`로 늘릴 수 있음)
→ 확인한 사실과 출처, 확인하지 못한 것, 자료 간 차이
```

`search_records`는 AI 내부 기능이며 `app.ai`로 공개하지 않습니다. planning·operations·회의 어시스턴트와 `tools/records.py`가 이 함수를 같이 쓰도록 둔 것입니다. 지금은 회의 어시스턴트만 쓰며, 검색과 근거 판단을 나눈 `find_chunks`·`assess_chunks`로 부릅니다([답과 출처](#답과-출처)). 호출하는 쪽의 조건에 맞춰 검색어 정리를 건너뛰거나(`rewrite=False`, 회의처럼 검색어를 이미 만든 경우), 검색 횟수(`max_rounds`)와 판단 모델(`invoke`)을 바꿀 수 있습니다. 모델은 출처를 직접 쓰지 않고 프롬프트에 붙인 자료 번호만 가리키며, 코드가 그 번호를 검색된 청크의 출처로 바꿉니다. 검색되지 않은 번호를 가리키면 `AIInvalidResponseError`입니다. 관련 청크가 하나도 없으면 모델을 부르지 않고 출처 없이 찾지 못했다는 결과를 돌려줍니다. 이 결과는 오류가 아닙니다. 기록 원문은 사용자 메시지의 `<record>` 구역에만 넣고 꺾쇠를 바꿔, 기록 속 지시문이 규칙을 바꾸지 못하게 합니다(AI-COMMON-01). 프롬프트 원문은 `features/retrieval/prompts/`에 있습니다.

청크 테이블에는 `record_id`·`file_name`·`category`·`event_id`·`club_id`를 복사해 두고 모두 BE가 채웁니다. 필터가 청크 테이블 하나에서 끝나고, AI는 메타데이터를 다루지 않습니다. 검색 결과의 출처(`RecordSource`)는 청크에서 그대로 옮기므로 검색되지 않은 기록이 출처로 나가지 않습니다.

BE 구현 전에는 `features/retrieval/memory_port.py`의 메모리 구현으로 색인·검색을 개발하고 평가합니다.

임베딩 모델은 게이트웨이가 제공하는 `text-embedding-3-small`이며 출력은 1536차원입니다. 저장소는 pgvector이고 청크 벡터 컬럼은 `vector(1536)`입니다. pgvector의 HNSW·IVFFlat 인덱스가 2000차원까지만 지원하므로 1536은 인덱스를 만들 수 있고, 3072차원 모델은 차원을 줄이지 않으면 인덱스를 만들 수 없습니다. 모델과 차원은 색인과 검색이 같아야 하므로 `llm.py`의 `EMBEDDING_DIMENSIONS`와 DB 컬럼을 함께 바꾸고, 바꾸면 저장된 벡터를 다시 만듭니다. 검색은 벡터 검색을 기본으로 하고, 연도·행사 이름처럼 정확한 낱말이 중요한 질문에서 품질이 부족하면 키워드 검색을 결합합니다(D-04). `sources[].location`은 FE 명세에 맞춰 `label` 하나를 씁니다.

청킹은 `features/retrieval/chunking.py`가 맡습니다. 파서는 물리적 위치(쪽·행)만 주고, 논리적 위치(조항·소제목)는 청킹이 청크 라벨에 붙입니다.

| 기록 | 나누는 단위 | 청크 라벨 예 |
| --- | --- | --- |
| 장부(CSV·XLSX) | 같은 시트의 행을 1,000자 안에서 고르게 묶음. 겹치지 않음 | `회비 수납 시트 · 2~15행`, `2~7행` |
| 문서(PDF·텍스트 기록) | 쪽 안을 장·조·번호 소제목으로 나눔. 1,000자를 넘으면 줄 경계에서 150자 겹쳐 자름. 쪽을 넘지 않음 | `2쪽 · 제10조(참가비 환불)`, `1쪽` |

문서 라벨은 덜 구체적이어도 되지만 다른 조항·소제목을 가리키면 안 됩니다. 그래서 제목인지 확신할 수 없는 줄에는 쪽 라벨만 붙입니다.

- **제목으로 보는 줄**: `제3장 회비`, `제1장(총칙)` 같은 장 / `제10조(참가비 환불)`, `제10조 (참가비 환불)`, `제11조（벌칙）`, `제12조[지출]`, `제10조의2(환불 신청)` 같은 조 / 30자 이하이고 콜론이 없고 문장으로 끝나지 않는 `1. 행사 개요` 같은 번호 소제목.
- **쪽 경계**: 조 안에 있는지와 마지막 번호 소제목의 번호를 다음 쪽이 이어받습니다. 앞 쪽에서 이어지는 문장이나 `2. …` 항목은 다음 조의 라벨을 받지 않고 쪽 라벨로 남습니다. 맨 앞의 짧은 줄을 문서 제목으로 보는 규칙은 첫 쪽에만 씁니다.
- **번호 소제목**: 직전 번호 소제목보다 번호가 클 때만 소제목으로 봅니다. `2. 예산` 다음의 `1. 숙소비`처럼 번호가 작거나 같으면 하위 목록인지 알 수 없으므로 쪽 라벨로 둡니다. 장이 바뀌면 번호를 새로 셉니다.
- **조문 참조**: 괄호 제목 없는 `제9조` 뒤에 `제M항`·`제M호`·`및`·`또는`·`내지`·`부터`·`~`가 오면 본문 속 참조로 보고 새 조를 열지 않습니다.
- **한계**: `■ 숙소`, `8.1 숙소`, `가. 숙소` 같은 제목은 알아보지 못하고 바로 앞 제목의 라벨을 이어받습니다. 앞 제목이 상위 제목이면 맞지만, 형제 제목이면 다른 섹션 라벨이 됩니다. 조문 참조도 위 목록에 없는 말(`제9조 규정에 따라`)이 오면 새 조로 봅니다.

임베딩할 때만 청크 앞에 문서명과 위치를 붙이고, 저장하는 청크 본문은 원문 그대로 둡니다. 측정값과 관찰은 [기록 색인·검색 평가 기록](retrieval-evaluation.md)에 남깁니다.

## 기능별 상세 범위

### planning — 계획 만들기와 수정

자연어 요청에서 행사 목표·인원·예산·일정 조건을 정리하고, 부족하거나 충돌하는 조건을 질문합니다. 제공된 기록 근거와 BE 계산 결과를 활용해 계획 대안, 단계·일정·담당 제안과 수정안을 만듭니다. 최초 계획뿐 아니라 운영 중 재계획에도 사용합니다. 계획의 확정·저장은 BE가 담당합니다.

### retrieval — 기록에서 근거 찾기

과거 행사 기록·장부·회칙에서 요청과 관련된 내용을 찾아 출처와 원문 위치를 구성합니다. 계획·운영 대응에 근거를 제공하고, 기록 챗봇의 질문에도 답합니다. 자료가 없거나 충돌하면 이를 명시합니다. 검색 결과를 곧바로 승인 정책이나 회계 확정값으로 적용하지 않습니다.

`tools/records.py`는 Agent에 노출되는 검색 도구의 입출력과 호출을 담당하고, 검색·근거 구성의 실제 기능은 retrieval에 둡니다. 같은 검색 로직을 두 곳에 중복 작성하지 않습니다.

### operations — 운영 중 변화에 대응

BE가 전달한 참가 취소·입금·견적·지출 등의 변화와 계산 결과를 바탕으로 현재 계획에 미치는 영향을 설명합니다. 추가 확인이 필요한 질문, 후속 작업, 대기자 충원·규모 조정 같은 대응안을 제시합니다. 변경 감지, 미납·환불 판정, 승인 검증, 메시지 발송·상태 변경 실행 자체는 BE와 Tool의 책임입니다.

### meeting — 회의 중 기록 조회

회의 발화마다 기록 조회가 필요한지 판단하고, 필요하면 검색어를 만들어 retrieval로 근거를 찾아 출처와 함께 답합니다. 실행 구조와 행사 Agent와 나눈 이유는 [회의 어시스턴트](#회의-어시스턴트)를 따릅니다. 오디오 수신·발화 구간 분할·음성 인식은 BE가 맡습니다.

### 함께 동작하는 예시

참가자가 취소되면 BE가 인원·예산을 재계산하고 행사 Agent에 신호를 보냅니다. 행사 Agent는 최소 인원 미달의 영향을 확인하고, 필요하다고 판단하면 retrieval로 과거 사례를 찾아 대응안이나 수정 계획을 만듭니다. 운영진이 골라야 하는 경우 확인 요청을 남기고 대기로 돌아가며, 답이 오면 이어서 처리합니다. 승인 대상 변경의 검증과 최종 반영은 BE에서 수행합니다.

## 모듈 의존 경계

BE는 `app.ai`의 공개 이름만 import하며 AI 내부 구현에 직접 접근하지 않습니다.
AI는 BE 모델·DB·서비스를 직접 import하지 않고 주입된 port를 사용합니다.
공개 진입점은 `__init__.py`, 기능 구현은 `facade.py`, 공개 데이터는
`contracts.py`, BE 기능 계약은 `ports.py`에 둡니다. 공개 이름은 `__init__.py`의 `__all__`이 기준입니다.
행사와 관련된 공개 기능은 해당 행사 Agent에 신호를 전달하고 처리 결과를 돌려받는 입구입니다.
기록 색인처럼 행사와 무관한 기능은 행사 Agent를 거치지 않고 바로 처리합니다.

행사 원본 상태와 승인 레코드는 BE, AI 실행 체크포인트는 AI의 책임 범위입니다.
저장·트랜잭션·실행 방식은 별도 합의 대상입니다.
승인은 그래프 interrupt가 아니라 BE의 Action 기록으로 받습니다.
SSE와 체크포인트 저장소는 아직 구현하지 않습니다.

행사 Agent를 실행하려면 다음을 BE와 합의해야 합니다.

- 체크포인트 저장소: 서버가 재시작돼도 실행 상태가 이어져야 합니다.
- 신호 보관: Agent가 처리 중일 때 들어온 신호를 보관하고, 인식 단계에서 처리하지 않은 신호를 모두 가져갑니다.
- 동시 실행 방지: 같은 행사 Agent는 한 번에 하나만 실행합니다.
- 시간 신호: 보내는 주기와 주체를 정합니다.

이전 범위와 BE 후속 작업은 [migration.md](migration.md)를 참고하세요.
