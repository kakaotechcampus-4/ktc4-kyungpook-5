# P1 응답 시간 기준 측정

상태: **고정 입력, 반복 실행기, 전체/세부 구간 관측과 집계를 구현하고 실제 모델 3세션 기준 측정을 완료했다.** 본측정 120건과 준비 실행 12건의 [원본과 분석](evaluation-results/planning-latency-real-2026-10-28/README.md)을 보존했다. 다음은 조건 변경의 기대 상태 확인과 계획 검증 실패 원인 진단이다.

관련: [#196](https://github.com/kakaotechcampus-4/ktc4-kyungpook-5/issues/196), AI-PLAN-01, AI-PLAN-05, AI-COMMON-02. 기존 개별 관찰은 [평가 기록](evaluation.md), 현재 실행 흐름은 [코드 따라가기](walkthrough.md)를 참고한다.

실측 기준은 `be76b60`이다. PR 준비 중 최신 develop의 #194 이력 안내와 #198 제외 단계 이름 보완을 통합했다. 보존한 실측은 이 변경 이전 코드의 기준값이며 현재 통합 코드의 재측정 결과로 바꾸어 설명하지 않는다. 모델을 다시 호출하지 않고 기존 원본을 유지한다.

이번 목표는 같은 입력과 설정으로 다시 잴 수 있는 출발점을 만드는 것이다. 빠른 모델로 교체하거나 프롬프트, 재시도, 출력 한도를 바꾸는 작업은 기준값 확보 뒤에 판단한다.

## 1. 어디부터 어디까지 재는가

**공개 AI 함수 호출 직전부터 반환 또는 예외 발생 직후까지**를 `ai_request_ms`로 잰다. `time.perf_counter_ns()`의 차이를 밀리초로 바꾼다. 결과 저장, 품질 검사, 통계 계산은 타이머를 멈춘 뒤 한다.

```text
고정 입력과 저장 상태 준비                    측정 전
  → chat_planning / generate_planning_preview  타이머 시작
      → 내부 상태 검증과 Graph 실행
      → 모델 응답과 Tool 처리
      → 반환 결과 조립
  ← 최종 결과 또는 예외                       타이머 종료
  → 결과 검사와 JSON 기록                     측정 후
```

공개 함수 안에서 수행하는 상태 변환은 포함한다. 호출 전 요청 객체 생성과 저장 JSON 복원, 호출 후 JSON 직렬화와 파일 쓰기는 제외한다. DB, 제품 HTTP, 브라우저 이동과 렌더링은 측정하지 않으며 실제 사용자 대기 시간은 #187 연결 후 별도로 잰다.

현재 [check_planning_public.py](../../scripts/check_planning_public.py)는 흐름 연결을 한 번씩 확인하는 스크립트다. 일부 시간에 반환 후 직렬화와 상태 복원도 포함하므로, 기존 26.287초와 16.522초를 새 기준의 전후 비교값으로 바로 사용하지 않는다.

## 2. 네 가지 요청을 따로 본다

현재 고정 입력은 `MT / 50명 / 참가비 25,000원 / 날짜와 장소 명시적 미정`이다. 제목과 총예산도 미정으로 둔다. 새 생성 준비 정책에 맞춰 날짜·장소 보류를 기록한 입력이며, 아래에 보존한 과거 실측과 입력 해시가 다르므로 직접 비교하지 않는다. 기준일은 `2026-10-28`, 시간대는 `Asia/Seoul`로 고정한다. 검색 port는 주입하지 않는다. 검색 포함 요청과 긴 이력은 이후 별도 사례로 추가한다.

측정 전에 현재 조건으로 생성 권유가 보류 없이 열려 있는 저장 상태를 한 번 준비하고 검수한다. 이력과 pending offer를 함께 JSON fixture로 고정하며 마지막 성공 초안은 null이어야 한다. 행사 조건과 권유 기준이 같고, 미해결 조건 변경이 없으며, 공개 상태 검증을 통과하는지 확인한다. fixture 준비에 모델을 호출한다면 setup 호출로 별도 기록한다. 이 fixture의 생성과 검수는 측정 밖이다. 네 사례 모두 같은 fixture에서 출발한다.

| 사례 ID | 사용자 동작 | 호출 함수 | 성공 확인 |
| --- | --- | --- | --- |
| C1 | “현재 정한 행사 조건만 간단히 설명해 줘. 값을 바꾸거나 생성 권유나 초안 생성을 하지는 마.” | `chat_planning` | 답변 있음, Tool 호출과 생성 없음, 조건 유지 |
| C2 | “예상 참가 인원을 60명으로 바꿔줘. 계획 초안은 만들지 마.” | `chat_planning` | headcount만 60명으로 반영, 나머지 조건 유지, 생성 없음 |
| G1 | 생성 권유에 “응, 만들어줘.”라고 답함 | `chat_planning` | 생성 성공과 계획 검증 통과, 조건 유지 |
| G2 | 「다음: 흐름 만들기」 클릭 | `generate_planning_preview` | 생성 성공과 계획 검증 통과, 조건과 이력 유지 |

사례 ID는 실행기가 의도한 요청의 분류다. 실제 Tool 선택, 호출 횟수, 분기도 따로 기록한다. C1에서 Tool을 썼다면 일반 상담의 정상 표본으로 조용히 바꾸지 않고 기대 경로 불일치로 남긴다. C2의 모델 호출 수를 무조건 2회라고 고정하지 않는다.

매 요청은 fixture를 새로 복원한다. 이전 반복의 응답을 다음 입력으로 이어 붙이지 않는다. request_id와 이번 message_id만 반복별 고유한 값으로 만들고, 조건, 대화 문구, 이력과 권유 상태는 유지한다. 버튼에 가짜 사용자 메시지를 추가하지 않는다. 이전 생성 결과와 같은 요청 ID를 재사용해 캐시 반환 시간을 생성 시간으로 재지 않는다.

고정 입력은 동일한 상황을 반복하기 위한 것이다. 모델 응답이나 생성 단계 개수까지 같아야 한다는 뜻은 아니다. 생성된 Step 수, Action 수와 출력 크기는 결과로 기록하고 길이가 다른 결과를 임의로 버리지 않는다.

## 3. 어떤 숫자를 기록하는가

### 대표 지표

| 지표 | 쉬운 설명 | 집계 기준 |
| --- | --- | --- |
| 성공 요청 p50 | 관측된 성공 요청 시간의 가운데 지점 | 사례별 정상 성공 표본 |
| 성공 요청 p95 | 관측된 성공 요청 시간의 95% 지점, 긴 대기를 확인하는 참고값 | 같은 사례의 같은 성공 표본 |
| 성공률 | 시도한 요청 중 기대 동작과 자동 검사를 통과한 비율 | 성공 수 / 시작한 본 측정 요청 수 |
| 실패 수와 실패 응답 시간 | 실패가 얼마나 나고, 실패를 알기까지 얼마나 기다렸는지 | 실패 유형별 건수와 관측 시간 |

평균과 최댓값도 보조 지표로 남기되 평균 하나로 대표하지 않는다. p50/p95와 함께 표본 수를 반드시 표시한다. 성공과 실패의 지연을 구분하는 이유는 빠르게 오류를 낸 요청 때문에 정상 처리 시간이 빨라 보일 수 있기 때문이다. [Google SRE의 지연과 오류 구분](https://sre.google/sre-book/monitoring-distributed-systems/#the-four-golden-signals), [백분위수 사용 설명](https://sre.google/workbook/monitoring/#calculations)을 따른다.

분위수 계산은 `numpy.percentile(values, [50, 95], method="linear")`와 같은 R7 방식으로 고정한다. 이는 NumPy의 기본 방식이며 계산 규칙을 맞추기 위한 선택이다. 구현에 NumPy 의존성을 새로 추가할 필요는 없다. 정렬한 0부터 시작하는 배열에서 위치 `(n - 1) * p`의 양옆 값을 선형 보간하면 같다. [NumPy 공식 문서](https://numpy.org/doc/2.0/reference/generated/numpy.percentile.html).

예를 들어 시간 `[2, 3, 4, 5, 6]`초라면 p50은 4초, p95는 5.8초다. **설명용 숫자이며 실제 측정값이 아니다.** 표본이 0이면 분위수는 null이다. 작은 표본의 p95를 안정적인 서비스 상위 지연이나 완료 시간 보장으로 해석하지 않는다. 이번 첫 측정에서는 p99를 대표 지표로 사용하지 않는다.

### 원인을 찾는 보조 기록

| 기록 | 용도 |
| --- | --- |
| `generation` 구간 | 공통 생성 Graph 전체의 시간. 채팅과 버튼의 내부 생성 구간 비교 |
| `compose_plan` 구간 | 입력 구성, 생성 모델 호출과 출력 수신, 구조화 결과 해석 시간 |
| `generation_model` 구간 | 생성 모델 진입 함수의 시간. compose_plan 안에 포함됨 |
| `validate_plan` 구간 | 카탈로그, 일정, 행동, 근거 검증과 최종 초안 조립 시간 |
| `agent_model` 구간 | 대화 Agent의 모델 호출별 시간. 수락 해석과 결과 설명 등에 사용 |
| 논리 모델 호출 수, Tool 이름과 호출 수 | 대화 모델과 생성 모델을 나눠 반복 호출 원인 확인 |
| 실제 HTTP 시도 수 | 관측 가능하면 기록. SDK 재시도를 포함하며 논리 호출 수와 구분 |
| 입력 길이와 출력 크기 | 이력 수, 요청 JSON 크기, 사용자 발화 길이, 모델 메시지 text 문자 수, preview UTF-8 바이트 수, Step/Action 수. text는 Tool 스키마를 포함한 전체 모델 입력이 아님 |
| 토큰 사용량과 캐시 사용량 | 공급자 메타정보에서 확인되는 경우만 기록 |

구간의 시간은 각 span의 duration_ms다. generation 안에 compose와 validate가 들어가므로 이 세 값을 다시 합산하지 않는다. 전체 함수 시간에서 생성 시간을 뺀 값을 순수 LLM 시간으로 단정하지도 않는다. 실제로 여러 번 생성했다면 호출별 구간을 모두 남긴다. 구간별 p95를 더해 전체 p95를 만들지 않는다.

논리 모델 호출은 감싼 모델 진입 함수를 호출하기 직전에 센다. 실패한 호출도 포함하며 성공 후 증가하는 기존 결과의 model_calls 값만으로 실패 횟수까지 추정하지 않는다. 설정 오류로 HTTP 전송 전 실패한 경우도 이 논리 시도에는 포함된다. 현재 SDK 재시도 기본값은 2회지만 실제 HTTP 횟수가 항상 3회인 것은 아니다. 관측하지 못한 HTTP 횟수, 토큰, 공급자 캐시 정보는 null과 미관측 이유로 남긴다. 글자 수를 토큰 수로 바꿔 쓰지 않는다.

생성 모델의 내부 스트리밍은 완성본을 모으는 방식이다. 현재 사용자에게 토큰을 순차 표시하지 않으므로 첫 토큰 시간을 사용자 응답 시간의 대표값으로 쓰지 않는다.

## 4. 어떻게 반복하는가

첫 기준은 **사례별 30회, 총 120회**다. 같은 설정의 독립 실행 세션 3개에서 각각 사례별 10회씩 쟀다. 이는 비용과 반복 가능성을 고려한 시작 규모이며, 업계 공통 최소 표본이나 통계적 충분성을 보장하는 기준이 아니다.

| 설정 | 첫 기준 |
| --- | --- |
| 동시 요청 수 | 1. 하나가 끝나면 다음 요청 실행 |
| 본 측정 | 세션 3개 × 라운드 10개 × 사례 4개 = 120회 |
| 준비 실행 | 세션 시작마다 사례별 1회, 총 12회. 결과는 보존하고 본 측정과 구분 |
| 순서 | 홀수 라운드 C1 → C2 → G1 → G2, 짝수 라운드는 역순 |
| 요청 간 대기 | 앞 요청 종료 뒤 1초. 요청 시간에 포함하지 않음 |
| 모델과 설정 | 현재 설정 유지. 모델명, reasoning/temperature의 실제 설정 여부, 생성 출력 한도와 streaming, timeout과 SDK retry 설정 기록 |
| 추가 재시도 | 실행기가 실패 표본을 성공할 때까지 다시 실행하지 않음 |

각 세션은 새 프로세스로 시작하고 준비 실행을 기록한 뒤 본 측정을 시작한다. 세션 시각과 순서를 보존한다. 준비 실행은 로컬 초기화 영향을 구분하려는 절차이며 공급자 모델이 항상 준비된 상태이거나 캐시가 꺼졌음을 보장하지 않는다.

한 라운드의 G1과 G2는 같은 입력 상태에서 독립 실행한다. 두 요청 사이에서 결과를 넘기지 않는다. 이렇게 하면 채팅 전체 시간과 버튼 전체 시간을 섞지 않으면서 시간대와 실행 순서의 영향을 줄여 볼 수 있다. 요청 간 1초 대기로 모든 rate limit을 피할 수 있다고 가정하지 않는다.

현재 요청 timeout과 SDK 재시도는 유지하고 그 대기도 요청 시간에 포함한다. 실행기가 추가로 전체 요청 제한 시간을 둔다면 사전에 프로필에 고정하고 도달 시 harness_timeout으로 구분한다. 이 값은 SDK timeout이나 서비스 응답 보장이 아니다. 중단된 실행은 interrupted와 완료되지 않은 측정으로 표시하고 원본을 보존한다.

단일 요청의 응답 시간을 재는 프로필이다. 동시 사용자 처리량, 최대 RPS, 서버 포화 성능은 이번 결과로 판단하지 않는다. 다른 행사 조건, 긴 이력이나 검색 포함 측정은 별도 프로필로 추가하고 같은 통계에 섞지 않는다.

## 5. 성공과 실패를 어떻게 판단하는가

함수가 예외 없이 반환돼도 성공이라고 단정하지 않는다. 생성 요청에서 `generation_result.status=failed` 또는 needs_clarification을 반환하거나 기대한 생성이 없으면 성공 표본이 아니다. 정상 반환 여부와 사례별 기대 동작의 충족 여부를 각각 기록한다.

공통 자동 확인은 다음과 같다.

- 공개 타입과 저장 상태 JSON 왕복 검증을 통과한다.
- C1은 조건과 상태의 의미를 유지하며 Tool을 실행하지 않는다. C2는 headcount 60명 외의 조건을 임의로 바꾸지 않는다.
- G1/G2는 조건을 그대로 유지하고 유효한 새 초안을 만든다. 날짜 미정 조건을 존중하며 포함/제외 목록의 완전성과 기존 계획 검증을 통과한다.
- G2는 대화 이력을 추가하거나 변경하지 않는다.
- 실패 응답에서는 기존 조건과 마지막 성공 초안의 보존을 확인한다. 기존 초안이 있는 실패 경로는 고정 응답 회귀 테스트에서도 별도로 확인한다.

시간 초과, 출력 한도, 모델 출력 형식 실패, 계획 검증 실패, 상태 오류, 제한/연결 오류, 기대 경로 불일치와 미분류 오류를 구분한다. 공급자 원문 대신 안전한 오류 분류와 실패 구간만 남긴다. 공개 실패 문구를 읽어 추측하지 않고 관측 가능한 오류 타입과 내부 분류를 기록한다.

원본에는 준비 실행과 본 측정, 시작한 모든 요청의 성공과 실패, 중단을 남긴다. 요약은 사례별 성공 시간과 실패 시간을 구분하고 전체 완료 요청의 시간 분포도 보조로 제공한다. 미시작 요청은 성공률 분모에 넣지 않고, 시작했으나 중단된 요청은 미완료로 따로 표시한다. 미완료가 있다면 완전한 기준 측정으로 발표하지 않는다.

예를 들어 본 측정 30회 중 28회 성공했다면 `28/30, 93.3%`와 성공 지연 표본 `n=28`, 실패 2건의 유형과 시간을 함께 보여 준다. 실패를 숨기고 28회만 성공률 분모로 쓰지 않는다. 이 역시 계산 예시이지 현재 시스템의 측정 결과가 아니다.

이 성공률은 고정 사례의 실행과 자동 계약 검증 결과다. 초안의 자연스러움, 운영상 타당성, 전체 사용자 요청에 대한 정확도를 보장하지 않는다. 답변과 초안 원본은 별도로 읽고 품질 관찰을 남긴다.

## 6. 재현에 필요한 결과물

다음 세 가지를 남긴다. 집계 전에 실패를 제거하거나 기존 결과를 덮어쓰지 않는다.

| 결과물 | 필수 내용 |
| --- | --- |
| 고정 입력 | 실제 검수한 snapshot JSON과 네 사례 문구, 기준일, 기대 동작. fixture 버전과 SHA-256 |
| 실행 원본 | 실행/세션/라운드/사례/요청 ID, 시작 시각, 실제 순서, 준비 실행 여부, 시간과 구간별 관측, 결과와 오류, 자동 확인 결과 |
| 요약 | 사례별 시도/완료/성공/실패 수, 성공률, 성공 p50/p95/평균/최대, 실패 유형과 시간, 모델 호출 수와 출력 크기 |

실행 환경에는 commit, dirty 여부와 관련 코드/프롬프트/fixture 해시, Python/주요 의존성 버전, 실행 환경과 지역의 확인 가능 범위, 모델 식별자, 실제 옵션, timeout/retry 설정을 남긴다. 요청 ID 외 입력이 같은지 확인할 정규화 입력 해시와 각 실제 요청 해시를 구분한다. API 키, 인증 헤더와 설정 주소는 결과에 넣지 않는다.

세션별 요약을 함께 보고, 합친 p50/p95는 원본 표본을 모아 다시 계산한다. 세션별 p95를 평균 내거나 네 사례의 p95를 평균 내서 전체 응답 시간이라고 부르지 않는다. 공급자 내부 버전이나 캐시 동작을 알 수 없다면 확인 불가로 남긴다. 재현 가능은 같은 절차를 실행할 수 있다는 뜻이며 같은 밀리초가 다시 나온다는 뜻은 아니다.

## 7. 구현 상태와 실행 방법

### 고정 입력과 반복 실행기의 구현 범위

고정 입력은 [planning_latency.json](../../tests/fixtures/eval/planning_latency.json)에서 관리한다. 실제 공개 함수와 권유 Tool에 고정 모델 응답을 넣어 만든 합성 상태이며, 외부 모델 호출은 사용하지 않았다. MT 50명과 25,000원, 미정 날짜, Tool 호출/결과의 짝, 마지막 권유 답변과 pending offer의 일치를 확인했다. 실제 사용자가 작성한 정답 세트는 아니다.

[measure_planning_latency.py](../../scripts/measure_planning_latency.py)는 한 프로세스에서 한 세션만 수행한다. 기본값은 준비 실행 4회와 본 측정 10라운드 40회다. 세 세션은 각각 새 프로세스로 실행하고 서로 다른 결과 폴더와 session_id를 사용한다. `--dry-run`은 입력과 실행 순서만 검증하며 모델이나 API 설정을 읽지 않는다.

결과 폴더는 기존 폴더를 재사용하지 않는다. fixture 복사본과 환경 정보를 보관하고, `attempts.jsonl`에 요청별 started/finished 이벤트를 추가한다. started 기록을 쓴 뒤 타이머를 시작하고, 함수 반환 직후 타이머를 멈춘 뒤 검사와 finished 기록을 쓴다. 강제 종료로 finished가 없다면 정상 완료로 해석하지 않는다.

현재 구현은 공개 함수 전체 시간, 실제 반환 결과, 기대 동작 검사와 요청별 성공/실패, 세부 구간과 모델 진입 시도 및 p50/p95 집계다. SDK 내부 HTTP 시도와 토큰은 관측하지 않는다. 해당 필드는 null과 범위 설명으로 구분하고, 공개 실패 사유 문구로 세부 원인을 추측하지 않는다.

### 모델 없이 입력과 순서 확인

`be/`에서 실행한다. 결과 폴더나 API 설정이 필요하지 않다.

```sh
.venv/bin/python -m app.ai.scripts.measure_planning_latency --session-id dry-01 --rounds 1 --no-warmup --dry-run
```

네 요청의 순서, 고유 ID와 요청 해시가 표시된다. 요청 ID를 제외한 입력 해시도 함께 제공하므로 다음 반복의 출발 조건이 같았는지 확인할 수 있다. 실행 시간이 출력되는 성능 측정은 아니다.

### 실제 모델 한 세션 실행

아래는 API 설정을 사용해 실제 모델을 호출하는 명령이다. 구간 관측은 기본으로 설치되며 실제 3세션 기준 측정도 같은 CLI의 기본 옵션으로 수행했다. 보존한 결과를 읽는 데 모델 재실행은 필요하지 않다.

```sh
.venv/bin/python -m app.ai.scripts.measure_planning_latency --session-id baseline-01 --output-dir /tmp/planning-latency/baseline-01
```

같은 설정에서 session_id와 output-dir을 각각 baseline-02, baseline-03으로 바꾸고 별도 프로세스로 실행하면 세 세션이 된다. 합계 132개의 공개 요청 중 본 측정은 120개, 준비 실행은 12개다. 공개 요청 수와 실제 모델/HTTP 호출 수는 다르다. 동시 실행하지 않는다.

`--rounds`, `--no-warmup`, `--interval-seconds`로 소규모 동작 확인도 가능하다. 다른 옵션으로 실행한 결과를 기본 기준값과 섞지 않는다. 기존 결과 폴더가 있으면 덮어쓰지 않고 종료한다.

| 파일 | 읽는 방법 |
| --- | --- |
| `fixture.json` | 그 세션이 사용한 정확한 원본 입력 |
| `session.json` | 코드/입력 해시와 설정, 계획된 순서, 준비 실행과 본 측정의 분리된 건수, 종료 상태 |
| `attempts.jsonl` | 같은 attempt_id의 started와 finished를 연결. finished에 ai_request_ms, observation, 성공/실패, 검사 항목과 반환 결과가 있음 |

`status=completed`는 계획한 요청을 끝까지 실행했다는 뜻이다. 요청이 전부 성공했다는 뜻은 아니므로 counts의 failed도 확인한다. CLI 종료 코드는 전부 성공 0, 실패 요청 또는 실행 오류 1, 사용자 중단 130이다. `interrupted`, `runner_failed`, 남은 started 이벤트는 완전한 기준 결과로 해석하지 않는다. 강제 종료하면 session.json이 running으로 남을 수 있으며 원본 이벤트로 확인한다.

### 저장 기록의 오프라인 집계 범위

[summarize_planning_latency.py](../../scripts/summarize_planning_latency.py)는 저장된 fixture.json, session.json, attempts.jsonl만 읽는다. API 설정이나 모델을 사용하지 않는다. 같은 attempt_id의 시작과 종료를 연결하고, 입력 해시와 예정 순서, 중복 여부를 확인한다. 완료된 세션의 건수는 원본 이벤트에서 다시 계산해 manifest와 비교한다. 파일을 읽을 때 기록을 추가하거나 기존 결과를 덮어쓰지 않는다.

준비 실행과 본 측정은 각각 사례별로 집계한다. 성공 p50/p95/평균/최대, 실패의 시간과 유형, 전체 완료 요청의 시간 분포를 분리한다. 시작만 있고 종료가 없는 요청은 pending, 취소된 요청은 interrupted로 남긴다. 두 상태를 실패 응답 시간에 넣거나 0ms로 바꾸지 않는다. 성공률의 분모는 시작한 요청 전체이며, 미완료가 있으면 부분 결과로 표시한다.

세션을 합칠 때 입력, 프로필, 실행 모드, 모델 설정, 의존성 및 코드 해시가 일치해야 한다. 같은 세션을 두 번 지정하거나 실제 모델과 주입한 호출자 모드를 섞으면 거절한다. 합친 분위수는 원본 표본으로 다시 계산한다. 단일 세션의 기록이 완전하다는 것과 기본 3세션 120회 프로필을 모두 측정했다는 것은 구분한다.

고정 응답과 가상 시계로 성공/실패/준비 실행이 섞인 기록을 만들고, 예상한 통계와 대조한다. 부분 기록은 불완전 상태로 요약하고, 중복 종료, 음수/비정상 시간, 입력 변조 등 계산을 신뢰할 수 없는 기록은 거절한다. 강제 종료로 마지막 JSON 한 줄만 덜 쓰인 경우에는 그 사실을 표시하고 앞서 완성된 이벤트만 사용한다.

### 모델 없이 저장 결과 집계

다음 명령은 이미 만들어진 세션 폴더를 읽는다. 모델 호출은 없으며 원본 파일도 변경하지 않는다. 실제 모델로 세 세션을 측정했다는 뜻은 아니며 아래 경로는 사용 예시다.

```sh
.venv/bin/python -m app.ai.scripts.summarize_planning_latency --sessions /tmp/planning-latency/baseline-01 /tmp/planning-latency/baseline-02 /tmp/planning-latency/baseline-03 --output /tmp/planning-latency/summary.json
```

콘솔에는 본 측정의 사례별 시작/성공/실패/미완료/미시작 건수, 성공률과 성공 p50/p95를 출력한다. 단위는 ms다. JSON에는 준비 실행, 세션별 결과와 실패 유형별 시간도 보존한다. 출력 파일이 이미 있으면 덮어쓰지 않는다.

| 집계 JSON | 의미 |
| --- | --- |
| `groups.measurement.C1` 등 | 같은 사례의 모든 세션 원본을 합친 본 측정 결과 |
| `groups.warmup.C1` 등 | 본 측정에 섞지 않은 준비 실행 결과 |
| `counts.started`, `success`, `failed` | 시도 수와 성공/실패 수. 성공률의 분모는 started |
| `counts.pending`, `interrupted`, `not_started` | 종료 기록 없음, 취소, 아예 시작하지 않음을 구분 |
| `success_rate` | 0~1 비율. 콘솔에서는 백분율 표시. 시작이 없으면 null |
| `success_ms`, `failure_ms`, `completed_ms` | 성공, 실패, 둘을 합친 완료 응답 시간의 각각 다른 분포 |
| `interrupted_wait_ms` | 취소 전 관측한 대기 시간. 완료 응답 시간에 섞지 않음 |
| `sessions` | 개별 세션의 같은 통계, 원본 파일 해시와 마지막 줄 손상 여부 |
| `observation` | 해당 사례의 구간 집계. 옛 형식이면 null |
| `observation_complete` | 시작한 요청의 구간 기록이 모두 닫혔는지 확인. 관측 자료가 없으면 null |

집계 JSON의 `complete=true`는 지정한 파일의 요청 기록이 끝까지 있다는 뜻이다. 실패가 없다는 뜻이나 기본 120회 프로필을 충족했다는 뜻이 아니다. 따라서 session_count, profile과 사례별 counts를 함께 본다. CLI 종료 코드 0은 완전한 기록의 집계 성공, 2는 요청 또는 구간 관측이 미완료인 부분 요약, 1은 잘못된 입력 또는 파일 쓰기 실패다. 요청 자체의 성공 여부와 구분한다.

### 세부 구간 관측의 구현 범위

[planning_latency_observation.py](../../scripts/planning_latency_observation.py)가 측정 세션 동안만 공개 workflow의 생성 함수, Agent의 모델 진입 함수, 생성 Graph의 compose/validate를 감싼다. compose에 전달되는 실제 invoke도 감싸 생성 모델의 논리 호출 시도를 관측한다. 함수 정의 때 고정된 기본 invoke도 이 경로로 관측하며, 실행이 끝나면 원래 함수를 복원한다. 공개 계약과 기능 코드, 프롬프트와 재시도 정책은 바꾸지 않는다.

요청별 ContextVar로 기록을 분리하고 하나의 측정 세션만 관측기를 설치할 수 있게 한다. 각 구간에 ID, 부모 ID, 요청 시작 기준 시작/종료 시점과 소요 시간, 정상 반환/실패/중단을 기록한다. 함수가 예외를 내도 finally에서 종료 시간을 남기며 오류 타입과 안전한 분류만 저장한다. 메시지 내용이나 공급자 오류 원문을 구간 기록에 복사하지 않는다.

관측 구간은 agent_model, generation, compose_plan, generation_model, validate_plan이다. generation 안에 compose와 validate가, compose 안에 generation_model이 들어간다. 부모와 자식 시간을 더하지 않는다. 모델 함수 시간에는 SDK 처리와 응답 수신/해석이 포함되며 공급자 서버의 순수 추론 시간으로 설명하지 않는다. SDK 내부 HTTP 재시도 대기도 포함하지만 HTTP 시도 수나 토큰은 null로 유지한다.

새 기록은 report_version=2로 구분한다. 종료 이벤트에 observation을 넣고 집계에서 구간 시간, 부모 관계와 논리 호출 수를 검증한다. 기존 version=1도 계속 읽지만 구간은 미관측으로 표시하며 새 기록과 섞어 집계하지 않는다. 관측한 구간이 실행되지 않은 경우는 호출 0회, 관측이 없는 예전 기록은 null로 구분한다. 요청당 같은 구간의 합과 실제 한 호출의 분포도 구분한다.

정상 반환된 생성 실패는 감싼 구간에서 확인한 timeout/출력 형식/계획 검증 등의 원인을 연결한다. 실패 문구를 읽어 추측하지 않는다. Agent가 실패 후 생성 Tool을 다시 선택하면 앞선 실패 구간과 뒤의 성공 구간을 모두 보존한다. 최종 요청이 성공했어도 그 안의 실패 시도는 사라지지 않는다.

| 지표 경로 (`groups.measurement.G1.observation` 기준) | 의미 |
| --- | --- |
| `model_call_attempts.agent_model` / `generation_model` | 관측된 논리 호출 시도 합계. SDK 내부 HTTP 재시도 수가 아님 |
| `by_stage.<구간>.per_call_ms` | 완료된 개별 함수 호출의 분포 |
| `by_stage.<구간>.per_completed_request_total_ms` | 완료된 공개 요청 하나에서 같은 구간의 여러 호출 시간을 합한 분포 |
| `by_stage.<구간>.calls`, `error_calls`, `interrupted_calls` | 해당 함수의 진입, 예외/실패, 중단 횟수. 다른 구간의 오류 수와 합쳐 요청 실패 수로 쓰지 않음 |
| `by_stage.<구간>.error_codes` | 해당 구간에서 관측한 오류 분류 |
| `by_stage.<구간>.pending_calls` | 요청 종료 시 아직 끝나지 않아 시간을 확정할 수 없는 구간 |

예를 들어 한 요청에서 대화 모델을 10ms와 5ms 두 번 호출했다면 per_call_ms 표본은 2개, per_completed_request_total_ms 표본은 15ms 한 개다. 버튼 요청은 대화 모델이 실행되지 않으므로 calls=0, 단일 호출의 p95=null, 그 요청의 대화 모델 총합은 0ms다. 옛 기록은 이 구분 자체를 관측하지 않았으므로 observation=null이다.

취소 중에 executor의 동기 검증 함수가 계속 실행될 수도 있다. 요청 종료 시점에 끝나지 않은 구간은 running, end_ms/duration_ms=null로 남기고 분포에 넣지 않는다. 뒤늦게 끝나도 요청 종료 후의 시간을 섞지 않는다. observation.complete와 집계 observation_complete가 false로 표시된다. 종료 시점이 있는 취소 구간은 interrupted_wait_ms로 따로 보관한다.

관측기의 설치/해제와 파일 기록, 결과 검사는 전체 타이머 밖이다. 요청 실행 중의 얇은 래퍼와 시계 읽기에는 관측 오버헤드가 있다. 구간을 관측하지 않은 옛 결과와 직접 성능 개선율을 계산하지 않고, 같은 형식/코드로 측정한 결과만 합친다. 측정 흐름의 예제는 [코드 따라가기](walkthrough.md#세부-구간은-어느-함수의-앞뒤에서-재는가)에 설명한다. 해당 예제의 숫자는 고정 시계로 지정한 검증값이며 실제 모델 속도가 아니다.

### 다음 작업

1. **완료: 고정 입력과 반복 실행기.** 공개 함수와 실제 Graph에 고정 모델 응답을 넣어 입력 독립성, 기대 동작, 실패/중단 보존과 시간 경계를 검증했다. 기존 단발 검증 스크립트는 연결 확인용으로 유지했다.
2. **완료: 고정 응답으로 기록과 집계 검증.** 실제 기록기와 공개 Graph의 모델 응답 및 시간을 고정해 집계로 연결했다. 알려진 합성 숫자로 성공률과 R7 p50/p95, 준비 실행/실패/미완료 분리, 원본 표본을 합친 계산을 검증했다. 결과는 [평가 기록](evaluation.md)에 있다.
3. **완료: 세부 구간 관측.** 측정 도구의 임시 래퍼로 생성/검증/대화 모델의 구간과 실패한 논리 호출을 관측하고 집계한다. 고정 응답과 가상 시계로 정상/실패/재시도/중단을 검증했다. 공개 응답이나 런타임 정책은 변경하지 않았다.
4. **완료: 실제 기준 측정과 해석.** 같은 코드/설정의 새 프로세스 3개로 본측정 120회와 준비 실행 12회를 모두 기록했다. [평가 기록](evaluation.md)과 [원본 분석](evaluation-results/planning-latency-real-2026-10-28/README.md)에 성공/실패 시간, 상태 불일치, 생성 재시도와 한계를 남겼다. 실패를 대체하지 않았고 모델/프롬프트/정책을 바꾸지 않았다.

다음은 C2의 specified/tentative 기대 기준과 날짜 보류 추가를 확인하고, invalid_plan의 세부 규칙을 안전하게 식별할 관측을 보완하는 작업이다. 현재 원본으로는 과거 실패의 세부 규칙을 확인할 수 없으며, 새 관측을 연결한 뒤 같은 조건에서 진단해야 한다.

기준 측정이 끝나면 어느 구간과 호출 패턴이 시간을 차지하는지부터 확인한다. 원인이 불분명하면 추가 측정이 다음 작업이다. 개선 실험을 한다면 한 번에 한 요소만 바꾸고 같은 프로필로 기준 버전과 변경 버전을 번갈아 비교한다. 조건 보존과 출력 완전성이 깨진 결과를 속도 개선으로 판단하지 않는다.
