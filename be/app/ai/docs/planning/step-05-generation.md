## 1. 사용자가 경험할 한 흐름

```text
사용자: MT고 약 50명, 인당 25,000원 정도. 날짜는 나중에.
  → 조건 변경 Tool: MT / 인원·참가비 잠정 / 일정 보류
  → Agent: 현재 정보로 준비 순서를 만들 수 있고 권유할 맥락인지 판단
  → 권유 상태 기록: 지금 조건의 계획 초안을 만들자는 제안
AI: 날짜는 비워두고, 이 조건으로 준비 순서를 먼저 잡아볼까요?

사용자: 응, 만들어줘.
  → Agent: 직전 제안의 수락으로 해석
  → 생성 Tool: 제안·최신 조건·현재 발화 확인
  → 별도 생성 graph: 초안 구성 → 코드 검증
  ← 단계·목적·순서 / 미정 일정 / 추가로 정할 내용
  → 대화 Agent: 실제 결과 설명
  → UI: 성공한 초안을 P2에 표시
```

권유만으로는 생성하거나 화면을 이동하지 않는다. 생성 수락은 초안을 보겠다는 뜻이다. 행사 확정·저장·운영 시작·공지 발송 등의 실행 승인이 아니다.

사용자가 받게 될 화면 내용은 예를 들어 아래와 같다. 전체 단계 목록이 아니라 출력의 일부를 설명한 예시다.

```text
기준: MT / 약 50명·잠정 / 참가비 25,000원·잠정 / 날짜·장소 미정
사전 준비       장소·교통 알아보기 — 50명 기준 후보와 견적 확인 / 직접 수행 / 일정 미정
모집·확정       인원·일정 확정     — 모집 결과로 최종 규모와 날짜 정리 / AI 실행 / 일정 미정
행사 진행·마무리 행사 당일         — 집결·출발·인원 확인 / 직접 수행 / 일정 미정
추가로 정할 것: 행사 날짜, 장소 후보
```

여기서 'AI 실행'은 카탈로그상의 담당 표시다. 실제 계산·현장 확인이 이미 완료됐다는 의미가 아니다. 초안의 날짜를 임의로 정하거나 50명·참가비를 확정값으로 바꾸지 않는다.

이 단계의 '먼저 제안'은 사용자 발화를 처리하는 턴에서 먼저 권한다는 뜻이다. 사용자가 아무 말도 하지 않는 동안 타이머로 실행하는 기능은 이번 범위가 아니다. 상시 행사 Agent의 신호·대기는 [전체 구조](../architecture.md)의 후속 연결 범위다.

### 버튼으로 직접 요청하는 경로

`다음: 흐름 만들기` 클릭은 명시적인 생성 요청이다. Agent가 의도를 다시 해석하거나 생성 권유를 먼저 할 필요가 없다.

```text
채팅 발화 → agent → 생성 Tool → 채팅 근거·권유 확인 ─┐
                                                  → 공통 생성 graph → 검증된 초안 → P2
버튼 클릭 → 별도 내부 함수 → 최신 조건 확인 ─────────┘
```

버튼 요청은 `request_id`, 최신 draft·generation 상태, 최근 대화·기준일을 전달한다. 채팅 요청은 이번 발화의 ID·문구를 검증한 뒤 `source=chat`을, 버튼 함수는 발화 근거 없이 `source=button`을 만든다. 클릭을 가짜 HumanMessage로 넣지 않는다. 버튼 활성화의 최소 기준은 유형 유무 등 코드 검증이며 AI의 권유 여부와 무관하다. 전송 중 클릭 잠금·중복 클릭 요청 ID·성공 후 P2 전환·오류 재시도는 5-3 로컬 UI에 연결했다.

## 2. 생성 가능 조건과 권유할 타이밍을 구분한다

| 판단 | 담당 | 초기 기준 |
| --- | --- | --- |
| 지금 입력으로 생성 처리를 호출할 수 있는가 | 코드 | 행사 유형이 있고, 실제 사용할 조건이 유효하며, 이번 요청에서 적용해야 할 조건 변경이 실패한 채 남아 있지 않음 |
| 지금 초안 생성을 먼저 권할 만큼 도움이 되는가 | LLM | 행사 목적/유형과 규모·비용·시기·장소·진행 선호 등 현재 맥락으로 유용한 준비 순서를 제안할 수 있는지 판단 |
| 사용자가 생성을 요청하거나 권유를 수락했는가 | LLM 해석 + 코드의 대상·근거 확인 | 직접 생성 요청 또는 현재 유효한 권유의 수락. 모호하면 질문 |

최소 조건은 '유형이 있으면 반드시 생성/권유한다'는 뜻이 아니다. 'MT'만 말했으면 보통 도움이 되는 내용을 더 의논한다. 사용자가 'MT라는 것만 정했지만 기본 준비 순서부터 만들어줘'라고 직접 요청하면 일반적인 초안을 허용한다. 유형도 없으면 어떤 행사인지 한 가지를 확인하며, 빈칸을 임의로 ETC로 채우지 않는다. 분류가 애매하면 기타로 볼지 의논한다.

날짜·장소·인원·예산·참가비가 모두 있어야 한다는 규칙이나 '6개 중 4개' 점수를 두지 않는다. 날짜 없는 계획은 날짜를 미정으로, 잠정 인원은 잠정으로 남긴다. 비용·인원에 의존하는 상세 판단은 확인이 필요한 내용으로 표시한다.

권유할 때는 무엇을 만들 수 있고 무엇을 비워둘지 짧게 설명한다. 질문·상담에 먼저 답하고, 감사 인사나 설명 요청에 권유를 억지로 붙이지 않는다. 사용자가 미루면 같은 조건에서 반복 권유하지 않는다. 조건이 바뀌어도 매번 다시 권하지 않으며, 계획 방향이 구체화되어 도움이 되는 맥락에서 재권유할 수 있다. 직접 생성 요청은 이전 보류보다 우선한다.

## 3. 같은 대화 Agent, 별도 생성 graph

```text
기존 대화 graph: agent ↔ tools
  ├─ update_event_conditions   현재 조건 변경
  ├─ search_past_events        과거 사실·출처 조회
  ├─ update_generation_offer   권유/보류 상태 기록
  └─ generate_event_plan       초안 생성 호출
       ↓ 필요한 입력만 전달
     생성 graph: compose_plan → validate_plan → END
       ↑ 검증된 초안 또는 실패
  → Tool 결과를 읽고 사용자에게 답변
```

대화 Agent가 대화·생성 시점을 판단한다. 생성 graph는 조건과 요구사항으로 구조화된 초안을 만들고 검사한다. P2는 결과를 보여주는 UI이며, 새로운 대화 상대나 운영 상태로 바뀌는 경계가 아니다. 대화·조건은 이어진다.

생성 graph는 구조화 출력 모델 호출 1개(`compose_plan`)와 결정론적 검증(`validate_plan`)이다. 별도의 자율 Sub Agent, 추가 의도 분류 LLM, 생성 graph 내부의 자동 수정 반복은 넣지 않았다. 검증 실패는 성공으로 포장하지 않고 반환한다. 대화 Agent가 결과를 보고 재시도할 수는 있으며 기존 한 턴 Tool 한도 3회에 함께 포함된다. 전체 행사 Agent의 planning/operations 전환과 혼동하지 않는다.

`run_planning_agent_turn(..., generate=run_plan_generation)`처럼 생성 기능을 주입해야 새 두 Tool을 모델에 공개한다. 현재 로컬 API는 이를 주입한다. 대화 프롬프트는 planning-agent-v5, 생성 프롬프트는 planning-generation-v1이다. 원문 인용 지침 보완(v4), 생성 Tool의 현재 메시지 ID 코드 주입(v5), 각각의 실측·한계는 [평가 기록](evaluation.md)에 남겼다.

## 4. 권유와 수락을 기억할 최소 상태

현재 `PlanningDraft`는 **행사 조건 초안**이다. 생성된 **단계별 계획 초안**과 다른 데이터다. 조건에 생성 결과를 억지로 넣지 않고 한 턴 입출력에 아래 실행 상태를 추가하는 방향으로 설계한다.

| 데이터 | 보관할 것 | 이유 |
| --- | --- | --- |
| `generation_offer` | 서버가 만든 권유 ID, `pending`/`deferred`, 권유 요약, 권유 당시 `PlanningDraft` 복사본 | '응'의 대상 확인, 같은 조건 반복 권유 억제, 오래된 권유 확인 |
| `plan_preview` | 마지막으로 성공한 계획 초안과 그 초안의 기준 조건 | 실패 시 이전 성공 결과 보존, 현재 조건과 결과의 차이 표시 |

구현에서는 이를 `generation: PlanningGenerationState` 안의 `offer`·`preview`로 묶는다. 거절된 조건 변경이 남았는지 `condition_change_pending`과 대상 `pending_condition_fields`도 함께 전달한다. 해당 필드의 변경이 성공하면 해소하며, 다른 필드만 바꿔서는 해소하지 않는다. 대상을 알 수 없는 거절은 자동 해제하지 않는다. 사용자가 현재 남은 값으로 생성하겠다고 명시하면 `use_current_conditions`로 재확인할 수 있다. 버튼 요청도 미해결 상태를 생략해 성공처럼 표시하지 않는다. 이 상태는 권한/승인 레코드가 아니다.

처음에는 제안 하나와 마지막 성공 초안만 보관한다. 해시·점수·복잡한 상태 머신은 두지 않는다. 메시지·Tool 이력도 그대로 이어간다. 로컬 UI는 이 상태를 다음 턴에 반환하고 새 대화에서 비운다. 운영 서비스의 보관·검증 주체는 BE와 합의해야 하며, 클라이언트가 보낸 상태를 권한/승인의 근거로 신뢰하지 않는다.

조건이 같은지는 값·잠정 여부·보류 주제처럼 계획에 의미가 있는 내용을 비교한다. 근거 메시지 ID만 달라졌다고 새 조건으로 보지 않는다. 생성 성공 시 수락한 pending 제안은 비우고 결과를 preview에 남긴다. 실패하면 이전 성공 preview와 조건을 유지하며 재시도할 수 있다. 이미 현재 조건의 preview가 있으면 불필요하게 처음 생성 권유를 반복하지 않는다.

`update_generation_offer`는 말을 대신하는 Tool이 아니라 **제안 상태를 남기는 Tool**이다. 자연어 답변은 여전히 LLM이 쓴다. 초기 입력은 `action=offer|defer`, 짧은 이유, defer인 경우 이번 사용자 발화의 `MessageEvidence` 정도로 제한한다. 조건·ID·스냅샷은 실행 코드가 채운다. 같은 조건의 보류는 코드도 재권유를 막고, 변경된 조건에서의 타이밍은 LLM이 판단한다.

권유를 기록한 턴의 최종 답변에는 그 권유를 실제로 설명해야 한다. 이 기록만으로 사용자가 화면에서 읽었다고 보장하지는 않는다. 실패 응답의 상태를 FE가 채택하지 않는 기존 원칙을 유지하며, 오래된 '응'을 만능 수락으로 사용하지 않는다.

## 5. 생성 Tool과 생성 처리의 입력·결과

### LLM이 요청할 인자 — `GenerateEventPlanInput`

- `quote: NonBlankStr`: 이번 사용자 발화의 생성 요청/수락 문구 그대로. 메시지 ID는 LLM 인자가 아니라 코드가 `request.current_message.id`에서 붙인다.
- `offer_id: str | null`: 앞선 권유를 수락할 때 그 ID. 직접 요청이면 생략 가능.
- `use_current_conditions: bool`: 거절된 변경 대신 현재 남은 조건을 쓰겠다고 사용자가 명시한 경우에만 true. 기본 false. 버튼 함수에도 같은 확인 옵션을 별도로 둔다.

행사 조건·이번 메시지 ID·동아리 ID·단계 카탈로그·전체 계획을 LLM이 Tool 인자로 다시 쓰게 하지 않는다. 현재 검증된 state에서 코드가 읽는다. 근거 문구 일치는 실제 문구가 있다는 검사이지, 수락 의도를 증명하는 검사는 아니다. 직접 요청·모호한 수락의 해석 품질은 실제 다중 턴 평가로 확인한다.

### 코드가 구성할 입력 — `PlanGenerationInput`

- `basis_draft`: 최신 조건·잠정 여부·보류 주제의 복사본.
- `trigger`: 채팅 메시지 ID·근거 또는 버튼 요청 ID. 서버 어댑터/Tool 처리기가 출처를 정한다.
- `messages`: 이번 발화를 포함한 최근 사용자·AI 텍스트. Tool 원문·SDK 메타정보는 넣지 않는다.
- `reference_date`, `timezone`: 현재 날짜 문맥. 행사 날짜가 비었다고 이 날짜를 대신 넣지 않는다.
- `catalog`: 생성 Node가 고정 모듈에서 읽어 제공한다. 요청자가 교체할 입력 필드는 아니다.
- `reference_facts`: 사용할 수 있는 실제 검색 사실·출처. 없으면 빈 목록. 기록이 있어야 생성 가능한 것은 아니다.

과거 기록은 참고 자료다. 필요할 때 기존 검색 Tool을 먼저 쓸 수 있지만 생성마다 검색을 강제하지 않는다. 채팅 처리기는 마지막 검색 Tool 결과의 명확한 facts만 전달한다. 마지막 조회가 실패/없음이면 옛 성공으로 대체하지 않고, 충돌 값들을 단일 사실로 합치지 않는다. 사용자 조건으로 채택하지 않은 과거 값은 현재 조건을 바꾸지 않으며, 생성에서 가정으로 활용하면 출처와 가정임을 함께 표시한다. 버튼 경로의 참고 자료는 호출 어댑터가 준비한다.

### 반환할 결과 — `PlanGenerationResult` / `EventPlanPreview`

결과 상태는 `generated` / `needs_clarification` / `failed`로 구분한다. 성공일 때만 새 preview를 채택한다. 타입은 [generation/schemas.py](../../features/planning/generation/schemas.py), 버튼·공통 처리는 [entrypoints.py](../../features/planning/generation/entrypoints.py), 채팅 처리는 [agent/generation_tools.py](../../features/planning/agent/generation_tools.py)를 따른다.

| 성공 초안의 정보 | 표현 기준 |
| --- | --- |
| `basis_draft` | 어느 조건으로 만든 결과인지 보존 |
| `steps` | 1개 이상. 허용 code, 단계 목적, 묶음 안 순서, 시작·마감, 예정 행동 |
| `excluded_steps` | 카탈로그에서 포함하지 않은 단계의 code·이유 |
| `assumptions` | AI가 둔 가정과 근거 출처. 사용자 조건과 분리, 없으면 빈 목록 |
| `open_questions` | 날짜·장소 등 아직 정할 내용. 모두 즉시 되묻는 질문 목록은 아님 |
| `warnings` | 일정 충돌·준비 기간 부족·확인할 제약 |

미정 시각은 `null`이고 FE가 '미정'으로 표시한다. 상대 순서는 제안할 수 있지만 날짜나 마감 시각을 만들어 확정하지 않는다. 날짜를 제안해야 한다면 가정으로 분리하고 날짜 필드는 미정으로 유지한다. 금액 합계·예산 배분을 LLM이 계산해 채우는 기능은 이번 생성 범위에 넣지 않는다.

고정 이름·묶음·담당은 카탈로그에서 코드가 보완한다. Action은 해당 단계에서 허용한 유형의 예정 제목·미정 기한 정도로 시작한다. 공지 본문·실제 대상·실행 상태·승인 레코드는 만들지 않는다. 운영 중 필요할 때 생기는 CONFIRMATION을 계획에 미리 Action으로 쌓지 않는다. 행동 없는 단계도 완료 상태로 만들지 않는다.

검증 코드는 허용 단계·중복·묶음/순서·Action 조합·날짜 관계, 포함/제외 목록의 완전성, 사용한 근거의 실제 출처를 확인한다. 의미상 단계 선택과 자연스러운 설명까지 완벽히 보장하는 것은 아니며 실제 결과를 별도로 검토한다.

같은 출처(chat/button)·같은 요청 ID·같은 기준의 마지막 성공 요청은 모델을 다시 부르지 않고 같은 preview를 반환한다. ID를 다른 조건에 재사용하면 확인을 요구한다. 마지막 성공 한 건만 기억하므로 오래된 요청 전체의 중복 제거·세션 동시성은 보장하지 않는다. 새로운 preview ID는 로컬 임시 참조이며 BE의 저장 ID가 아니다.

채팅 결과의 `model_calls`는 대화 Agent 호출, `generation_model_calls`는 생성 내부 호출의 합이다. 이번 턴의 생성 결과는 `generation_result`, 마지막 성공 초안은 `generation.preview`다. 생성하지 않은 턴에도 preview는 유지하며 `preview_is_current`로 최신 조건과 일치하는지 표시한다. 실제 HTTP 재시도 횟수와 논리 모델 호출 수는 다르다.

### 생성 모델의 출력 한도와 실패 구분 (#176)

단계·일정·예정 행동을 한 번에 쓰는 생성 호출에는 `max_output_tokens=8192`, `streaming=True`를 명시한다. 현재 게이트웨이는 일반 응답을 2,000토큰으로 제한하고 더 큰 한도는 스트리밍에서만 허용한다. 모델 통신을 스트리밍으로 받고 완성본을 모아 검증하므로, UI 응답은 계속 검증된 초안 한 번이다. 대화·검색 모델과 생성 프롬프트는 유지한다. 출력 한도는 추론 토큰도 포함하며, 항상 그만큼 소비한다는 뜻은 아니다.

모델이 출력 한도 도달을 알리면 미완성 응답으로 처리한다. JSON이 파싱되더라도 성공으로 채택하지 않는다. 모델 출력 형식 실패·코드의 계획 검증 실패·시간 초과와 구분해 고정된 안전한 사유를 전달하고, 조건과 이전 초안은 유지한다. 공급자 응답 원문이나 키는 UI·로그에 남기지 않는다. 자동 생성 반복으로 실패를 숨기지 않으며, 사용자의 새 요청으로 다시 시도한다. 비교 조건·실측과 남은 제한은 [평가 기록](evaluation.md)에 남긴다.

## 6. 정상·보류·실패 예시로 경계를 확인한다

| 입력/상황 | 기대 흐름 |
| --- | --- |
| MT·약 50명·참가비, 날짜 보류 | 현재 조건으로 준비 순서 권유 가능. 날짜를 다시 정하도록 강제하지 않음 |
| 권유 후 '아직 만들지 말자' | deferred 기록 → 대화 지속. 같은 조건 재권유 차단 |
| 권유 후 '응, 만들어줘' | pending 제안·기준 조건 확인 → 생성 |
| 참가비 변경 제안과 생성 권유가 함께 있었고 '좋아' | 대상이 모호하므로 무엇을 할지 확인. 생성/조건 변경을 동시에 추측하지 않음 |
| 권유 후 50명→40명 변경, 나중에 예전 권유를 짧게 수락 | 예전 조건의 제안을 자동 적용하지 않음. 40명 기준으로 만들지 확인 |
| '40명으로 바꾸고 그 조건으로 바로 만들어줘' | 조건 변경 성공 → 최신 40명으로 직접 생성 요청 처리. 같은 내용을 다시 수락받지 않음 |
| 날짜 변경 Tool이 거절됐는데 이어 생성 요청 | 이번 변경이 반영되지 않았음을 설명하고 기준을 확인. 오래된 날짜로 조용히 생성하지 않음 |
| 유형만 있고 사용자가 기본 준비 순서 직접 요청 | 일반 초안 생성, 규모·일정·비용은 미정 |
| 유형도 없고 '만들어줘' | 어떤 행사인지 한 가지 확인. 카탈로그 단계 임의 선택 금지 |
| 검색 자료 없음/검색 실패 | 기록이 없거나 확인 못 했음을 구분. 기록 없이 가능한 일반 초안은 생성 가능 |
| 생성 모델/검증 실패 | 실패 설명, 현재 조건·이전 성공 초안 보존. P2에 새 결과가 생겼다고 하지 않음 |
| 생성 후 조건 변경 | 새 조건 유지, 기존 preview는 다른 기준임을 표시. 자동 재생성하지 않고 필요하면 재생성 제안 |

같은 턴의 조건 변경과 생성은 순차 실행한다. 실패한 변경 뒤에는 자동 생성을 막고, 사용자가 기존 조건으로 만들겠다고 명확히 요청하면 그 기준으로 진행할 수 있다. 새 요청은 현재 초안과 실제 Tool 이력으로 판단하며, legacy pending-modification 상태를 그대로 이식하지 않는다.

## 9. 5-3 로컬 HTTP·P2 연결 계약

관련 [#173](https://github.com/kakaotechcampus-4/ktc4-kyungpook-5/issues/173). `tests/ui/planning/`의 독립 테스트 앱에 연결한다(#174). 제품 `fe/`에는 연결하지 않는다. 사용자 시나리오는 채팅/클릭 → 서로 다른 API → 공통 생성 graph → 실제 초안의 P2 표시다. 공개 BE 계약·저장은 바꾸지 않는다.

- 채팅 `POST /__planning-test/agent/turn`: draft/history와 generation을 함께 왕복한다. 서버가 실제 생성 기능을 주입하며 reply·조건·권유·preview를 한 성공 응답에서 채택한다.
- 버튼 `POST /__planning-test/agent/generate`: request_id·draft·generation·history·기준일/시간대를 받는다. current_message는 받지 않는다. 같은 이력 검증을 거쳐 실제 사용자/AI 텍스트와 마지막 기록 사실만 구성해 별도 버튼 함수로 전달한다. 응답은 `{result: GenerationUpdate, elapsed_ms, fixture_count, source: button}`이며 답변/이력을 새로 만들지 않는다.
- FE는 draft/history/generation을 하나의 세션 상태로 보관한다. 버튼 생성은 generation만 갱신하고 채팅 이력·말풍선을 추가하지 않는다. 성공한 generated 결과에서만 P2로 이동한다. 실패 응답에서도 채팅의 유효한 조건 변경은 유지한다.
- 생성/전송 중 입력·초기화·다음 버튼을 잠근다. 네트워크 오류는 요청 전체의 스냅샷과 같은 ID로 재시도하고, 그동안 다른 요청을 막는다. 응답을 받은 생성 실패는 설명하고 현재 상태로 다시 생성할 수 있게 한다.
- P2는 테스트 앱에 복사한 StepFlow를 읽기 전용으로 사용한다. 제품 FE의 컴포넌트를 import하지 않는다. 서버가 준 이름·묶음·담당·목적·미정 일정을 표시하며 FE/BE 코드 차이는 제외 단계 이름을 찾는 명시적 변환에 둔다. 가정·출처·미확인·경고·제외 사유도 표시한다. 수정/저장/운영 시작 버튼은 이번 테스트에 제공하지 않는다.
- 채팅으로 돌아가도 초안은 유지한다. 조건이 바뀌면 preview_is_current로 이전 초안임을 표시한다. 새 대화/새로고침은 브라우저 상태를 비운다.

실제 모델 사례는 실행 전 기대 결과를 고정하고 실패도 남긴다. API 없는 회귀와 실제 모델·UI 결과를 구분해 [평가 기록](evaluation.md)에 기록한다.

직접 사용하려면 [3단계 실행 방법](step-03-ui.md)처럼 AI 서버·독립 테스트 UI를 실행하고 [테스트 화면](http://127.0.0.1:5174/)을 연다. 기존 서버는 재시작해야 한다. 제품 FE의 `/planning`은 FE팀 범위다. 실제 모델 테스트는 별도 포트 5174의 루트 화면에서 한다. 조건을 말한 뒤 다음 버튼을 누르거나, 대화에서 초안을 요청한다. 생성 성공 후 '대화로 돌아가기'로 이어서 조건을 바꿀 수 있다. 샘플 기록 준비는 선택 사항이다.

### BE·FE 협의할 내용

- 브라우저에 임시 보관하는 session을 서비스에서 누가 보관·검증할지, 같은 요청 ID·동시 요청·조건 버전을 어떻게 다룰지.
- 현재 서버는 마지막 성공 상태를 요청에서 돌려받는다. 응답을 잃었을 때 서버가 그 성공을 기억하지 못하므로 같은 ID 재시도도 재생성될 수 있다. 실제 서비스의 멱등성 저장소를 보장한 구현이 아니다.
- 공개 PlanDraft 변환, 단계 코드 통일, 임시 preview ID와 BE 저장 ID의 분리.
- 읽기 전용 P2의 저장/수정/운영 시작 연결과, 추가 확인 항목을 지금 모두 답해야 하는 필수 조건으로 보이지 않게 하는 표현.
- 모델의 자발적 권유 타이밍·JSON 파싱 실패 재현과 품질 개선. UI 연결 성공과 모델 품질 전체 통과를 구분한다.
