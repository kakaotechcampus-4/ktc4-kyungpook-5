# 4단계 — 기존 기록 검색을 Tool로 재사용

2026-10-24 · #169 · AI-PLAN-04·03, AI-RET-02. 기존 `retrieval.nodes.search_records()`를 새 Agent에서 호출한다. 검색어·임베딩·근거 판단 알고리즘은 바꾸지 않는다.

## 예시와 책임

올해 참가비 25,000원 → “2025년 봄 MT 참가비는?” → agent가 검색 Tool 선택 → 기존 검색이 사실과 출처 반환 → agent가 설명, 올해 값 유지 → “올해도 그 금액으로 하자” → 조건 변경 Tool → 올해 값 반영.

기존 합성 샘플의 2025 봄 MT 보고서에는 45,000원이 있다. 이 값은 예시의 기대값이며, 여러 기록이 서로 다르거나 질문의 대상이 모호하면 임의로 하나를 고르지 않고 설명/확인한다.

```text
agent → search_past_events(query)
          → 기존 search_records(rewrite=True, max_rounds=1)
          → 검색어 정리 → 질문 임베딩 → 주입된 port → 근거 판단
       ← 사실·출처·미확인·충돌
agent → 과거 기록 설명 / 현재 조건 유지
```

새 검색 Node를 추가하지 않는다. 기존 tools Node가 Tool 이름으로 조건 변경과 검색을 나누어 실행한다. legacy의 고정 추출·조회 판단·답변 조립은 호출하지 않는다.

## Tool 입력·결과와 상태

- `SearchPastEventsInput`: `query` 하나. 동아리 ID·권한·port는 LLM 인자에 포함하지 않는다.
- 서버는 `club_id`와 `RecordSearchPort`를 검색 처리기에 주입한다. 현재 행사 종류·시작일은 검색 맥락으로 전달하지만, 올해 인원·참가비·장소와 현재 행사 ID로 과거 자료를 제한하지 않는다.
- `RecordLookupResult`: query, 상태(`available`, `not_found`, `failed`, `rejected`), 기존 `RecordSearchResult`, 이유.
- `available`은 사실/충돌 근거가 있다는 뜻이며 완전한 답변을 보장하지 않는다. 미확인 항목도 함께 반환한다.
- `not_found`는 검색은 실행했으나 근거가 없는 정상 결과다. `failed`는 모델·임베딩 등의 일시적 실패다. 설정·권한·예상하지 못한 오류는 상위로 전파한다.
- 검색 결과는 ToolMessage로 대화에 남기고, 한 턴 결과의 `record_lookup`으로 UI에 전달한다. ToolExecution은 조건 변경 또는 검색 결과를 담는다.
- 검색 처리기는 `draft`를 반환하거나 변경하지 않는다. 조회만으로 올해 값을 채우지 않는다.

검색을 주입하지 않은 호출에서는 검색 Tool을 모델에 공개하지 않는다. 주입한 경우에만 두 Tool을 제공한다. 모델 호출 대체용 테스트 인터페이스는 유지한다.

한 턴의 Tool 시도 상한 3회는 두 Tool에 공통 적용한다. 검색 내부는 기존 1회차·최대 3개 검색어 정책을 유지한다. 검색어 정리·근거 판단 등의 내부 LLM 호출은 Agent의 model_calls와 구분한다.

## UI와 실패 처리

기존 샘플 준비 API를 재사용해 합성 기록을 명시적으로 메모리에 색인한다. 새 화면에 준비 버튼·샘플 수·참고 자료를 표시한다. 실제 DB 저장은 하지 않는다.

화면은 반환된 구조화된 사실과 출처를 표시한다. 찾지 못한 내용, 기록 간 차이, 검색 실패를 구분한다. 이번 턴에 조회하지 않았으면 마지막 조회 자료를 유지하되 최신 현재 행사 사실처럼 보이지 않게 표시한다. 새 조회가 없거나 실패한 경우의 자료와 상태를 혼동하지 않는다.

검색만 일시적으로 실패하면 이번 턴의 유효한 조건 변경은 보존하고 LLM에 실패를 알려준다. 다음 질문은 대화에 맞춰 LLM이 결정한다. 근거 원문의 지시는 데이터로 취급한다. 답변 문장의 모든 주장까지 자동 검증한다고 가정하지 않으며 구조화 출처 보존과 자연어 답변 검토를 구분한다.

## 확인할 사례

검색→올해 조건 유지, 검색 결과 수락→조건 반영, 조건 변경+검색 혼합, 빈 기록, 일부 미확인, 자료 차이, 검색 실패 시 조건 보존, 서버 동아리 범위 주입을 API 없이 확인한다. 실제 모델과 UI에서도 검색→출처→수락을 실행하고 결과와 지연을 기록한다.
