### 시간과 토큰의 관계

[analyze.py](analyze.py)로 호출 시간과 토큰 수의 최소제곱 직선을 구했다. r은 상관계수로, 1에 가까울수록 두 값이 함께 움직인다. 인과나 개선 효과를 뜻하지 않는다.

| 구간 | 시간 ~ 출력 토큰 | 시간 ~ 입력 토큰 | 읽는 법 |
| --- | --- | --- | --- |
| 생성 59호출 | 약 13.5초 / 1,000토큰, r = 0.96 | 입력이 거의 일정(2,041~2,057)해 의미 없음 | 출력이 길수록 거의 그만큼 오래 걸렸다 |
| 대화 180호출 | 절편 2.48초, 약 10초 / 1,000토큰, r = 0.36 | 절편 2.32초, r = 0.20 | 토큰과의 관계가 약하고 호출마다 약 2.3~2.5초가 기본으로 든다 |

예를 들어 생성 호출 p50(출력 약 1,400토큰, 그중 추론 516)은 직선으로 보면 추론 부분이 약 7초, 계획 JSON 부분이 약 12초에 해당한다. **이 나눔은 측정값으로 그은 직선에서 계산한 값이며, 추론을 줄였을 때 그만큼 빨라진다는 측정은 아니다.** 2단계에서 직접 잰다.

### 캐시

생성 호출은 59번 모두 입력의 99.9%가 캐시로 처리됐다. 대화 호출은 180번 중 한 번도 캐시가 걸리지 않았다. 대화 입력은 매 요청 4,400토큰 이상이고 앞부분(Tool 스키마와 시스템 지시)이 같은데도 그렇다. 원인은 확인하지 않았다. 대화 시간과 입력 토큰의 관계가 약해(r = 0.20) 캐시가 걸려도 얼마나 빨라질지는 알 수 없다.

**같은 조건의 전후 비교가 아니다.** 10-28 이후 고정 입력(날짜·장소를 명시적 미정으로 기록, `749e4e3`)과 대화 프롬프트(v7)가 바뀌었고, 측정 시각도 다르다(오후 3시대 / 밤 11시대).

다만 버튼 생성 성공 초안은 두 날짜 모두 13단계, 행동 10개, 약 5,000바이트로 크기가 같았다. 그런데 생성 호출 p50은 11.8초에서 18.8초로 늘었다. 같은 크기의 초안을 더 느리게 쓴 것이다. 생성 프롬프트(`compose.md`)는 바뀌지 않았다. 공급자 쪽 처리 속도가 측정 시각에 따라 달랐을 가능성이 있지만 확인할 수 없다. 따라서 **다른 날 잰 절대 시간끼리 비교하지 않고, 2단계부터는 기존 설정과 바꾼 설정을 같은 측정 안에서 번갈아 잰다.**

C2 엄격한 검사 통과가 8/30에서 30/30이 된 것은 #205의 프롬프트 보완(생성 보류와 조건 질문 보류 구분) 이후로 보인다. 이번 측정의 목적이 아니므로 원인으로 단정하지 않는다.

| 파일 | 내용 |

결과는 작업 트리 밖에 쓴 뒤 이 폴더로 복사했다. 측정 중 작업 트리가 바뀌면 세션 기록이 dirty가 되기 때문이다. 키, 인증 헤더, 설정 주소가 결과 파일에 없는지 확인했다.

재집계는 모델이나 API 설정을 쓰지 않는다. `be/`에서 실행하고, 출력 파일은 새 경로로 지정한다.

```sh

.venv/bin/python -m app.ai.scripts.summarize_planning_latency \
  --sessions $R/session-01 $R/session-02 $R/session-03 --output /tmp/planning-tokens-summary.json
.venv/bin/python $R/analyze.py --output /tmp/planning-tokens-analysis.json
```

## 해석의 한계

- 같은 합성 MT 상황을 사례별 30번 반복한 결과다. 긴 이력, 검색 포함 턴, 다른 행사와 실제 사용자 요청 분포를 대표하지 않는다. BE DB/HTTP와 화면 대기는 포함하지 않는다.
- 토큰은 SDK 재시도 중 마지막 응답의 값이다. HTTP 시도 수는 계속 미관측이다.
- 공급자 처리 속도가 시각에 따라 달라질 수 있어, 이 절대 시간을 완료 시간 보장이나 SLO로 쓰지 않는다.
