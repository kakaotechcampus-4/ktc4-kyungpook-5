# 생성 출력 형식의 단계 코드 좁히기와 추론 깊이 재확인 — 2026-11-04

관련 [#276](https://github.com/kakaotechcampus-4/ktc4-kyungpook-5/issues/276)(선행 [#264](https://github.com/kakaotechcampus-4/ktc4-kyungpook-5/issues/264), 상위 [#262](https://github.com/kakaotechcampus-4/ktc4-kyungpook-5/issues/262)), AI-PLAN-05.

#264는 버튼 생성(G2)만 재서 생성 모델의 추론 깊이를 `low`로 바꿨다. 같은 날 채팅 생성(G1)을 재 보니 low의 통과 수가 기본값보다 적었다(29/30 → 25/30, [기록](../planning-generation-reasoning-2026-11-04/README.md#채팅-생성g1-확인--14021425)). low의 실패 5건은 모두 생성 모델이 취소 단계 코드 4개(`CANCEL_*`)를 "뺀 단계"에 적어 계획 검사(`catalog_partition`)에서 거절된 것이었다.

그래서 두 가지를 차례로 쟀다.

1. **③ 형식 좁히기:** 생성 모델의 출력 형식에서 단계 코드 허용값을 17개에서 카탈로그 13개로 줄인 v2를, 줄이기 전 v1과 번갈아 쟀다(추론 깊이는 둘 다 low).
2. **④ 추론 깊이 재확인:** v2 위에서 추론 깊이 기본값과 low를 다시 번갈아 쟀다.

> **용어**
> - **출력 형식**: 생성 모델에게 "이 모양의 JSON으로 답하라"고 보내는 형식(`PlanComposition`). 단계 코드 칸(`code`)에 쓸 수 있는 값 목록도 들어 있다. 생성 요청은 스트리밍이라 LangChain이 이 형식을 `strict: true`로 보낸다.
> - **`catalog_partition`**: 넣은 단계와 뺀 단계를 합치면 카탈로그 13개와 정확히 같아야 한다는 검사. 카탈로그 밖 코드를 적거나, 어떤 단계를 넣지도 빼지도 않으면 거절된다.

## 한 줄 결론

**v2에서 G1 30건이 모두 통과했고(v1 25/30) 취소 코드는 한 번도 나오지 않아 형식 좁히기를 채택했다. 그 위에서 low도 기본값과 통과 수가 같고(30/30) 생성 호출 p50이 18.93초에서 10.73초로 줄어 `low`를 유지한다.**

## 바꾼 코드

`features/planning/generation/schemas.py`의 `ModelStep`, `ModelExcludedStep`이 `code`를 `CatalogStepCode`(카탈로그 13개의 `Literal`)로 받는다. 생성 버전은 `planning-generation-v2`다.

모델에 보내는 형식을 실제 요청 본문으로 비교하면 차이는 아래뿐이다. 지시문(`prompts/compose.md`), 검증 규칙, 공개 계약(`contracts.py`)과 저장 형식은 그대로다.

```text
v1  "code": {"$ref": "#/$defs/StepCode"}  → StepCode: 17개(카탈로그 13 + CANCEL_* 4), 설명 "고정 단계 카탈로그 … 이 중에서 고르고"
v2  "code": {"enum": [카탈로그 13개], 같은 설명}            제외 단계 정의 이름 ExcludedPlanStep → ModelExcludedStep
```

`scripts/generation_output_v1.py`는 v1 형식을 그대로 둔 것이다. 실제 요청 본문의 형식이 develop의 v1과 글자까지 같은 것을 확인했다. 두 곳에서 쓴다. #239 재검사 도구가 예전 실패 원본(CANCEL 포함)을 읽을 때와, 비교 실행기의 v1 변형이다. 저장소에 있던 검증 실패 원본 13건을 새 코드로 다시 읽어 모두 원래 규칙으로 다시 거절되는 것을 확인했다.

## 결과

시간은 초다. p50은 가운데 값, p95는 95% 위치의 선형 보간값이다(R7). "생성 호출"은 생성 모델 호출 1번의 시간이다.

| 비교 | 변형 | 통과 / 시작 | 실패 내역 | 성공 요청 p50 / p95 | 생성 호출 p50 / p95 |
| --- | --- | --- | --- | --- | --- |
| ③ | v1 | 25/30 | 취소 코드 3, `DEMAND_SURVEY` 빠뜨림 2 | 16.63 / 23.31 | 10.95 / 13.94 |
| ③ | v2 | 30/30 | 없음 | 17.51 / 21.33 | 11.13 / 13.36 |
| ④ | default | 30/30 | 없음 | 24.25 / 27.08 | 18.93 / 20.97 |
| ④ | low | 30/30 | 없음 | 15.86 / 18.04 | 10.73 / 12.52 |

- **③** v1의 실패 5건은 모두 `catalog_partition`이었다. 3건은 취소 코드 4개를 뺀 단계에 적은 모양, 2건은 사전 수요 조사(`DEMAND_SURVEY`)를 넣지도 빼지도 않은 모양이다. v2에서는 두 모양 모두 나오지 않았다. 빠뜨림이 사라진 것은 30건에서 2건 차이라 형식 변경의 효과로 보지 않는다.
- **③** 속도는 거의 같다. 같은 세션·라운드 30쌍 중 16쌍에서 v2의 생성 호출이 빨랐다. 형식 변경은 속도를 바꾸려는 변경이 아니다.
- **③** v2에서 모델이 형식 밖 코드를 쓴 요청은 0건이었다(실행기가 생성 응답 원문에서 `code` 값만 뽑아 기록). `strict` 형식을 공급자가 지키는지는 이것만으로 알 수 없다. 모델이 쓰지 않은 것인지, 쓸 수 없던 것인지 구분하지 못한다.
- **④** 짝지은 30쌍 모두에서 low의 생성 호출이 빨랐다. 성공 요청 p50은 24.25초에서 15.86초로 8.39초 줄었다.
- ④의 default 생성 호출(18.93초)은 같은 날 14시대 G1 측정(14.91초)보다 길었다. 측정 시각마다 공급자 속도가 다르므로 다른 실행의 절대값끼리 비교하지 않고, 같은 실행 안의 변형끼리만 비교한다.

## 해석의 한계

- 같은 합성 MT 상황(날짜·장소 미정)의 채팅 생성만 쟀다. 버튼 생성(G2)은 다시 재지 않았다. 형식 변경은 같은 생성 경로를 쓰므로 G2에서도 취소 코드 실패를 막는 방향이지만, G2 수치는 #264(v1) 값만 있다.
- 날짜가 정해진 행사, 기록 근거가 있는 생성은 재지 않았다. 날짜 계산이 필요한 초안에서 low의 통과율은 미측정이다.
- `DEMAND_SURVEY` 빠뜨림(v1에서 2건)은 형식으로 막는 실패가 아니다. 이번 표본의 v2에서 나오지 않았을 뿐 남아 있을 수 있다.
- 초안의 내용 품질(목적 문장, 운영상 타당성)은 자동 검사 밖이다.
