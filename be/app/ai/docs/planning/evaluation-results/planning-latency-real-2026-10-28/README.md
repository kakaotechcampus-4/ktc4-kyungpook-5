## C2: 「인원 변경이 실패했다」는 뜻인가

**60명 반영 자체는 30/30건 성공했다.** 참가비 등 나머지 조건값도 30/30건 유지됐고, 초안 생성은 30/30건 실행하지 않았다. 엄격한 검사는 여기에 다음 기준까지 요구했다.

| 검사 | 관찰 결과 |
| --- | --- |
| headcount=60 외 나머지 조건값 유지 | 30/30 통과 |
| 인원의 상태를 specified로 기록 | 26/30 통과. 4건은 tentative |
| deferred_topics를 원래 빈 목록으로 유지 | 11/30 통과. 19건은 dates 추가 |
| 모든 기대 검사 동시 통과 | 8/30 |

날짜 보류만 달라진 요청 18건, 인원 상태만 달라진 요청 3건, 둘 다 달라진 요청 1건이다. 따라서 `19 + 4`를 서로 다른 실패 요청 23건으로 세면 안 된다. 지정된 기대 기준을 사후에 완화해 성공률을 올리지는 않았다.

실제 예시 `real-20261028-03-measurement-0001-C2`:

```text
입력: “예상 참가 인원을 60명으로 바꿔줘. 계획 초안은 만들지 마.”
→ update_event_conditions → update_generation_offer → 답변
결과: headcount=60, fee_per_person=25000, 초안 생성 없음
      headcount.status=tentative, deferred_topics=[dates]
판정: 값 변경은 성공. 기대한 specified와 보류 상태 유지에는 불일치.
```

프롬프트는 명확한 값은 specified, “대략” 등 잠정 표현은 tentative로 다루도록 한다. 다만 고정 입력의 “예상 참가 인원”을 잠정으로 읽을 여지도 있다. 먼저 이 문장의 기대 상태와 허용할 자율 변경을 합의해야 한다. 자동 검사 불일치를 모두 제품 오류로 단정하거나 모델을 바로 교체할 근거로 사용하지 않는다. 요청하지 않은 날짜 보류 추가는 별도로 확인할 동작이다.

## G1/G2: 초안을 썼는데 왜 실패했는가

G1 2건과 G2 3건의 최종 실패는 모두 `validate_plan / invalid_plan`이었다. 생성 모델과 compose_plan은 정상 종료했지만, 다음 코드 검증에서 계획을 거절했다. 함수는 이를 `generation_result.status=failed`로 반환했으므로 **예외 없이 반환된 요청도 성공은 아니다.** 본측정 120건 모두 공개 함수는 정상 반환했다.

현재 관측기는 오류 타입과 안전한 분류를 남긴다. 어떤 카탈로그/날짜/행동/근거 규칙을 위반했는지 식별하는 코드는 없고, 거절된 중간 `PlanComposition`도 보존하지 않는다. 따라서 세부 원인은 미확인이다. 날짜 미정이 원인이라고 추정해 검사 규칙을 없애면 안 된다.

최종 실패는 5요청이지만 생성 시도 실패는 6회다. 다음 한 요청에서 두 번 실패했기 때문이다.

```text
real-20261028-02-measurement-0003-G1
“응, 만들어줘.”
→ Agent 판단 1.590초
→ 생성 12.080초 → validate_plan 거절
→ Agent 판단 3.034초
→ 생성 재시도 12.175초 → validate_plan 다시 거절
→ Agent 설명 2.356초
← 실패 반환, 전체 31.244초 (나머지는 Graph/상태 처리 등의 시간)
```

이 추가 생성은 측정기가 재시도한 것이 아니라 기존 Agent의 Tool 선택이다. 같은 오류가 부모 generation과 자식 validate_plan에 모두 남으므로 전체 span 오류 수 12를 요청 실패 수로 사용하지 않는다.

## 어느 구간에서 기다렸는가

아래는 **사례별 전체 완료 30요청의 요청당 평균 시간**이다. 실패와 요청 안의 추가 생성도 포함한다. 각 요청에서 같은 구간이 여러 번 실행되면 먼저 합한다. 서로 겹치지 않는 최상위 구간만 사용했다.

| 사례 | 전체 평균 | 대화 모델 합계 평균 | 생성 Graph 합계 평균 | 그 밖의 시간 평균 |
| --- | --- | --- | --- | --- |
| C1 | 2.484초 | 2.479초 | 0초 | 0.005초 |
| C2 | 6.954초 | 6.945초 | 0초 | 0.010초 |
| G1 | 17.875초 | 5.181초 | 12.686초 | 0.008초 |
| G2 | 11.674초 | 0초 | 11.672초 | 0.001초 |

생성 Graph 안의 대부분은 생성 모델 호출 대기다. 코드 검증은 생성 시도 61회의 평균 약 0.216ms, 최대 0.297ms였다. **검증 실행이 느린 것이 아니라, 시간이 걸려 작성한 초안이 뒤의 검증에서 거절되는 상황**이다. 모델 함수 시간은 SDK/통신/수신/해석을 포함하며 공급자의 순수 추론 시간은 아니다.

본측정에서 대화 모델 진입 182회와 생성 모델 진입 61회를 관측했다. 준비 실행의 대화 18회와 생성 6회는 별도다. C2는 대화 모델 총 91회로, 조건 변경 Tool과 생성 보류 Tool을 순차 선택한 사례가 있었다. “조건 변경이면 모델은 항상 두 번 호출된다”라고 고정하면 안 된다.

채팅에는 수락 판단과 생성 후 설명이 추가된다. 다만 G1/G2는 생성 입력 문맥과 출력 길이도 달라질 수 있다. 성공 p50의 차이 5.238초를 곧바로 순수 Agent 오버헤드라고 부르지 않는다. 성공 계획의 단계 수도 G1은 12단계 6건/13단계 22건, G2는 12단계 9건/13단계 18건이었다.

수동으로 예시 원문을 읽었을 때 채팅 성공 예시는 구조화 결과의 13단계를 답변에서 12개 항목으로 요약했다(정산과 환급을 한 항목으로 표현). 자동 통과는 전체 답변의 상세 품질까지 검수했다는 뜻이 아니다. 구조화 preview를 UI의 기준 데이터로 사용한다는 기존 계약을 유지한다.

본측정은 CLI 기본 옵션으로 세 번 순차 실행했다. 각 실행은 다음 형태다(`be/`, 기존 API 환경 설정 필요). 이 명령은 **새 모델 호출**이므로 결과 확인을 위해 재실행할 필요가 없다.

```sh
.venv/bin/python -m app.ai.scripts.measure_planning_latency --session-id real-20261028-01 --output-dir /tmp/new-baseline/session-01
```

session-id/폴더를 각각 02, 03으로 바꿔 별도 프로세스로 실행한 기록이다. 이번 작업 트리 밖의 기존 `.env`를 프로세스 환경으로만 읽었으며 기존 환경변수는 덮어쓰지 않았다. 키를 출력하거나 복사하지 않았다. CLI는 검증 실패가 있으면 종료 코드 1을 반환하지만, 세션 `status=completed`와 모든 요청 기록을 확인한 뒤 다음 세션으로 진행했다.

보존 원본의 재집계는 모델이나 API 설정을 사용하지 않는다. `be/`에서 실행한다. 출력 파일은 기존 파일을 덮어쓰지 않도록 새 경로로 지정한다.

```sh
.venv/bin/python -m app.ai.scripts.summarize_planning_latency \
  --sessions app/ai/docs/planning/evaluation-results/planning-latency-real-2026-10-28/session-01 \
             app/ai/docs/planning/evaluation-results/planning-latency-real-2026-10-28/session-02 \
             app/ai/docs/planning/evaluation-results/planning-latency-real-2026-10-28/session-03 \
  --output /tmp/planning-real-summary.json

.venv/bin/python app/ai/docs/planning/evaluation-results/planning-latency-real-2026-10-28/analyze.py \
  --output /tmp/planning-real-analysis.json
```

보조 진단은 같은 폴더의 combined-summary.json과 원본을 읽는다. `conditions_match`는 headcount만 60으로 바꾼 전체 조건 사전과 일치하는 요청 수다. `deferred_topics_counts`는 최종 보류 목록별 요청 수다. `mean_request_breakdown_ms`는 완료 요청의 평균 구간이며 부모/자식을 중복 합산하지 않는다. `examples`는 성공 p50에 가장 가까운 실제 요청을 고른 것이고 p50 자체를 단일 요청으로 꾸민 값이 아니다.

원본 3세션의 복사 전후 바이트 일치를 확인했다. 정식 집계로 세션 설정/입력/기록/구간 완전성을 검증하고, 보존한 파일로 재집계한 결과와 원래 집계의 JSON 일치를 확인했다. 보조 진단도 같은 원본에서 다시 계산해 일치했다. 자격증명과 설정 주소가 결과 파일에 포함되지 않았는지 확인했다.

## 해석의 한계와 다음 순서

이 결과는 같은 합성 MT 상황을 사례별 30번 반복한 결과다. 다른 행사, 긴 이력, 검색, 동시 사용자나 실제 사용자 요청 분포를 대표하지 않는다. BE DB/HTTP, FE 화면 대기는 포함하지 않는다. 특히 C2 성공 지연은 8표본이고 생성 실패 시간도 함께 봐야 한다. 작은 표본의 p95를 완료 시간 보장이나 SLO로 쓰지 않는다. SDK 내부 HTTP 시도 수와 토큰/캐시 사용량은 계속 미관측이다.

1. C2의 specified/tentative 기대 기준과 생성 보류 시 날짜 보류까지 바뀌는 동작을 먼저 확인한다. 판정 기준을 바꾸면 기존 점수는 유지하고 새 기준을 별도로 기록한다.
2. 계획 검증에 안전한 세부 규칙 코드를 남겨 invalid_plan 5건의 원인을 좁힐 수 있게 한다. 이번 원본만으로 과거 실패의 세부 원인을 복구할 수는 없다.
3. 같은 실패의 반복 생성이 사용자에게 도움이 되는지 확인한다. 원인 확인 후 정책을 검토한다.
4. 그 뒤 병목에 맞는 변경을 하나씩 실험하고 같은 프로필로 전후를 비교한다. 성공률과 조건 보존을 함께 본다.
