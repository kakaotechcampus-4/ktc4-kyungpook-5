# 생성 보류와 조건 질문 보류의 경계 비교 (#205)

관련 요구사항: AI-PLAN-01, AI-PLAN-03, AI-COMMON-01, AI-COMMON-02.

**자연스러운 답변 뒤에 요청하지 않은 보류 상태가 추가되는 문제를 지침 수정으로 줄이는지 확인했다.** 핵심 입력 30회씩의 비교에서 불필요한 날짜 보류가 기존 17/30건, 수정 0/30건으로 관측됐다. 정상적인 날짜 보류도 유지됐다. 모호한 재개 표현의 실패 1건은 그대로 보존했으며 모든 자연어 요청의 정확성을 보장하는 결과는 아니다.

## 문제와 확인한 경로

```text
현재: MT / 50명 / 참가비 25,000원 / 날짜 미정 / 보류 주제 없음
사용자: 예상 참가 인원을 60명으로 바꿔줘. 계획 초안은 만들지 마.
답변: 예상 참가 인원을 60명으로 변경했어요. 계획 초안은 만들지 않고 보류해둘게요.

기존 사례의 내부 상태:
  인원 60명 → 정상
  초안 생성 없음 → 정상
  날짜 질문 보류 추가 → 요청하지 않은 변경
```

기존 #196 원본에서는 19/30건에서 날짜 보류가 추가됐다. 실제 Tool 인자에서 “계획 초안은 만들지 마.”를 날짜 보류 근거로 사용한 것을 확인했다. 원문 포함 여부 검사는 통과하지만, 그 문장이 선택한 주제의 논의를 보류하라는 의미인지는 코드가 확인하지 않는다. 날짜 미정은 날짜 질문 보류와 다르다.

이전 지침은 조건 질문 보류와 생성 권유 보류를 각각 설명했지만 둘이 독립된 상태라는 경계와 부정 예시가 충분하지 않았다. 대화 문맥의 날짜 미정 표현이 영향을 줬을 가능성도 있다. 이것은 원인 후보이며 모델의 내부 판단 이유를 확정한 설명이 아니다.

## 판단과 변경

- 인원 값이 맞고 tentative/specified만 다른 경우는 이번 주 지표의 실패로 보지 않는다. 두 상태는 여전히 구분해 반환하며 행사 최종 승인을 뜻하지 않는다.
- 생성하지 말라는 의사를 무관한 조건 주제에 확장하는 것은 수정 대상이다.
- 먼저 시스템 지침만 수정했다. Tool 스키마, 처리기, Node 연결, 모델 설정은 바꾸지 않았다.
- 지침에 생성 보류와 질문 보류의 차이, 미정값으로 보류를 추론하지 않기, 두 의사가 함께 있으면 각각 적용하기를 명시했다. 짧은 문맥 참조는 유지한다.
- 모든 보류를 막거나 ‘날짜’라는 단어가 없으면 거절하는 방식은 사용하지 않았다. “그건 나중에”처럼 문맥으로 처리할 요청을 함께 검증했다.

지침 버전은 planning-agent-v6다. 실제 변경은 [chat.md](../../../../features/planning/agent/prompts/chat.md), 구조와 입력/출력은 [코드 따라가기](../../walkthrough.md#생성-보류가-날짜-질문-보류로-번지지-않게-하기-205)에 있다.

### 검사 기준

LLM이 답변을 채점하지 않는다. [inspect_boundary()](../../../../scripts/check_planning_deferrals.py)는 공개 반환값으로 다음을 확인한다.

1. headcount만 60명으로 바뀌고 다른 조건값은 유지된다.
2. 최종 보류 주제 목록이 사례의 기대값과 같다. 필요 없는 추가뿐 아니라 필요한 보류 누락도 실패다.
3. 초안을 생성하지 않고 생성 권유 보류를 기록한다.
4. 다른 조건의 metadata와 기존 이력, 원본 요청을 보존한다.
5. JSON 왕복, 화면/보관 상태 일치, 요청 ID/버전과 답변 존재를 확인한다.

모든 검사를 통과해야 사례 통과다. 인원의 tentative/specified는 진단값으로 남기며 점수에 반영하지 않는다. **기존 #196의 엄격한 점수 8/30은 바꾸지 않았다.** 이번 평가의 기준과 모델 실행 배치가 달라 그 점수를 새 점수와 바로 비교하지 않는다.

## 결과

아래 ‘통과’는 위 전체 검사를 함께 통과한 요청 수다.

| 실행 / 사례 | 기존 지침 | 수정 지침 |
| --- | --- | --- |
| 최초 / 핵심: 인원 변경 + 생성하지 않기 | 13/30 | 30/30 |
| 최초 / 생성 보류 표현 변형 | 0/3 | 3/3 |
| 최초 / 날짜 직접 보류 + 생성 보류 | 3/3 | 3/3 |
| 최초 / 날짜와 장소 함께 보류 | 3/3 | 3/3 |
| 최초 / 직전 날짜 질문에 “그건 나중에” | 3/3 | 3/3 |
| 최초 / 기존 날짜 보류에서 “날짜는 다시 얘기하자” | 0/3 | 2/3 |
| 추가 / 새 생성 보류 표현 | 0/3 | 3/3 |
| 추가 / 명확한 날짜 보류 해제 | 2/3 | 3/3 |

핵심 사례에서 인원 변경, 다른 조건값 유지, 실제 생성 없음은 두 지침 모두 30/30건 통과했다. 불필요한 날짜 보류는 기존 17/30건, 수정 0/30건이었다. 기존 #196의 19/30건과 이번 17/30건은 다른 실행 배치이며 실패를 대체해 고른 표본이 아니다.

추가 표현은 “초안 작업은 다음에 하자. 지금은 예상 인원만 60명으로 기록해 줘.”였다. 기존 지침은 3건 모두 기대에 없는 보류가 있었으며 그중 1건은 날짜 외 다른 주제까지 보류했다. 수정 지침은 3건 모두 주제 상태를 유지했다. 수정 지침의 1건은 headcount를 tentative로 표시했지만 이번 허용 기준에 따라 통과했고 원문을 보존했다.

### 원래 평가에서 실패한 사례는 지우지 않았다

“날짜는 다시 얘기하자”는 현재 재개와 나중에 논의하자는 뜻으로 읽힐 여지가 있다. 초기 평가는 재개를 기대했지만 수정 지침의 1건은 보류를 유지했다. 이 요청은 원래 실패로 남겼다. 이미 dates가 보류된 상태에서 유지된 것이므로 새로운 날짜 보류 추가와도 구분한다. `extra_topics`는 기대한 최종 주제 목록보다 남아 있는 주제를 뜻하며 항상 새로 추가한 주제라는 뜻은 아니다.

그 뒤 “날짜 보류를 해제하고 지금부터 일정을 정하자. 인원은 60명으로 바꾸고 초안 생성은 하지 마.”를 별도로 확인했다. 날짜 재개는 두 지침에서 3/3건 처리됐고, 기존 지침 1건은 생성 권유 보류를 남기지 않아 전체 검사 2/3건이었다. 수정 지침은 3/3건 전체 통과했다.

후속 결과를 초기 실패 요청의 성공으로 대체하거나, 명확한 표현에 성공했으므로 모호한 표현도 해결됐다고 해석하지 않는다.

## 코드 흐름과 얻은 근거

```text
인원은 60명으로 바꾸고 초안은 만들지 마
  → agent_node: 최신 상태와 지침, 이번 발화 읽기
  → update_event_conditions: 인원만 변경, 주제 보류 목록 유지
  → update_generation_offer(defer): 생성 권유만 보류
  → agent: 적용된 결과를 읽고 답변
  → view / next_state 반환
```

지침 외의 실행 경로를 같게 두고 비교했을 때 목표 오류가 줄어들었으므로, 두 보류의 범위를 지침에서 명확히 하는 것이 이 입력군에 도움이 됐다는 근거를 얻었다. 지침에 추가한 설명과 예시 중 어느 부분이 얼마나 기여했는지, 이전 문맥의 영향이 얼마나 컸는지는 별도로 분리하지 않았다.

## 남은 한계

- 지침 보완으로 재현 사례를 개선한 것이며, 잘못된 Tool 인자를 코드가 의미까지 판별해 항상 차단하도록 바꾼 것은 아니다. 더 넓은 실제 표현에서 같은 문제가 나오면 안전한 검증과 수정 경로를 추가 검토한다.
- 같은 합성 MT 상황의 반복과 작은 대조 표본이다. 일반적인 정확도나 모든 표현의 무오류를 보장하지 않는다. 답변 전체 품질은 수치로 평가하지 않았으며 사례 원문을 함께 읽었다.
- 모호한 재개 표현의 판단은 남은 과제다. 현재 보류를 사용자가 언제 재개했다고 볼지 별도 기준이 필요하다.
- 이미 보관된 잘못된 보류를 자동 삭제하지 않는다. 정상적인 사용자 보류와 구분 없이 상태를 초기화하면 안 된다. 명확한 재개 요청을 처리하는 경로는 확인했다.
- BE/FE 계약, 상태 형식, 제품 UI는 바꾸지 않았다. 제품 연결과 배포 검증은 이 결과에 포함되지 않는다.
