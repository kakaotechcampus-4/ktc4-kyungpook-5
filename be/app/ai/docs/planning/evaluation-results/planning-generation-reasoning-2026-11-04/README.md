# 생성 모델 추론 깊이 기본값/low 비교 — 2026-11-04

관련 [#264](https://github.com/kakaotechcampus-4/ktc4-kyungpook-5/issues/264)(상위 [#262](https://github.com/kakaotechcampus-4/ktc4-kyungpook-5/issues/262)), AI-PLAN-05.

#263 측정에서 생성 호출 출력의 약 37%가 추론이었다. 그래서 생성 모델의 추론 깊이만 바꾼 `low`와 기존 설정(`default`, 값을 보내지 않음)을 같은 실행 안에서 번갈아 쟀다.

> **추론 깊이(reasoning effort)**: 모델이 답을 쓰기 전에 내부에서 얼마나 생각할지 정하는 설정이다. `build_chat_model(reasoning={"effort": "low"})`처럼 호출별로 정한다. 추론에 쓴 토큰도 출력 토큰에 포함되고, 생성 호출의 시간은 출력 토큰 수에 거의 비례한다(#263, r = 0.96).

## 한 줄 결론

**`low`에서 생성 호출 1번의 p50이 15.39초에서 11.14초로, p95가 19.72초에서 12.91초로 줄었다. 계획 검증 통과(26/30 → 28/30)와 초안 단계 수(중앙값 13)는 줄지 않아 측정 전에 정한 채택 기준 세 가지를 모두 만족했다. `low`를 채택했다.**

## 결과

시간은 초다. p50은 가운데 값, p95는 95% 위치의 선형 보간값이다(R7).

| 변형 | 통과 / 시작 | 성공 요청 p50 / p95 | 생성 호출 p50 / p95 | 출력 토큰 p50 / p95 | 그중 추론 p50 / p95 | 출력 중 추론 |
| --- | --- | --- | --- | --- | --- | --- |
| default | 26/30 | 15.32 / 19.12 | 15.39 / 19.72 | 1,508 / 1,923 | 516 / 904 | 37.2% |
| low | 28/30 | 11.09 / 12.64 | 11.14 / 12.91 | 1,190 / 1,304 | 240 / 363 | 21.8% |

- 같은 세션·라운드의 default와 low를 짝지은 30쌍 중 **29쌍에서 low가 빨랐다.** 생성 호출 시간 차이는 중앙값 4.09초, 평균 4.60초다.
- 추론을 뺀 출력(계획 JSON)은 중앙값 954 → 928토큰으로 거의 같았다. 성공 초안의 행동 수 중앙값은 둘 다 10개, 크기는 5,236 → 5,110바이트다. **줄어든 것은 추론이고 초안 자체는 거의 그대로였다.**
- p95가 더 크게 줄었다(19.72 → 12.91초). default는 추론이 길어지는 호출(최대 900토큰대)이 있었고, low는 추론 양의 폭이 좁았다.
- 입력은 두 변형 모두 2,041토큰, 그중 2,038토큰이 캐시였다.

### 계획 검증 실패: 두 변형 모두 같은 원인

실패 6건(default 4, low 2)은 모두 `invalid_plan`이었고, #239의 기록 방식으로 거절 규칙을 남긴 결과 **6건 모두 `catalog_partition`, 같은 모양**이었다.

```text
생성 모델의 excluded_steps(이번 초안에서 뺀 단계)에
CANCEL_NOTIFY_PARTICIPANTS, CANCEL_VENUE, CANCEL_REFUND, CANCEL_RECORD 4개가 들어감
→ 행사 계획 카탈로그에 없는 코드라 포함·제외 목록이 카탈로그와 맞지 않음 → 거절
```

이 네 코드는 행사 취소 흐름용 단계(`app.core.enums.StepCode`)다. 생성 프롬프트는 "취소 단계 금지"라고 적고 있지만, 구조화 출력 스키마의 `code` 타입이 `StepCode` 전체라 모델이 고를 수 있다. 추론 깊이와 관계없이 나오는 실패이므로 이번 변경의 영향으로 보지 않는다. 26 → 28의 차이도 개선이라고 말하지 않고 "떨어지지 않았다"로만 읽는다. 원인 후보는 #262 5단계 후보(검증 실패 줄이기)로 넘긴다.

## 바꾼 코드

`features/planning/generation/model.py`의 `build_plan_model`이 `reasoning={"effort": "low"}`(`PLAN_REASONING`)를 보낸다. 대화 모델은 그대로(값 미지정)다. 테스트 `test_plan_generation_model.py`가 실제 SDK 요청 본문에 이 값이 실리는지 고정한다.

## 파일과 재집계

| 파일 | 내용 |
| --- | --- |
| `session-01~03/session.json` | 프로필, 시각, 코드·입력·프롬프트·검증기 해시, 환경, 집계(`summary`) |
| `session-01~03/attempts.jsonl` | 66요청의 started/finished 이벤트. `variant`(default/low), 생성 구간 `usage`, 거절 규칙(`violations`) 포함 |
| `session-01·03/validation/` | 검증에서 거절된 초안과 위반 정보(#239 형식). 대화 본문은 넣지 않는다 |
| [analysis.json](analysis.json) | 세 세션을 합친 집계, 세션별 생성 호출, 쌍 비교, 채택 기준 판정, 위반 내용 |
| [analyze.py](analyze.py) | 위 분석을 원본에서 다시 계산하는 오프라인 스크립트 |

결과는 작업 트리 밖에 쓴 뒤 이 폴더로 복사했다. 키, 인증 헤더, 설정 주소가 결과 파일에 없는지 확인했다.

재집계는 모델이나 API 설정을 쓰지 않는다. `be/`에서 실행한다.

```sh
.venv/bin/python app/ai/docs/planning/evaluation-results/planning-generation-reasoning-2026-11-04/analyze.py \
  --output /tmp/planning-reasoning-analysis.json
```

다시 재려면 실제 모델 설정이 필요하다. 결과 폴더는 작업 트리 밖에 둔다. `default` 변형은 코드의 기본값이 `low`로 바뀐 뒤에도 값을 보내지 않으므로 같은 비교가 된다.

```sh
.venv/bin/python -m app.ai.scripts.compare_generation_reasoning --output-dir <작업 트리 밖 폴더>/session-01 --session-id reasoning-01
```

## 해석의 한계

- 같은 합성 MT 상황(날짜·장소 미정)의 버튼 생성만 쟀다. 날짜가 정해진 행사, 기록 근거가 있는 생성은 재지 않았다. 날짜 계산이 필요한 초안에서 추론을 줄였을 때의 검증 통과율은 미측정이다.
- 채팅 생성(G1)도 같은 생성 모델을 쓰지만 이번에는 재지 않았다. G1의 요청 시간이 얼마나 줄지는 미측정이다.
- 초안의 내용 품질(목적 문장의 자연스러움, 운영상 타당성)은 자동 검사 밖이다. 단계·행동 수와 크기가 같다는 것만 확인했다.
- 측정 시각이 낮 1시대다. 다른 날 잰 절대 시간(예: 11-03 G2 18.83초)과 비교하지 않는다.
