# 조건 Tool 첫 조각은 완료보다 얼마나 먼저 오나 (#297)

2026-11-04 KST. 코드 변경 전 `40ac905`에서 관찰만 했다. `measure_tool_start.py`가
`llm_stream.ReplyStream.accept`를 감싸 Tool 호출 조각이 처음 보인 시각을 적고,
진행 포트로 `condition_applied/completed` 시각과 작업 ID를 적는다. 원본은 `report.json`이다.

## 조건

- 모델 `gpt-5.6-luna`, 공개 함수 `chat_planning(request, progress=port)`. 검색 port 없음, DB·HTTP 없음.
- 시작 초안: 행사 종류 MT, 예상 인원 30명. 이력 없는 한 턴.
- 입력 3개 × 3회, 입력을 번갈아 9턴.

| 입력 | 문장 |
| --- | --- |
| A 이름 | 행사 이름은 2026년 MT로 해 줘 |
| B 인원 | 인원은 35명으로 바꿔 줘 |
| C 인원+일정 | 인원은 40명으로, 일정은 12월 5일부터 1박 2일로 해 줘 |

## 결과

- 간격: 최소 1,157 · p50 1,785 · 최대 2,260ms. 조건 Tool 첫 조각 p50 1,966ms, 완료 p50 3,689ms.
- 9턴 모두 첫 조각의 호출 ID가 완료 이벤트의 `operation_id`와 같았다.
- 바꾸는 값이 많은 C가 간격이 길었다(1,974~2,260ms). 인자 조각을 더 오래 쓰기 때문으로 보이지만 확인하지 않았다.

## 해석과 한계

- 첫 조각에서 "조건을 반영하고 있어요"를 보내면 진행 중 줄이 이 표본에서 1.2초 이상 보인다.
  짧게 깜빡이지 않아 화면 쪽 최소 표시 시간은 넣지 않았다.
- SDK 수신 시각이다. 제품 화면에서는 BE 준비와 이력 길이만큼 모두 늦다. 변경 뒤 로컬 제품 화면 1턴
  ("지금 행사이름은 2026년 MT로, 2025년 MT기록의 일정과 똑같이 해줘")에서는 진행 중 줄이 4.7초에 뜨고
  0.7초 뒤 완료로 바뀌었다. 표본 1건이라 위 범위 밖이라는 것만 기록한다.
- 이력이 있는 턴, 검색이 앞에 오는 턴, 다른 모델은 재지 않았다.
