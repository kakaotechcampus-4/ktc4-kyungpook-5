# 1단계 — 행사 초안 State와 조건 변경 Tool

2026-10-24 · #166 · AI-PLAN-01·02·03. LLM이 선택할 조건 변경 행동의 처리기를 구현했다. 자연어 해석·Tool 바인딩·LangGraph 실행은 2단계다.

## 이 단계의 역할

```text
현재 초안 + 변경 요청 + 이번 사용자 메시지
    → update_event_conditions()
    → 근거·중복·날짜 검증
    → 적용/유지/거절 결과 + 새 초안
```

이번에는 사람이 변경 요청을 직접 만들어 실행한다. 다음 단계에서 LLM이 같은 요청 형식을 생성하고 tools Node가 처리기를 호출한다. 처리기 내부에서 자연어를 다시 해석하거나 LLM을 추가 호출하지 않는다.

## State

`PlanningDraft`는 `conditions`(현재 값), `condition_meta`(값별 tentative/잠정 또는 specified/명시와 근거), `deferred_topics`(보류 주제)를 묶는다. 상태는 새 객체로 반환하며 입력의 dict나 값을 직접 수정하지 않는다. 공통 조건 타입 `PlanningConditions`와 필드별 값 검증은 기존 `schemas.py`에서 재사용한다.

값이 None이면 미정이며 메타정보도 제거한다. BE에서 전달한 기존 값에 출처 정보가 없으면 메타정보 없이 받을 수 있다. `specified`는 사용자가 명시했다는 뜻이며 최종 승인·DB 저장과 다르다. 보류 주제는 조건 필드와 같되 시작일/종료일은 `dates` 하나로 묶는다.

## 입력과 결과

`UpdateEventConditionsInput`:

- `changes`: `SET(change={field, value}, status, evidence)` 또는 `CLEAR(field, evidence)` 목록.
- `defer_topics`, `resume_topics`: `{topic, evidence}` 목록. 현재 발화의 어떤 말로 보류/재개했는지 확인한다.
- `evidence`는 이번 사용자 메시지의 ID와 실제 포함된 문구다. “그걸로 하자”도 근거로 가능하며, 무엇을 수락했는지 판단하는 것은 다음 단계 LLM의 역할이다.

결과 `ConditionUpdateResult`:

| 필드 | 의미 |
| --- | --- |
| `status` | `applied`: 값·메타정보·보류 중 변화가 있음 / `unchanged`: 변화 없음 / `rejected`: 묶음 거절 |
| `draft` | 실제 적용 후 초안. 거절이면 원본 |
| `changed_fields` | 값 또는 메타정보가 바뀐 필드. 보류만 바뀌면 빈 목록일 수 있음 |
| `reason` | 거절 이유. 성공·유지에는 없음 |

필드별 값 타입이 잘못된 요청(음수 인원 등)은 입력 스키마에서 거절된다. 유효한 타입으로 들어온 요청의 날짜 관계·근거·중복 충돌은 처리기가 `rejected`로 돌려준다. 2단계의 tools Node가 두 종류를 모두 모델이 이해할 실행 결과로 변환해야 한다.

## 작은 실행 규칙

1. 한 호출의 모든 변경과 보류/재개를 검증한 뒤 함께 적용한다. 실패하면 원본을 유지한다.
2. 요청에 없는 조건은 유지한다. CLEAR는 무료(0원)가 아닌 미정으로 바꾸고 메타정보를 지운다.
3. 같은 값이라도 잠정 → 명시 등 메타정보가 바뀌면 적용이다. 같은 요청을 같은 결과에 다시 적용하면 unchanged다.
4. SET하면 해당 주제의 보류가 해제된다. CLEAR만으로는 보류를 해제하지 않는다.
5. 같은 필드를 두 번 바꾸거나, 같은 주제를 보류와 재개에 동시에 넣거나, SET한 주제를 동시에 보류하면 거절한다. 날짜 두 필드는 하나의 dates 주제다.
6. 날짜는 묶음을 적용한 최종 상태에서 확인한다. 시작일·종료일을 함께 옮기는 중간 상태는 검사하지 않는다.

상담인지 변경 요청인지는 이 함수가 판별하지 않는다. 상태 변경을 잘못 요청하는 LLM을 이 검증만으로 막을 수는 없으며 2단계의 대화 사례로 확인한다.

## 생성 보류와 질문 보류의 경계 (#205)

`deferred_topics`는 사용자가 잠시 의논하지 않기로 한 행사 조건의 주제다. 초안을 생성하지 말라는 의사와 구분한다. “인원을 60명으로 바꿔줘. 계획 초안은 만들지 마”라면 인원 변경과 생성 권유 보류만 적용하고 날짜나 장소 주제의 보류 목록은 유지한다. 미정값이 있다는 이유로 자동으로 보류 주제를 추가하지 않는다.

“날짜와 장소는 나중에 정할게. 초안도 아직 만들지 마”라면 두 주제 보류와 생성 권유 보류를 각각 적용한다. “그건 나중에” 같은 짧은 말도 직전 대화에서 가리키는 주제가 명확하면 문맥으로 처리한다. 주제가 불명확하면 무관한 항목을 추측해 바꾸지 않는다.

이번 수정에서는 대화 지침만 먼저 보완하고 다른 실행 코드와 모델 설정은 유지한다. Tool 처리기의 근거 원문 존재 검사가 의미까지 보장하지 않는 경계는 그대로 밝힌다. 이번 입력의 인원은 tentative 또는 specified 모두 허용하며, 원치 않는 보류 상태 추가를 주 지표로 본다. 기존 #196의 엄격한 기준과 원본 점수를 사후 변경하지 않는다.

검증은 같은 고정 상태에서 기존 지침과 수정 지침을 번갈아 적용한다. 핵심 입력은 각 지침에서 30회, 표현 변경과 정상적인 날짜 보류/여러 주제 보류/문맥 보류/보류 재개는 각 3회씩 비교한다. 인원과 다른 조건값, 보류 목록, 생성 권유 보류, 실제 생성 없음, 이력/JSON 왕복과 원본 보존을 확인한다. 모델 출력은 고정하지 않는다. 이번 비교는 지침 경계의 작은 합성 회귀 평가이며 실제 서비스 전체의 무오류 보장은 아니다.

실행한 90요청과 별도 후속 12요청의 결과는 [평가 기록](evaluation.md#생성-보류와-조건-질문-보류의-경계-205-2026-10-29)에 있다. 핵심 입력은 개선됐지만 모호한 재개 표현의 실패 1건을 보존했다. 이미 보관된 보류를 자동 삭제하는 변경은 하지 않는다.

## 확인할 사례

50명·25,000원 잠정 반영 + 날짜 보류, 무료와 CLEAR, 기존 값 유지, 날짜 묶음 이동/충돌 거절, 잘못된 근거, 중복 변경, 잠정 → 명시, 값 설정 시 보류 해제, 재실행, 입력 객체 보존을 API 없이 검증한다. 실제 모델의 자연스러움·판단 정확도는 아직 미측정이다.
