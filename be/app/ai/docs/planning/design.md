# 행사계획 대화 Agent 설계

> 현재 구현: 조건 대화와 기록 검색, 생성 권유, 채팅/버튼의 최초 생성, 공개 요청/결과와 JSON 상태 변환. 제품 DB/HTTP/FE 연결은 #187, P2 편집 후 AI 검토는 #177의 후속 범위다. 공개 호출은 [P1 전달 안내](p1-handoff.md)와 [공개 계약](p1-public-contract.md)을 따른다.
> 현재 개발 방향의 진입점이다. 기존 [단계별 설계](legacy/plan_architecture.md)와 [코드 따라가기](legacy/planning-walkthrough.md)는 legacy 구현 참고다. 명칭·상세 타입·반복 제한은 구현과 실제 대화 결과에 맞춰 조정한다.
> [5단계 생성 권유·P2 전달](step-05-generation.md)은 5-1 명세(#171)·5-2 내부 실행(#172)·5-3 로컬 HTTP/P2 연결(#173)을 구현했다. 두 요청 경로의 실제 UI 검증과 모델 품질 제한은 [평가 기록](evaluation.md)에 있다.

테스트 UI는 `tests/ui/planning/`에서 독립 실행한다(#174). AI의 검증·연동 협의용이며 제품 `fe/`의 라우터·컴포넌트·타입·설정은 수정하지 않는다. FE팀은 참고 자료와 합의된 계약을 바탕으로 제품 화면을 구현한다.

## 1. 만들려는 경험

LLM이 사용자와 행사 계획을 의논하면서 필요한 조건을 채운다. 현재 발화, 행사 초안, 최근 대화를 보고 **답변·질문·조건 변경·기록 검색** 중 필요한 행동을 선택한다. 필요한 정보는 자연스럽게 묻되 매 답변 끝에 빈칸 질문을 붙이지 않는다.

- “일단 50명 정도”는 잠정 조건으로 받아들인다. 다시 정확한 인원을 요구하지 않는다.
- “참가비 3만 원이면 어때?”는 먼저 상담한다. 질문에 등장한 숫자를 곧바로 설정하지 않는다.
- “날짜는 나중에”라고 하면 보류한 사실을 기억하고 곧바로 재질문하지 않는다.
- “왜?”라는 질문에는 직전 행동과 실제 결과를 설명한다. 확인할 수 없는 실패 원인은 만들어내지 않는다.
- 짧고 친근한 존댓말로 구체적인 내용에 반응한다. 반복 인사·칭찬·기계적인 항목 나열을 피한다.

관련 요구사항은 AI-PLAN-01~05와 AI-PLAN-08이다. P1은 조건 대화와 최초 계획 생성 요청까지이며, 생성 성공 결과로 P2를 구성한다. 단계 제외와 복원, 순서 변경은 P2 편집 범위다. P1 발화의 단계 편집 요구를 따로 추출해 최초 생성에 적용하는 기능은 범위에 넣지 않는다. 제품 저장, P2 편집 후 검토, 운영 신호 처리는 미연결이다.

## 2. 입력과 State: LLM에 무엇을 보여주나

기본 아이디어는 **사용자 발화 + 현재 행사 상태**다. “그걸로 하자”를 이해하려면 최근 대화와 직전 제안/Tool 결과도 함께 필요하다.

| 정보 | 예시 | 역할 |
| --- | --- | --- |
| 현재 발화 | “날짜는 미정이고 대략 50명 생각 중” | 이번 요청 |
| 행사 초안 `conditions` | MT, 인원 50, 날짜 미정 | 화면과 다음 판단의 기준 |
| 조건 부가정보 `condition_meta` | 인원: 잠정, 근거 메시지/문구 | 값의 의미와 변경 근거 |
| 대화 `messages` | 최근 사용자·AI 발화, Tool 호출/결과 | 지시 대상과 대화 흐름 이해 |
| 보류 주제 `deferred_topics` | dates | 당장 재질문하지 않을 내용 |
| 이번 실행 정보 | Tool 결과·호출 횟수·검색 출처 | 실제 반영 설명과 종료 제어 |

조건 값과 부가정보는 함께 갱신한다. 잠정 여부는 모델의 자신감 점수가 아니라 **사용자가 얼마나 정해둔 값인지**를 나타낸다. 초기 표시는 `tentative`(잠정)와 `specified`(명시한 값) 정도로 시작한다. `specified`도 행사 최종 승인·DB 저장을 뜻하지 않는다. 미정은 값 없음이며 0원은 무료다.

“40~50명”은 임의로 45명으로 바꾸지 않는다. 우선 대화에 범위를 남겨 상담하고, 수치가 필요해질 때 기준 인원을 정한다. 범위 전용 타입, 긴 대화 요약, 상세 감사 로그는 첫 구현 결과를 보고 결정한다.

행사/동아리 ID, 기준일·시간대, 버전, 검색 port는 서버가 전달하는 실행 문맥으로 둔다. Tool 인자에 LLM이 임의의 동아리나 행사 ID를 채우게 하지 않는다. 모델에는 판단에 필요한 상태만 제공한다.

## 3. Node와 Tool의 흐름

```text
사용자 발화 + 현재 초안 + 최근 대화
    → agent Node: LLM 호출
        ├─ 최종 답변 → 이번 턴 종료 → 답변·현재 초안을 UI에 전달
        └─ Tool 호출 → tools Node: 검증·실행·상태 갱신
                          → 결과 메시지와 함께 agent로 돌아감
```

| 구성 | 맡는 일 | 맡기지 않는 일 |
| --- | --- | --- |
| `agent` Node | 대화를 읽고 Tool/답변 선택, 결과를 읽고 자연스러운 답변 작성 | 임의 state 덮어쓰기 |
| `tools` Node | 허용 Tool 실행, 인자·값 검증, 초안 갱신, 결과 반환 | 사용자 의도 재분류용 LLM 호출을 매번 추가 |
| 조건부 edge | Tool 호출이 있으면 tools, 없으면 종료 | 별도 LLM으로 경로 재판정 |
| 입출력 어댑터 | 요청 문맥 준비, UI 응답 구성 | 대화 뒤에 고정 질문 강제 추가 |

ReAct의 행동 선택 → 실행 → 결과 확인 형태를 작게 사용한다. 내부 사고 과정을 출력하게 요구하지 않고 Tool 이름·인자·결과로 흐름을 관찰한다. Tool 하나마다 Node를 만들지 않는다. `graph.py`에서 연결을, `tools.py`에서 가능한 행동을 읽을 수 있도록 한다.

Tool이 필요 없는 설명은 모델 호출 한 번으로 끝날 수 있다. 조건 변경은 보통 판단 → Tool → 결과를 읽은 답변으로 이어진다. 검색과 생성의 실제 호출 수 및 개별 지연은 [평가 기록](evaluation.md)에 있다. 반복 가능한 응답 시간은 [기준 측정 문서](latency-baseline.md)에 따라 네 사례로 나눠 확인한다(#196). 고정 입력과 전체 요청 시간의 반복 실행기, 기록의 오프라인 집계를 구현했으며 세부 구간 관측과 실제 기준값 수집은 후속이다.

이번 그래프의 종료는 **한 턴의 처리 종료**다. 전체 행사 Agent의 수명은 [architecture.md](../architecture.md)의 상위 설계에 따른다. 상시 Agent의 대기·신호·운영 전환을 이번 P1 실험에 모두 구현하지 않는다.

## 4. Tool 설계: 행동 단위로 작게 시작한다

### `update_event_conditions` — 행사 초안 갱신

**언제 쓰나:** 사용자가 조건을 제시·수정·해제하거나 잠정 기준을 정할 때. 단순 상담, 과거 행사 값 질문에는 사용하지 않는다. 앞선 AI 제안을 사용자가 받아들이면 대화에서 대상을 확인해 사용한다.

입력 초안:

- `changes`: 허용 필드의 SET/CLEAR 변경 목록. SET에는 필드에 맞는 값, 잠정/명시 상태, 근거 메시지와 문구를 담는다.
- `defer_topics` / `resume_topics`: 날짜 등 질문 주제를 보류하거나 다시 다루기로 한 내용. 조건 변경 없이 보류만 할 수도 있다.
- JSON 세부 스키마는 `agent/tools.py`의 `UpdateEventConditionsInput`에 구현돼 있다. 필드별 값 타입을 검증하며 임의 key로 전체 state를 수정하는 Tool은 제공하지 않는다.

출력 초안:

- 적용 여부(`applied`, `unchanged`, `rejected`), 실제 변경 항목과 최신 초안.
- 거절 시 이해 가능한 이유(예: 종료일이 시작일보다 이름). LLM이 설명하고 필요한 사항을 질문할 수 있어야 한다.
- 결과는 state와 Tool 결과 메시지에 일관되게 반영한다. 근거 문구 일치만으로 의도 해석의 정확성이 보장되지는 않으므로 대화 평가도 한다.

여러 조건은 한 호출로 묶어 최종 조합을 검증한다. 초기에는 한 호출의 변경 묶음을 전부 적용하거나 거절하는 단순한 정책을 사용한다. 누락된 항목은 유지하고 CLEAR만 값을 비운다. 날짜 충돌은 임의 보정하지 않는다. 사용자가 새 값을 정하면 해당 주제의 보류도 해제한다.

### `search_past_events` — 근거가 필요한 과거 기록 조회

**언제 쓰나:** 과거 행사 사실을 묻거나, 현재 계획을 비교하는 데 기록이 도움이 될 때. 매 턴 자동 실행하지 않는다.

- 입력: 검색 질문 `query`. 동아리 범위·현재 행사 문맥은 코드가 주입한다.
- 출력: 사실, 출처, 미확인 내용, 기록 간 차이 또는 검색 실패.
- 검색은 현재 행사 조건을 변경하지 않는다. 사용자가 과거 값을 적용하자고 하면 별도 조건 변경 Tool을 사용한다.
- 기존 `retrieval.nodes.search_records`와 검색 port를 재사용한다. legacy의 계획 식별용 DTO를 거치지 않고 질문·현재 행사 맥락·서버 동아리 범위를 전달한다. 빈 결과와 호출 실패를 구분한다.

### 계산 Tool은 필요한 시점에 추가

참가비 수입 등 계산 수요가 확인되면 `calculate_event_costs`를 추가한다. 계산은 코드가 수행하며 추정 수입을 행사 총예산으로 자동 설정하지 않는다. 현재 조건 변경과 검색 Tool은 구현돼 있으며 계산 Tool은 제공하지 않는다.

### Tool 공통 원칙

LLM에는 “무엇을 할 수 있는가”와 “언제 사용하면 안 되는가”, 입력 의미를 짧게 설명한다. 대화·질문 전용 Tool은 만들지 않고 LLM이 직접 답한다. UI의 숫자·출처는 Tool이 만든 구조화 결과로 표시한다.

초기에는 Tool을 순서대로 실행해 같은 조건에 대한 병렬 갱신을 피한다. 실제 사용 모델의 병렬 호출 설정 지원 여부와 무관하게 실행 코드에서도 순서를 보장한다. 한 턴 반복 횟수를 제한하고, 한도에 도달하면 추가 Tool 호출을 막고 완료된 결과·미처리 내용을 설명한다. 현재 한 턴 Tool 시도는 최대 3회이며, 이력은 Tool 메시지 포함 60개다. 한도 안내는 #194, 압축 설계는 #195에서 다룬다. 같은 요청 재실행으로 중복 상태 변경이 생기지 않도록 확인한다.

## 5. 입력 → 행동 → 상태 → 답변 예시

아래 문구는 목표 경험이며 고정 답변 템플릿이 아니다.

| 사용자 입력 | 선택할 행동 | 상태와 답변에서 확인할 것 |
| --- | --- | --- |
| “MT 준비하려고 해” | 조건 변경, 도움이 되는 질문 | 유형 MT 반영. “대략 몇 명이 함께할 예정인가요?”처럼 한 주제로 시작 가능 |
| “날짜는 아직 모르겠고, 대략 50명에 인당 25,000원 생각 중” | 잠정 조건 변경 + 날짜 보류 | 인원 50·참가비 25000 잠정 반영. 날짜·인원 재질문 없이 반영 내용 설명 |
| “참가비 3만 원이면 어때?” | 상담 답변, 필요하면 질문 | 기존 참가비 유지. 적정성을 단정하지 않고 숙박/이동 등 판단에 필요한 내용을 의논 |
| “그럼 일단 3만 원으로 잡자” | 직전 제안을 참조해 변경 | 참가비 30000 잠정 반영, 다른 조건 유지 |
| “왜 반영이 안 됐어?” | 최근 state·Tool 결과를 보고 설명 | 실제 반영/거절/미실행 여부를 설명. 기록이 없으면 원인 미확인이라고 알림. 무관한 빈칸 질문 금지 |
| “작년 MT는 어디 갔어?” | 기록 검색 | 출처와 장소 설명. 올해 장소는 유지 |
| “인원은 40명으로 바꾸고, 작년 장소도 찾아줘” | 조건 변경 후 검색 | 인원 40 반영 + 과거 장소 참고. 검색만 실패했다면 반영된 인원과 검색 실패를 구분 |
| “참가비는 다시 미정으로 하자” | CLEAR | 무료(0원)로 바꾸지 않고 미정 처리 |
| “끝나는 날이 시작하는 날보다 앞서네. 왜 안 돼?” | 설명 | 날짜 규칙 설명. 사용자 대신 날짜를 만들어 넣지 않음 |

상담 중 새로운 조건이 함께 나오면 두 의도를 함께 처리할 수 있다. 의도를 반드시 하나로 분류하는 별도 분류기를 먼저 만들지 않는다.

## 6. LangGraph 조사와 적용 판단

공식 자료 확인일: 2026-10-24. 저장소 `be/uv.lock`에는 langgraph 1.2.12, langchain-core 1.6.3, langchain-openai 1.6.2가 기록되어 있다. 설치 환경·모델 호환성 검증과는 구분한다.

| 조사 내용 | 이번 설계에 적용 |
| --- | --- |
| [Quickstart](https://docs.langchain.com/oss/python/langgraph/quickstart): 모델에 Tool을 연결하고 호출 여부에 따라 실행·종료 | `StateGraph`로 agent/tools 연결이 드러나게 작성 |
| [Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api): State·Node·edge와 상태 갱신 규칙 | 메시지는 누적하고 초안은 검증한 최신값으로 갱신. 병렬 쓰기·무한 반복을 방지 |
| [Tools](https://docs.langchain.com/oss/python/langchain/tools): Tool 입력 스키마, 실행 문맥, `Command` 기반 state 변경과 결과 메시지 | 변경 성공 후 state와 Tool 결과를 함께 전달. 일반 dict 반환만으로 자동 state 변경된다고 가정하지 않음 |
| [Persistence](https://docs.langchain.com/oss/python/langgraph/persistence): checkpointer는 스레드의 상태를 이어주는 장치 | 현재 무저장 UI 실험에서는 필요한 상태를 매 요청 전달. 실제 세션 저장은 BE와 합의한 뒤 적용 |

현재는 순차 실행과 조건 변경/검색 결과의 구분을 직접 읽을 수 있도록 작은 커스텀 tools Node를 사용한다. 처음부터 별도 Agent 프레임워크로 옮기거나 멀티 Agent로 나누지 않는다.

현재 `llm.py`의 `ainvoke_with_tools`가 Tool 호출 또는 답변을 반환한다. 모델 설정·오류 변환은 공통 계층에 두고, 검색 내부의 구조화 호출도 기존 함수를 사용한다. 실제 설정 모델의 Tool 선택 → 실행 결과 → 답변 흐름을 [검증 기록](evaluation.md)에 남긴다.

## 7. 기존 구현과 UI·BE 경계

기존 고정 추출과 조회 판단, 질문 조립은 `features/planning/legacy/`에 분리해 참고용으로 보존한다. 현재 공개 P1과 테스트 UI는 새 Agent를 사용한다. 검증 함수와 검색 코드는 새 입력에 맞는지 확인 후 재사용한다. 기존 테스트 중 고정 질문 순서를 요구하는 것은 새 구조의 합격 기준으로 사용하지 않는다.

현재 테스트 UI는 새 Agent 전용 API를 호출한다. legacy API는 이전 평가용으로 보존한다. 초안·Tool 이력·잠정 표시를 새 테스트 계약으로 전달하며, 기존 DTO의 질문 상태·생성 가능 정책으로 변환하지 않는다. [3단계 연결](step-03-ui.md)을 참고한다.

- FE: 잠정 표시, 채팅과 조건 카드 일치, 질문이 없는 답변, 출처 표시를 확인한다. 본문에 이미 있는 질문을 별도 필드로 다시 출력하지 않는다.
- BE: 현재 행사 상태·대화 전달 방식, 버전·동시 요청, 초안의 저장/확정 책임을 합의한다. LLM이 행사 식별·권한을 결정하지 않는다.
- 생성 가능 여부와 P2 진입 정책은 [5-1 명세](step-05-generation.md)에 정리했다. 코드의 최소 조건과 LLM의 권유 타이밍을 구분하며, 권유만으로 생성/페이지 이동을 하지 않는다. legacy의 판정 규칙을 새 대화에 자동 강제하지 않는다.

## 8. 작은 구현 순서와 확인 기준

| 순서 | 작업 단위 | 완료를 확인하는 방법 |
| --- | --- | --- |
| 1 | 최소 State + 조건 변경 Tool 처리기: 구현 | SET/CLEAR/잠정/보류와 여러 조건 동시 변경을 코드로 확인. [명세](step-01-state-tool.md), [코드 예시](walkthrough.md) |
| 2 | agent/tools 그래프 + 대화 지침: 내부 구현 | [명세](step-02-agent-graph.md), [실제 대화 평가](evaluation.md). 상담·수락 등 10턴의 상태·Tool 확인, 답변 추측성 표현 과제 있음 |
| 3 | 기존 P1 테스트 UI 연결: 내부 구현 | [실행·확인 방법](step-03-ui.md). 상담 시 카드 유지, 수락·잠정 반영, 보류·실패 재시도 확인 |
| 4 | 과거 기록 Tool 연결: 내부 구현 | [명세와 실행](step-04-record-tool.md). 출처 유지, 현재 조건 보호, 조회 후 수락·조건 반영 확인 |
| 5-1 | 생성 권유·수락·P2 전달: 명세만 정리 | [설계 초안](step-05-generation.md). 보류·직접 요청·조건 변경·실패 사례와 내부 입출력 |
| 5-2 | 생성 Tool·별도 생성 graph: 내부 구현 | 권유 상태, 최신 조건으로 생성, 구조화 초안과 검증. 채팅/버튼 구분, 신규 주입 테스트 39개 |
| 5-3 | 로컬 P2 연결·실제 검증: 구현 | 채팅/버튼→초안 UI, 실패 시 보존·실측. 자발적 권유와 JSON 파싱의 남은 제한 기록 |

각 단위 착수 전 이슈와 상세 계약을 필요한 만큼 구체화하고 작업 단위로 커밋한다. 실행한 대화와 실제 모델 결과는 [평가 기록](evaluation.md)에 있다. 자동 비교는 상태와 Tool 중심이며 친근함과 답변 전체의 정확도, 자발적 권유 품질을 보장하지 않는다.

비교할 것은 ① 값 반영과 무관한 값 보존 ② 질문·상담을 변경으로 오해하지 않는지 ③ 보류/이미 답한 내용의 재질문 ④ 설명 요청 해결 ⑤ 답변과 실제 상태 일치 ⑥ 호출 수·응답 시간이다. 친근함과 자연스러움은 사람이 직접 대화하며 검토한다.

평가셋 확대, 실패 유형별 분석, 검색 품질 개선(#156)은 후속 품질 과제로 유지한다. 먼저 작은 흐름을 실행해보고, 실패가 실제로 나온 부분부터 명세와 Tool 설명을 보완한다.
