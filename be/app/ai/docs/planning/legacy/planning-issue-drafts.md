## 초안 A — 작업 1

**제목: [AI] 행사계획 조건 스키마와 입력 검증 기준 정의**

### 무엇을 만드는가

행사계획 대화에서 수집할 조건을 `PlanningConditions`라는 공통 내부 타입으로 정의한다. 이후 모델 추출과 질문 선택이 같은 필드·값 규칙을 사용하도록 하며, 모르는 값과 잘못된 값을 구분한다.

관련 요구사항: `AI-PLAN-01`, `AI-PLAN-03`의 조건 표현·검증 기반. 사용자 기능 전체의 완료를 의미하지 않는다.

### 흐름 예시

```text
조건 입력 {headcount: 40, fee_per_person: 0, location: null}
  → PlanningConditions.model_validate(...)
  → 40명 / 무료 / 장소 미정으로 보관

조건 입력 {headcount: 0}
  → 인원은 1 이상이어야 한다는 검증
  → ValidationError (잘못된 조건을 그대로 수용하지 않음)
```

`null`은 미정이고, 금액 `0`은 무료 또는 예산 0이다. 종료일이 시작일보다 이른 경우도 검증에서 거절한다.

### 작업 범위

- [ ] 제목·유형·인원·참가비·예산·장소·시작일·종료일의 내부 타입 정의
- [ ] 숫자 범위, 문자열 길이·공백, 날짜 형식·순서 검증
- [ ] 기존 공개 `EventConditions`와 내부 타입의 경계를 문서화
- [ ] `plan_architecture.md`에 작은 작업 단위와 향후 연결 방향 정리
- [ ] 정상·미정·무료·잘못된 값에 대한 단위 테스트 추가
- [ ] README와 관련 설계·계약 문서에 현재 상태 반영

범위 밖: LLM 호출, DB 저장, 공개 계약 변경, LangGraph 실행 그래프 구현. 향후 단계 설계는 초안이며 구현 중 바뀔 수 있다.

### 완료 조건

- [ ] 유효한 조건과 미정 값을 생성할 수 있고, 잘못된 타입·범위·날짜를 거절한다.
- [ ] 기존 공개 계약을 사용하는 기능의 회귀 테스트가 통과한다.
- [ ] AI 내부 후보 조건과 BE 저장 모델이 동일한 계약이라는 오해가 없도록 문서에 경계를 명시한다.

### 현재 로컬 상태·검증

구현 파일은 `features/planning/legacy/schemas.py`, 테스트는 `tests/test_planning_conditions.py`다. 작업 1~3 통합 상태에서 AI 테스트 총 472개가 통과했다. 이 이슈의 PR을 분리한 뒤 해당 커밋 기준 테스트 결과를 추가한다.

### 참고 자료 · 관련 이슈

- 상위 작업: https://github.com/kakaotechcampus-4/ktc4-kyungpook-5/issues/67
- 설계: `be/app/ai/docs/planning/legacy/plan_architecture.md`

## 초안 B — 작업 2

**제목: [AI] 대화에서 행사 조건 변경을 추출하고 검증하여 반영**

### 무엇을 만드는가

사용자 발화에서 실제로 바꾸려는 조건만 LLM의 구조화 출력으로 추출한다. 모델이 반환한 변경과 발화 근거를 코드로 검증한 뒤 후보 조건에 반영하여, 언급하지 않은 기존 값이 사라지거나 모호한 요청이 임의로 확정되는 일을 줄인다.

관련 요구사항: `AI-PLAN-01`, `AI-PLAN-02`, `AI-PLAN-03`의 추출·변경 적용 부분.

### 흐름 예시

아래 JSON은 핵심 필드만 표시한 설명용 예시다.

```text
기존 조건: 인원 60명, 장소 학생회관
현재 발화(m1): “40명으로 하자”
  → extract_condition_changes()
  → 모델 구조화 출력:
    {op: SET, change: {field: headcount, value: 40},
     evidence: {message_id: m1, quote: "40명으로 하자"}, ...}
  → validate_and_apply(): 근거·값·전체 조건 검증
  → candidate_conditions: 인원 40명, 장소 학생회관
    status: APPLIED

“인원을 좀 줄이자”
  → 확정할 숫자가 없으므로 unresolved에 headcount 기록
  → 기존 인원 보존, status: NEEDS_CLARIFICATION
  → 다음 질문을 정하는 작업 3으로 전달
```

구조화 출력은 모델 응답 형식을 제한하는 장치다. 의미가 맞다는 보장은 아니므로 근거 확인·값 검증과 실제 발화 평가를 별도로 수행한다.

### 작업 범위

- [ ] 입력 메시지·기존 조건·문맥·기준 날짜·제안 수락의 내부 계약 정의
- [ ] `SET`/`CLEAR` 변경, 발화 근거, 미해결 사유의 구조화 출력 정의
- [ ] 별도 프롬프트 파일과 공통 구조화 출력 호출 연결
- [ ] 발화 근거·중복 변경·제안 수락 근거 검증
- [ ] 변경하지 않은 필드 보존 및 전체 조건 검증 후 후보 생성
- [ ] 날짜 충돌 시 해당 턴 변경 전체를 취소하고 원본 조건 반환
- [ ] 오류 전파·원자성 테스트 및 실제 모델 평가 스크립트·결과 기록
- [ ] 코드 따라가기 문서에 입력 → 구조화 출력 → 검증 → 후보 조건 설명

범위 밖: BE 저장·낙관적 잠금, 공개 `plan_chat`, 질문 문구 생성, 과거 행사 검색, 실제 LangGraph 연결. `base_version`을 전달하더라도 DB 최신 버전 충돌을 검사하는 구현은 아니다.

### 완료 조건

- [ ] 명확한 설정·해제를 반영하고 언급하지 않은 조건을 보존한다.
- [ ] 모호한 요청은 기존 값을 보존한 채 미해결 항목으로 전달한다.
- [ ] 날짜 충돌은 `VALIDATION_FAILED`와 원본 조건을 반환한다.
- [ ] 잘못된 응답·근거와 모델 호출 실패를 정상 성공으로 처리하지 않는다.
- [ ] A의 실제 스키마와 연결한 테스트 및 실제 공급자 구조화 출력 호출 결과를 남긴다.
- [ ] 평가 데이터·실행 조건·수치·한계를 재현 가능한 형태로 기록한다.

### 현재 로컬 상태·검증

- 주요 코드: `schemas.py`, `nodes.py`, `prompts/extract_conditions.md`.
- gpt-5.6-luna / `planning-conditions-v1` / 합성 사례 18개 순차 1회 실행에서 최종 조건·상태·미해결 필드가 **18/18 일치**했다.
- 추출 호출 중앙값 2,178ms, 최대 2,692ms. BE 저장·FE 표시 시간은 제외한다.
- 정답은 AI 작성 후 사람 검수 전이다. 모델 자체의 일반 정확도나 실제 서비스 품질을 보장하는 결과가 아니다.

구현 중 공급자가 discriminated union의 `oneOf` 스키마를 HTTP 400으로 거절했다. 필드별 Literal과 값 타입 검증은 유지하면서 일반 Union의 `anyOf`로 바꿨고, 프롬프트·평가 입력은 그대로 유지한 재호출에서 18건 모두 처리됐다. 자유 JSON으로 우회하는 대신 타입 계약을 유지했다. 공급자 호환성 회귀 테스트와 해당 경위를 문서에 남겼다.

### 참고 자료 · 관련 이슈

- 선행: 초안 A — 조건 스키마가 추출 결과의 최종 검증 기준이다. 등록 시 실제 번호로 교체한다.
- 상위 작업: https://github.com/kakaotechcampus-4/ktc4-kyungpook-5/issues/67
- 평가: `be/app/ai/docs/planning/legacy/planning-evaluation.md`
- 실행 결과: `be/app/ai/docs/planning/legacy/evaluation-results/planning-conditions-2026-10-22.json`
- 흐름 설명: `be/app/ai/docs/planning/legacy/planning-walkthrough.md`

## 초안 C — 작업 3

**제목: [AI] 조건 추출 결과에 따라 다음 질문을 선택하고 보류 상태 관리**

### 무엇을 만드는가

조건 추출 결과를 받아 지금 확인할 질문 하나를 선택한다. 이미 알려진 값과 앞서 물었거나 미룬 항목을 고려하여 같은 질문을 계속 반복하지 않고 행사계획 대화를 이어간다.

관련 요구사항: `AI-PLAN-02`, `AI-PLAN-03`의 질문 선택 부분. 문구는 코드 템플릿을 사용하여 추가 LLM 호출 없이 결정한다.

### 흐름 예시

```text
기존 조건: 행사 유형 MT, 인원 60명
사용자: “인원을 좀 줄이자”
  → 작업 2: headcount가 모호하다고 반환
  → select_next_question(): 모호한 항목 우선 확인
  → 인원 질문 + last_question_fields=[headcount]

사용자: “40명으로 하자”
  → 작업 2: headcount=40 반영
  → select_next_question(): 인원은 채워졌고 일정이 비어 있음
  → 일정 질문

대신 사용자가 “아직 모르겠어”라고 답하면
  → 작업 2: DEFERRED로 해석
  → 작업 3: 마지막 질문의 인원을 보류 상태에 기록
  → 다음 미정 항목 질문으로 진행
```

실제 질문은 템플릿 문구로 반환된다. “모르겠다”의 의미 해석은 추출 모델, 보류 기록과 질문 우선순위는 코드가 담당한다.

### 작업 범위

- [ ] 행사별 질문 상태와 질문 결과 타입 정의
- [ ] 날짜 충돌 → 현재 모호한 항목 → 아직 묻지 않은 미정 항목 순으로 선택
- [ ] 이미 채운 값·앞서 질문한 값·보류한 값의 기본 반복 질문 억제
- [ ] 날짜를 하나의 질문 주제로 묶고, 일부만 있으면 미정 날짜만 질문
- [ ] 명시적 수정·해제·재질문 상황에서 상태 갱신
- [ ] 자유 입력과 “아직 모르겠어요” 응답을 위한 질문 정보 반환
- [ ] 행사 간 상태 혼용 방지 및 추출 결과와의 연결 테스트
- [ ] 실제 2턴 대화 평가와 코드 따라가기 문서 갱신

범위 밖: 질문 상태의 BE 영속 저장, 장기 대화 전체 미해결 목록 관리, FE 렌더링, 계획 생성 가능 여부 판정. 질문이 없다는 결과가 곧 계획 생성 준비 완료라는 뜻은 아니다.

### 완료 조건

- [ ] 추출 결과의 날짜 충돌·모호함·미정 조건에 맞는 질문을 반환한다.
- [ ] 답을 받거나 보류한 항목에서 다음 항목으로 넘어간다.
- [ ] 명시적으로 다시 다루는 항목은 기존 질문 이력 때문에 무시하지 않는다.
- [ ] 다른 행사의 질문 상태를 잘못 재사용하면 거절한다.
- [ ] B의 실제 결과와 연결한 다중 턴 검증 및 문서 갱신을 완료한다.
- [ ] 상태 저장과 여러 미해결 항목의 장기 관리는 후속 작업으로 명시한다.

### 현재 로컬 상태·검증

- 주요 코드: `features/planning/legacy/questions.py`, 질문 정책 `planning-questions-v1`.
