# 기록 색인·검색 평가 기록

청킹·임베딩·검색 규칙을 바꿀 때 같은 조건으로 다시 재고, 이전 값과 비교하기 위한 기록이다.
최근 기록을 위에 쌓는다. 값은 예시 기록(`tests/fixtures/records/`) 기준이다.

## 재는 방법

```bash
cd be && uv run python app/ai/scripts/check_index_record.py [--json 결과.json]
cd be && uv run python app/ai/scripts/eval_retrieval.py [--search vector|records] [--max-rounds N] \
    [--header full|file|none] [--holdout] [--no-cache] [--json 결과.json]
```

- 키가 필요해 CI에서 돌리지 않는다. `be/.env`의 `AI_EMBEDDING_*`를 쓰고, `--search records`는 `AI_API_*`·`AI_MODEL`도 쓴다.
- 색인(`check_index_record.py`): 예시 기록 4종과 실제 한컴 PDF(`be/tests/fixtures/records/sample_report.pdf`, BE 파서 경유)의 청크 수·길이·시간
- 검색(`eval_retrieval.py`): 예시 기록 12종을 메모리 port에 넣고 [평가 질문](../tests/fixtures/eval/README.md)으로 상위 5개를 본다
  - 지표: Hit@1·3·5, MRR, Recall@1·3·5. 정의는 평가 질문 README에 있다. 개발용·확인용과 요구사항별로 나눠 보인다
  - `--search vector`: 질문을 그대로 임베딩해 찾는다(기준점)
  - `--search records`: 기록 검색 `search_records` 전체를 부른다. 검색어가 여러 개면 찾은 청크를 검색어 순서대로 이어 검색 지표를 잰다.
    결과(사실·확인하지 못한 것·자료 간 차이)를 정답과 비교한 결과 지표와 모델 응답이 잘못돼 실패한 수도 낸다
  - `--max-rounds`: `records`의 검색 횟수. 기본값은 기록 검색의 기본값(1, 검색어 정리만)이고 2면 재검색까지 잰다
  - `--header`: 청크 임베딩 이름표. `full` 문서명·위치(현재 색인), `file` 문서명만, `none` 없음
  - `--holdout`: 확인용 질문도 잰다. 개선하는 동안에는 끄고, 기록에 남길 측정에서만 켠다
  - 캐시: 임베딩은 모델·차원·글이, LLM 응답은 모델·출력 형식·메시지가 같으면 `be/app/ai/scripts/.cache/`에 저장한 값을 다시 쓴다.
    같은 조건이면 같은 결과로 다시 잴 수 있고 요청이 나가지 않는다. 캐시 파일은 커밋하지 않는다.
    캐시에서 꺼내면 걸린 시간이 실제와 다르고 LLM 응답의 흔들림이 보이지 않으므로, 기록에 남길 비교는 `--no-cache`로 3번 재서 평균과 범위를 적는다
  - 결과 JSON에 커밋 해시, 커밋하지 않은 변경이 있었는지(`dirty`), 설정값(검색 방식·검색 횟수·캐시 사용 여부 포함), 질문별 찾은 청크·결과·결과 지표·시간·요청 수·캐시에서 꺼낸 수가 남는다

평가 세트

- 기록: 예시 기록 12종. 헷갈리기 쉬운 연도·행사·충돌·지시문 함정은 [예시 기록 README](../tests/fixtures/records/README.md)의 함정 표에 있다
- 질문: 50개(개발용 38·확인용 12). AI-PLAN-04 16개, AI-RET-01 21개, AI-RET-03 10개, AI-COMMON-01 3개.
  정답은 사람이 검토해 확정했고, 형식과 판정 기준은 [평가 질문 README](../tests/fixtures/eval/README.md)에 있다

실험 원칙

- 한 번에 하나만 바꾼다. 검색 방식·이름표·청크 크기 등을 함께 바꾸면 무엇이 효과였는지 알 수 없다
- 개선하는 동안에는 개발용 질문만 보고, 기록에 남길 측정에서만 확인용 질문을 켠다
- 기록에는 커밋 해시와 조건을 함께 적는다. 커밋하지 않은 변경이 있는 상태(`dirty`)로 잰 값은 남기지 않는다

질문이나 정답을 바꾸면 이전 기록과 직접 비교할 수 없으므로 기록에 적는다.
아래 2026-10-07 기록은 이전 방식(예시 기록 4종, 질문 6개, 상위 3개)으로 잰 값이라 평가 질문 세트로 잰 값과 직접 비교하지 않는다.

### 관찰

- **고치려던 문제는 고쳐졌다.** 없는 충돌이 1.7 → 0.3으로 줄었고, 회칙의 10%와 회고의 15% 제안을 묶던 q20이 3번 모두 사실 2/2가 됐다.
  q15의 "2025 봄 MT 버스 기록 없음"도 3번 중 2번 냈다(수정 전 0번). 다만 그 2번은 가을 MT의 30분 지연을 사실로 내지 않아,
  q15의 두 정답을 함께 맞힌 적은 아직 없다.
- **1차 수정은 다른 행사의 값을 사실로 내게 만들었다.** "각각 사실로 적는다"가 "다른 연도나 다른 행사의 기록은 사실로 쓰지 않는다"와 부딪혀,
  q01(봄 MT 회비)에 가을 MT 장부 기록을 사실로 내는 등 "그 밖"의 틀린 사실이 7 → 19로 늘었다. 2차 수정에서 10으로 줄었다.
- **틀린 사실 합계가 그대로인 것은 대부분 측정의 한계다.**
  - 장부 출처: 정답 출처는 값이 원문에 그대로 있는 청크만 두므로, 행을 더해야 하는 장부(신환회 식당·다과, 가을 MT 회비 세 줄 등)는 정답 기록에서 빠져 있다.
    이 장부에서 낸 맞는 사실도 다른 기록으로 센다.
  - q49("다음 MT 회비 정할 때 참고할 기록 있어?"): 다른 연도 MT의 회비와 정산을 사실로 낸다. 정답은 2025 봄·가을 회비만 두었지만 참고할 기록으로 볼 수도 있어 라벨을 다시 볼 대상이다.
- **진짜 충돌을 덜 찾았는지는 판단하기 어렵다.** q43(확인용)은 수정 전 3번 모두, 두 수정 모두 3번 중 2번 찾았다. 충돌 질문이 하나라 개수 차이 1은 흔들림과 구분되지 않는다.
- **같은 검색어 정리로도 묶음마다 검색 지표가 다르다.** 검색어 정리 프롬프트는 바꾸지 않았는데 Hit@1이 0.58, 0.55, 0.58로 나왔다.
  q10은 2차 수정 측정 3번 모두 회고 청크를 찾지 못해 "없음"으로 냈다(수정 전 3번 중 1번). 프롬프트 차이가 아니라 검색어 정리의 흔들림이다.

결론: 2차 수정을 남긴다. 사실 수는 수정 전과 같고, 없는 충돌과 q20이 나아졌으며, 늘어난 틀린 사실은 대부분 장부 출처와 q49 라벨에서 나왔다.
